# Intégrations au système (bureau)

Notes d'implémentation de Seaglass, lues à la demande (index dans [`CLAUDE.md`](../CLAUDE.md)). La session média d'Android est dans [`android.md`](android.md).

## SMTC, MPRIS, Discord, ListenBrainz, zone de notification, démarrage

- **SMTC** (`integrations/smtc.rs`) : `ISystemMediaTransportControlsInterop::GetForWindow(hwnd de la fenêtre main)` sur un thread dédié (MTA). L'acteur notifie `Observers` à chaque `player-state` émis ; le thread ne touche SMTC que si les métadonnées, le statut ou les boutons changent, et la timeline toutes les 5 s ou après un saut. Boutons → `Cmd::SetPaused(bool)`, `Next`, `Previous` (`try_send`, thread WinRT). Vérifié avec l'API `GlobalSystemMediaTransportControlsSessionManager` : session `seaglass.exe`, titre / artiste / album / vignette / timeline, et Play / Pause / Suivant / Précédent pilotent bien le lecteur.
- **Boutons de la miniature** (0.5.31, #333, `integrations/thumbbar/`, Windows) : Précédent / Lecture-Pause / Suivant sous la miniature de la barre des tâches, par `ITaskbarList3::ThumbBarAddButtons`, avec les features `Win32_UI_Shell`, `Win32_UI_WindowsAndMessaging`, `Win32_Graphics_Gdi` et `Win32_System_Registry` de la crate `windows` déjà présente. Les clics arrivent en `WM_COMMAND` (`THBN_CLICKED`, identifiant = rang du bouton) : la fenêtre `main` est sous-classée par `SetWindowSubclass` (cohabite avec tao), posé dans `setup`, qui tourne sur le thread de la fenêtre ; un sous-classement doit être posé depuis ce thread. Tout l'état Win32 (`ITaskbarList3`, icônes, boutons posés) vit dans un `thread_local` du thread principal ; l'observateur `Observers::thumbbar` calcule une vue (lecture, titre chargé, suivant / précédent, langue ; testée) et ne passe par `run_on_main_thread` que si elle change. `ThumbBarAddButtons` échoue tant que le bouton de la barre des tâches n'existe pas (fenêtre créée cachée) et ne marche qu'une fois par bouton : les boutons sont posés sur le message `TaskbarButtonCreated` (`RegisterWindowMessageW`), reçu à l'affichage et après un redémarrage de l'explorateur, puis mis à jour par `ThumbBarUpdateButtons`. Icônes dessinées en code (`glyphs.rs`, anticrénelage 4×4, testé) à la taille `SM_CXSMICON`, blanches sur barre sombre et gris foncé sur barre claire (`HKCU\…\Themes\Personalize\SystemUsesLightTheme`), redessinées sur `WM_SETTINGCHANGE` si le thème a changé ; le jeu précédent est gardé un tour avant `DestroyIcon`. `ChangeWindowMessageFilterEx` laisse passer les messages de l'explorateur si l'app tourne en administrateur. Fenêtre cachée dans la zone de notification : pas de miniature, rien à faire. Progression dans l'icône (`SetProgressValue`) écartée : c'est la convention Windows d'un téléchargement ou d'une copie en cours.
- **MPRIS** (0.5.6, #312, `integrations/mpris/`, Linux) : l'équivalent du SMTC. Nom `org.mpris.MediaPlayer2.seaglass` sur le bus de session, objet `/org/mpris/MediaPlayer2`, `zbus` 5 en dépendance directe propre à Linux, avec ses features par défaut (`async-io`), soit la configuration déjà compilée pour `tauri-plugin-opener` et `tauri-plugin-single-instance`. Le `zbus` 4 du lockfile vient de `secret-service` (`keyring`). Observateur `Observers::mpris` (`watch` de `NowPlaying`, qui porte aussi le volume) ; une tâche tokio tient l'interface `Player` et n'émet `PropertiesChanged` que pour ce qui change (`logic.rs`, logique pure testée aussi sous Windows). `Position` n'est jamais signalée (spécification) : elle est estimée à la lecture depuis la dernière position reçue, et un écart de plus de 1,5 s sur le même titre émet `Seeked`. `Changing` (chargement) garde le statut précédent, MPRIS n'ayant que `Playing` / `Paused` / `Stopped`. `mpris:trackid` = `/dev/seaglass/app/track/<id>`, `xesam:artist` = une entrée avec les artistes déjà joints, pochette 320 par son URL. Commandes vers l'acteur : `Play`/`Pause` → `SetPaused`, `PlayPause` → `TogglePause`, `Stop` → pause (pas d'arrêt dans le lecteur), `Seek` relatif (au-delà de la fin → `Next`, avant le début → 0), `SetPosition` ignoré si le titre a changé ou hors bornes, `LoopStatus` ↔ `Repeat` (`None`/`Playlist`/`Track`), `Shuffle`, `Volume` (0–1 → 0–100, 0 si coupé). `Raise` réaffiche la fenêtre (`tray::show_main`) ; `CanQuit` faux, `OpenUri` non pris en charge, pas de `TrackList`. La logique renvoie `Jump` et non `Cmd` : détruire un `Cmd` dans un test casse le binaire de test Windows (voir `android.md`). Vérifié dans WSL le 2026-11-11 avec `playerctl` et `dbus-monitor` : métadonnées et pochette, play / pause / play-pause, position absolue et relative, suivant, précédent, volume, répétition, aléatoire, signaux `PropertiesChanged` et `Seeked`. Pas vérifié : applet média d'un vrai bureau (GNOME, KDE) et touches média du clavier.
- **Présence Discord** (0.4.92, #215, `integrations/discord/`, bureau seulement) : aucune crate, IPC local de Discord écrit à la main (`ipc.rs`) : named pipe `\\.\pipe\discord-ipc-0..9` (socket Unix `$XDG_RUNTIME_DIR/discord-ipc-<n>` ailleurs), trames `opcode u32 LE + longueur u32 LE + JSON`, poignée de main `{v: 1, client_id}` → `READY`, puis `SET_ACTIVITY` (`args.pid`, `activity` ou `null`), `PING` → `PONG`, `CLOSE` = connexion perdue ; lecture dans une tâche à part, arrêtée avec la connexion (le pipe ne se ferme qu'avec ses deux moitiés, et Discord efface alors la présence). Activité (`activity.rs`, logique pure testée) : type 2 « Écoute », `status_display_type` 1 (l'artiste dans la liste des membres), titre en `details`, artistes en `state`, pochette 320 par son URL `https://` (pas d'asset téléversé) et album en info-bulle, `timestamps` début / fin (barre de progression), bouton « Ouvrir dans TIDAL » (`tidal.com/browse/track/<id>`) ; textes coupés à 128 caractères, complétés jusqu'à 2. Rien en pause ni à l'arrêt, activité précédente gardée pendant un chargement ; renvoyée seulement si le titre ou le texte change, si elle apparaît ou disparaît, ou après un saut (début décalé de plus de 2 s) ; 4 s au moins entre deux envois (Discord : 5 par 20 s), le dernier état attend son tour. Observateur `Observers::discord` (`watch` de `NowPlaying`). **Réglage** `UiSettings::discord` (**désactivé par défaut**), copié dans un `watch` global par `apply_to_backend` ; actif : connexion, nouvel essai toutes les 15 s si Discord est fermé ; désactivé : connexion fermée. **Identifiant** : `DISCORD_CLIENT_ID` du `.env` (`build.rs` → `SEAGLASS_DISCORD_CLIENT_ID`, variable au lancement prioritaire), application Discord nommée « Seaglass » (ce nom s'affiche dans « Écoute … ») ; sans lui, `discord_available` vaut faux et Réglages › Application › Discord est masqué. Tests : `cargo test discord` (faux Discord sur `tokio::io::duplex`) ; **`cargo test live_discord -- --ignored --nocapture`** contre le vrai Discord (lancé sur le poste) : activité acceptée le 2026-11-06 (application `1568264624166535200`, réponse avec `type` 2, `status_display_type` 1, bouton et horodatages ; affichée 20 s). Pochette et suivi de la lecture dans l'app pas encore vus à l'œil. Aperçu : `?route=settings&tab=app&discord=1`.
- **ListenBrainz** (0.5.84, #431, `integrations/listenbrainz/`, bureau **et Android**) : envoi facultatif des écoutes, sans clé d'application (jeton utilisateur, `Authorization: Token …`). **Jeton** collé dans Réglages › Application › ListenBrainz (`ListenBrainzSettings.svelte`), vérifié par `GET /1/validate-token` avant d'être gardé dans le keyring (`seaglass` / `listenbrainz`, JSON `{token, user}`) ; jamais relu par l'UI ni journalisé (`Token` sans `Debug`). **La présence du jeton est l'interrupteur** : aucun réglage dans `UiSettings`, donc rien dans la sauvegarde des réglages. Vérifié le 2026-11-18 : `validate-token` répond **200 même pour un jeton invalide** (`{"valid": false}`), valide = `valid: true` + `user_name` ; `submit-listens` avec un mauvais jeton : 401 ; limites 1 000 écoutes par requête et 10 240 octets par écoute (champs libres coupés à 500 caractères) ; en-têtes `X-RateLimit-*` (`Reset-In` en secondes). **Format** (`payload.rs`, testé) : `track_name` avec la version entre parenthèses, artistes joints par « , », `release_name`, `additional_info` : `isrc`, `duration_ms`, `media_player` / `submission_client` = `Seaglass` et leurs versions, `music_service: "tidal.com"` (domaine reconnu par ListenBrainz), `origin_url: https://tidal.com/track/<id>`. **Début d'un titre** : `playing_now` envoyé depuis `note_listen` quand le titre joue vraiment (pas en pause, `ListenTracker::announce`, une fois par écoute, de nouveau en repeat One), jamais pendant un blind test ; sans file, sans attendre la réponse. **Écoute comptée** (règle de `player::listen`) : mise en file SQLite (`store/scrobbles.rs`, 10 000 au plus, les plus anciennes abandonnées) avec `listened_at` = maintenant − temps réellement écouté, figé à l'entrée (un lot renvoyé garde ses dates). Les écoutes reçues d'un autre appareil (#430) entrent dans `plays` sans passer par là : jamais renvoyées. Rien n'est mis en file sans compte. **Tâche d'envoi** : une écoute → `single`, plusieurs → `import` par 100 ; réseau, 5xx, 429 → nouvel essai après `X-RateLimit-Reset-In` ou une attente croissante (30 s à 30 min) ; 401/403 → jeton marqué refusé (toast, message dans les réglages), envoi suspendu jusqu'au prochain jeton, file gardée ; 400/413 sur un lot → reprise une écoute à la fois, l'écoute refusée seule est retirée. « Retirer » oublie le jeton et **vide la file**. Aperçu : `?route=settings&tab=app&listenbrainz=1|refused` (jeton contenant « bad » refusé). **Pas encore vérifié** avec un vrai compte (écoutes visibles sur listenbrainz.org, correspondance MusicBrainz), ni sur le S21.
- **Zone de notification** (#83, `integrations/tray.rs`, feature `tray-icon` de `tauri`) : icône toujours créée (clic gauche = afficher la fenêtre, ou la cacher si elle est visible et au premier plan, #226 : `click_hides`, testé ; cliquer sur l'icône prend le focus à la fenêtre juste avant, donc une perte du focus de moins de 500 ms compte comme au premier plan, `note_focus` sur `WindowEvent::Focused` ; menu : titre en cours grisé, Lecture/Pause, Suivant, Précédent, Afficher Seaglass, Mini-lecteur, Quitter), commandes par `Cmd` comme SMTC, menu et info-bulle tenus à jour en observateur de l'acteur (`Observers::tray`, textes recalculés seulement si la vue ou la langue change ; libellés testés). Réglage `UiSettings::close_action` (`quit` par défaut, `tray`) dans Réglages › Application › Fenêtre, copié côté backend dans un atomique (`apply_to_backend`, au démarrage et par `set_ui_settings`) et lu sur `CloseRequested` de `main` : `prevent_close` + `hide`, **seulement si l'icône existe** (sinon l'app deviendrait inaccessible). Quitter = `app.exit(0)` (mpv arrêté, mise à jour reportée installée). Démarrage réduit : l'autostart passe `--minimized`, une entrée `Run` active est réécrite au lancement pour l'ajouter (`refresh_autostart`) ; la fenêtre `main` est `visible: false` dans la config et affichée dans `setup` sauf avec `--minimized` et une icône créée. Une seule instance (`tauri-plugin-single-instance`, validé dans #118, enregistré en premier) : un second lancement réaffiche la fenêtre existante puis se ferme, sauf s'il porte `--minimized` (`tray::show_on_second_launch`, testé). Sous Windows le plugin ne tire que `windows-sys` ; `zbus` et les crates `async-*` du `Cargo.lock` ne servent que sous Linux. Aperçu : `?route=settings&tab=app&tray=1`.
- **Mini-lecteur** (0.5.36, #384, `commands/mini_player.rs`, bureau) : deuxième fenêtre `mini` (`WebviewWindowBuilder`, 360 × 112 logiques, sans décorations ni redimensionnement, `always_on_top` réglable) qui charge la même page ; `main.ts` monte `views/MiniWindow.svelte` au lieu d'`App` quand l'étiquette de la WebView est `mini` (`isMiniWindow`, lue dans les métadonnées, sans IPC ; `?mini` dans l'aperçu). Elle ne lit que `player-state` et les favoris, et n'envoie que les commandes du lecteur. Une seule des deux fenêtres est visible : ouvrir le mini-lecteur cache `main`, fermer `mini` (`CloseRequested` : bouton, Échap, Ctrl+M, Alt+F4) réaffiche `main` par `tray::reveal_main`, et `tray::show_main` (icône, menu, relance de l'app) ferme d'abord `mini`. Création hors du thread principal (commande `async`, tâche pour le menu de l'icône) : une WebView créée depuis un gestionnaire d'événement bloque sous Windows. Réglages `mini_player` en SQLite : `onTop` (vrai par défaut) et position physique, gardée à la fermeture et sur `ExitRequested` ; reprise seulement si le haut de la fenêtre tombe sur un écran (`reachable`, testé : écran débranché, fenêtre réduite à -32000), sinon coin bas droit de l'écran de `main` (`corner`, testé). Capability `mini.json` : `core:default` plus `core:window:allow-start-dragging` pour `data-tauri-drag-region`. Les commandes de l'app restent appelables depuis `mini` : les filtrer par fenêtre demanderait un manifeste d'app listant toutes les commandes, pour une page locale de confiance. Le zoom de l'interface (#337) ne s'applique qu'à `main`. Double-clic sur la pochette = retour à la grande fenêtre (le double-clic d'une zone de glissement tente d'agrandir, refusé faute de permission).
- **Raccourcis globaux** (0.5.61, #413, `integrations/hotkeys.rs`, bureau) : `tauri-plugin-global-shortcut` (2.4, crate `global-hotkey` 0.8 : `RegisterHotKey` sous Windows, X11 sous Linux) piloté côté Rust seulement, sans paquet JS ni capability. Plugin ajouté dans `setup` par `app.plugin(…)` après `AppState`, et non dans le constructeur : sans serveur X sa création échoue, et l'app ne doit pas en mourir (`global_shortcuts_status.available` vaut alors faux, le groupe des Réglages est masqué). Réglage `UiSettings::global_shortcuts` (`commands/settings/global_shortcuts.rs`, logique pure testée) : `enabled` (**désactivé par défaut**) et `bindings` (action → combinaison `Ctrl+Alt+Space`, modificateurs puis `KeyboardEvent.code`, le format de `global-hotkey`) ; Ctrl, Alt ou Super obligatoire, Maj seule refusée ; lecture tolérante (action inconnue, combinaison mal formée ou en double laissées de côté, sans perdre les autres réglages). Combinaisons proposées en Ctrl+Alt (inutilisé par les raccourcis de l'app) : Espace, ←, →, ↑, ↓, L (aimer), S (afficher la fenêtre). `apply` (au démarrage et par `store_and_apply`) retire tout puis enregistre chaque combinaison ; un échec (prise par une autre app, touche inconnue) est gardé et renvoyé par `global_shortcuts_status.failed`, affiché sous l'action. Actions : lecture/pause, suivant, précédent → `Cmd` comme SMTC ; volume → `Cmd::StepVolume(±5)` (cran depuis le niveau entendu, `Volume::step` testé) ; afficher la fenêtre → `tray::show_main` ; aimer → événement `global-shortcut` à l'UI, qui l'exécute par son registre (`runAction("play.like")`, #412), car l'état des favoris vit là. `globalShortcuts` est propre au bureau dans la sauvegarde des réglages. UI : Réglages › Application › Raccourcis globaux (`GlobalShortcutsList.svelte`, capture dans `lib/hotkeys.ts`, testée) ; un clic sur la combinaison attend la suivante, Échap annule, Retour arrière retire, doublon refusé. Une combinaison déjà enregistrée par l'app ne parvient plus à la page pendant la capture (le système la prend) : l'action se déclenche au lieu d'être saisie. Vérifié par `cargo test hotkeys` (combinaisons lisibles par `global-hotkey`) et dans l'aperçu (`?route=settings&tab=app&hotkeys=1|taken`) ; **pas encore vérifié** dans l'app réelle (touches pressées hors de la fenêtre, conflit avec une autre app), ni sous Linux (Wayland : seulement via XWayland, à voir).
- **Lancement au démarrage** (#13) : `tauri-plugin-autostart` piloté côté Rust (`autostart_enabled` / `set_autostart`), sans paquet JS ni capability. L'état est lu dans le registre (`HKCU\…\Run`, valeur `Seaglass`, et `StartupApproved\Run`), jamais copié en SQLite. Chemin = `current_exe()` : à tester sur un build installé. Limites connues : `auto-launch` tente `HKLM` en premier (app lancée en admin), valeur non entre guillemets, entrée non retirée à la désinstallation, fenêtre ouverte normalement.

## Notifications des nouvelles sorties (0.5.85, #435)

- **Choix** : code natif, sans `tauri-plugin-notification`. Sur le bureau, ce plugin (notify-rust) ne remonte pas le clic, or la notification doit ouvrir l'album ou le fil. Seulement deux features de plus pour la crate `windows` (`UI_Notifications`, `Data_Xml_Dom`) ; `zbus` sous Linux ; Kotlin dans `seaglass-mobile` sous Android.
- **Détection** (`commands/feed_alerts.rs`, logique pure testée) : après chaque lecture du fil par la tâche de fond (`feed::spawn_watch` : 20 s après le lancement, puis toutes les 6 h), si le réglage `releaseNotifications` est activé (désactivé par défaut, `UiSettings`, reporté par `apply_to_backend`). Sont retenus les albums **pas vus** (état local du fil), datés de moins de 3 jours et absents de l'ensemble `feed_notified` (réglage SQLite, par compte, 1 000 clés au plus, même forme que `feed_seen`). Sans ensemble pour ce compte (premier passage après l'activation, autre compte), il est créé avec les sorties du moment **sans notifier** : pas de rafale à l'activation. S'il ne peut pas être enregistré, on ne notifie pas (sinon la même sortie reviendrait 6 h plus tard). Les mixes du fil ne sont pas des sorties.
- **Contenu** : une sortie donne « Nouvelle sortie » avec « artiste · titre », et le clic ouvre l'album. Plusieurs donnent « N nouvelles sorties » avec les trois premiers artistes, et le clic ouvre le fil. Le clic passe par le mécanisme des liens partagés (`link::open` : `LinkTarget` gardé, événement `open-link`, `take_shared_link`), désormais écouté aussi sur le bureau ; nouvelle cible `LinkTarget::Feed`.
- **Windows** (`integrations/notify/toast.rs`) : toast WinRT `ToastGeneric`, texte échappé, `CreateToastNotifierWithId` avec l'identifiant de l'app (`dev.seaglass.app`). Windows n'accepte que l'AUMID d'un raccourci du menu Démarrer : l'installeur NSIS de Tauri le pose sur `Seaglass.lnk` (vérifié le 2026-11-18). Sans installation, le toast est refusé sans erreur, et `pnpm tauri dev` en profite si l'app est installée. Le clic arrive par `Activated` tant que le processus vit (zone de notification comprise) : la fenêtre est réaffichée (`tray::show_main`), puis la page s'ouvre. Touché plus tard depuis le centre de notifications, app fermée, le toast relance seulement l'app : pas d'activateur COM enregistré. Essai : `cargo test live_toast -- --ignored`.
- **Linux** (`integrations/notify/dbus.rs`) : `Notify` sur `org.freedesktop.Notifications` (comme `notify-send`), action `default`. Le signal `ActionInvoked` est attendu jusqu'à `NotificationClosed`, au plus 24 h ; l'abonnement est pris avant l'envoi.
- **Android** (`ReleaseNotifications.kt`, commande `notifyRelease` de `Bridge`, sans activité) : canal `releases` (« Nouvelles sorties », nom dans la langue de l'app), une seule notification à la fois (id 435), petite icône `notification_release` (disque en silhouette). Le clic ouvre `ShareActivity` avec `https://tidal.com/album/<id>` ou `seaglass://feed` (lien interne reconnu par `link::resolve`). Permission `POST_NOTIFICATIONS` déclarée et demandée à l'activation du réglage (commande `requestNotifications`, Android 13+). Refusée, l'envoi échoue et passe au journal. Limite : la vérification ne tourne que tant que le processus vit (lecture en cours, app ouverte). Il n'y a pas de WorkManager.

## Journaux et rapports de plantage

0.5.10, #192, `logs/` (bureau et Android). Tout reste sur l'appareil : pas de service de rapport (Sentry & co), l'utilisateur copie le texte dans une issue.

- **Journal** (`logs/file.rs`) : une seconde couche `tracing_subscriber::fmt` (sans ANSI, même filtre `RUST_LOG` / `seaglass_lib=info`) écrit dans `seaglass.log` du dossier `app_log_dir` de Tauri (`%LOCALAPPDATA%\<identifiant>\logs` sous Windows, `<dataDir>/logs` sous Android). Ouvert dans `setup`, juste après le Keystore : les lignes d'avant ne vont qu'à la sortie standard. Au lancement, l'ancien devient `seaglass.old.log` ; au-delà de 4 Mo aussi (Android garde le processus des jours). Écriture sans tampon, une ligne par appel (`panic = "abort"` en release ne laisse rien en mémoire) ; un garde par thread évite qu'un panic pendant l'écriture ne reprenne le verrou. **Paramètres des URLs masqués** (`redact` : `https://h/p?…`) : les URLs de flux sont signées. Les tokens ne sont de toute façon jamais journalisés. Un second lancement bloqué par l'instance unique quitte avant `setup` et ne fait pas tourner le journal de la première.
- **Panics Rust** (`logs/report.rs`) : hook installé au premier appel de `run`, qui écrit `crash.txt` (version, OS, date UTC, thread, message, emplacement, backtrace ; symboles absents en release, `strip = true`) puis appelle le hook précédent. Le message passe aussi dans le journal.
- **Android** (`CrashLog.kt`, commande `crashSetup` du pont JNI, appelée par `android::crash_setup` avec le dossier des journaux) : gestionnaire des exceptions non rattrapées qui écrit sa pile dans le même `crash.txt` avant celui d'Android ; et `ActivityManager.getHistoricalProcessExitReasons` (Android 11+), qui donne la dernière sortie `REASON_CRASH`, `REASON_CRASH_NATIVE` (panic Rust compris, `SIGABRT`) ou `REASON_ANR` pas encore vue (date de la plus récente gardée dans `exit-seen`). Trace jointe seulement pour un ANR (64 Ko au plus) : celle d'un plantage natif est un tombstone binaire. Au premier lancement de cette version, une ancienne sortie anormale encore dans l'historique est rapportée une fois.
- **Rapport** : au lancement, `crash.txt` et/ou la sortie Android deviennent `last-crash.txt`, avec les 300 dernières lignes de `seaglass.old.log` (le journal du lancement planté). `take_crash_notice` le signale une fois à l'UI, qui affiche un toast cliquable (15 s) copiant le rapport. Réglages › Application › Journaux : « Copier le journal » (500 dernières lignes de ce lancement, utile pour un bug sans plantage, surtout sous Android où le dossier est inaccessible), « Copier le dernier rapport de plantage », « Ouvrir le dossier » (bureau, `tauri-plugin-opener` depuis Rust). Copie par `navigator.clipboard` (refusée dans le volet d'aperçu du navigateur intégré, pas dans la WebView de l'app).
- **Bureau, limites** : un plantage natif de l'app (hors panic Rust) ou de WebView2 ne laisse pas de rapport, seulement la fin du journal (Tauri n'expose pas `ProcessFailed`). Un mpv qui s'arrête seul laisse son code de sortie dans le journal à la relance (`ProcessGuard::set`) ; sa sortie standard reste ignorée (`--no-terminal`, et un journal de mpv contiendrait les URLs signées).
- Aperçu : `?route=settings&tab=app&crash=1` (toast et rapport factice).
