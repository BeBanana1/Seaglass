# Intégrations au système (bureau)

Notes d'implémentation de Seaglass, lues à la demande (index dans [`CLAUDE.md`](../CLAUDE.md)). La session média d'Android est dans [`android.md`](android.md).

## SMTC, Discord, zone de notification, démarrage

- **SMTC** (`integrations/smtc.rs`) : `ISystemMediaTransportControlsInterop::GetForWindow(hwnd de la fenêtre main)` sur un thread dédié (MTA). L'acteur notifie `Observers` à chaque `player-state` émis ; le thread ne touche SMTC que si les métadonnées, le statut ou les boutons changent, et la timeline toutes les 5 s ou après un saut. Boutons → `Cmd::SetPaused(bool)`, `Next`, `Previous` (`try_send`, thread WinRT). Vérifié avec l'API `GlobalSystemMediaTransportControlsSessionManager` : session `seaglass.exe`, titre / artiste / album / vignette / timeline, et Play / Pause / Suivant / Précédent pilotent bien le lecteur.
- **Présence Discord** (0.4.92, #215, `integrations/discord/`, bureau seulement) : aucune crate, IPC local de Discord écrit à la main (`ipc.rs`) : named pipe `\\.\pipe\discord-ipc-0..9` (socket Unix `$XDG_RUNTIME_DIR/discord-ipc-<n>` ailleurs), trames `opcode u32 LE + longueur u32 LE + JSON`, poignée de main `{v: 1, client_id}` → `READY`, puis `SET_ACTIVITY` (`args.pid`, `activity` ou `null`), `PING` → `PONG`, `CLOSE` = connexion perdue ; lecture dans une tâche à part, arrêtée avec la connexion (le pipe ne se ferme qu'avec ses deux moitiés, et Discord efface alors la présence). Activité (`activity.rs`, logique pure testée) : type 2 « Écoute », `status_display_type` 1 (l'artiste dans la liste des membres), titre en `details`, artistes en `state`, pochette 320 par son URL `https://` (pas d'asset téléversé) et album en info-bulle, `timestamps` début / fin (barre de progression), bouton « Ouvrir dans TIDAL » (`tidal.com/browse/track/<id>`) ; textes coupés à 128 caractères, complétés jusqu'à 2. Rien en pause ni à l'arrêt, activité précédente gardée pendant un chargement ; renvoyée seulement si le titre ou le texte change, si elle apparaît ou disparaît, ou après un saut (début décalé de plus de 2 s) ; 4 s au moins entre deux envois (Discord : 5 par 20 s), le dernier état attend son tour. Observateur `Observers::discord` (`watch` de `NowPlaying`). **Réglage** `UiSettings::discord` (**désactivé par défaut**), copié dans un `watch` global par `apply_to_backend` ; actif : connexion, nouvel essai toutes les 15 s si Discord est fermé ; désactivé : connexion fermée. **Identifiant** : `DISCORD_CLIENT_ID` du `.env` (`build.rs` → `SEAGLASS_DISCORD_CLIENT_ID`, variable au lancement prioritaire), application Discord nommée « Seaglass » (ce nom s'affiche dans « Écoute … ») ; sans lui, `discord_available` vaut faux et Réglages › Application › Discord est masqué. Tests : `cargo test discord` (faux Discord sur `tokio::io::duplex`) ; **`cargo test live_discord -- --ignored --nocapture`** contre le vrai Discord (lancé sur le poste) : activité acceptée le 2026-11-06 (application `1568264624166535200`, réponse avec `type` 2, `status_display_type` 1, bouton et horodatages ; affichée 20 s). Pochette et suivi de la lecture dans l'app pas encore vus à l'œil. Aperçu : `?route=settings&tab=app&discord=1`.
- **Zone de notification** (#83, `integrations/tray.rs`, feature `tray-icon` de `tauri`) : icône toujours créée (clic gauche = afficher la fenêtre, ou la cacher si elle est visible et au premier plan, #226 : `click_hides`, testé ; cliquer sur l'icône prend le focus à la fenêtre juste avant, donc une perte du focus de moins de 500 ms compte comme au premier plan, `note_focus` sur `WindowEvent::Focused` ; menu : titre en cours grisé, Lecture/Pause, Suivant, Précédent, Afficher Seaglass, Quitter), commandes par `Cmd` comme SMTC, menu et info-bulle tenus à jour en observateur de l'acteur (`Observers::tray`, textes recalculés seulement si la vue ou la langue change ; libellés testés). Réglage `UiSettings::close_action` (`quit` par défaut, `tray`) dans Réglages › Application › Fenêtre, copié côté backend dans un atomique (`apply_to_backend`, au démarrage et par `set_ui_settings`) et lu sur `CloseRequested` de `main` : `prevent_close` + `hide`, **seulement si l'icône existe** (sinon l'app deviendrait inaccessible). Quitter = `app.exit(0)` (mpv arrêté, mise à jour reportée installée). Démarrage réduit : l'autostart passe `--minimized`, une entrée `Run` active est réécrite au lancement pour l'ajouter (`refresh_autostart`) ; la fenêtre `main` est `visible: false` dans la config et affichée dans `setup` sauf avec `--minimized` et une icône créée. Une seule instance (`tauri-plugin-single-instance`, validé dans #118, enregistré en premier) : un second lancement réaffiche la fenêtre existante puis se ferme, sauf s'il porte `--minimized` (`tray::show_on_second_launch`, testé). Sous Windows le plugin ne tire que `windows-sys` ; `zbus` et les crates `async-*` du `Cargo.lock` ne servent que sous Linux. Aperçu : `?route=settings&tab=app&tray=1`.
- **Lancement au démarrage** (#13) : `tauri-plugin-autostart` piloté côté Rust (`autostart_enabled` / `set_autostart`), sans paquet JS ni capability. L'état est lu dans le registre (`HKCU\…\Run`, valeur `Seaglass`, et `StartupApproved\Run`), jamais copié en SQLite. Chemin = `current_exe()` : à tester sur un build installé. Limites connues : `auto-launch` tente `HKLM` en premier (app lancée en admin), valeur non entre guillemets, entrée non retirée à la désinstallation, fenêtre ouverte normalement.
