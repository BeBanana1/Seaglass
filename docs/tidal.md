# API TIDAL

Notes d'implémentation de Seaglass, lues à la demande (index dans [`CLAUDE.md`](../CLAUDE.md)). Tout ce qui touche TIDAL vit dans `src-tauri/src/tidal/` ; vérifier un endpoint avant de s'y fier.

## Résultats du spike (2026-10-29, tidalapi 0.8.11, abonnement HI_RES, pays CH)

Observé avec `spike/play.py probe` puis décodage réel dans mpv 0.41.

- **Le type de connexion détermine la qualité, pas l'abonnement.**
  - Client « appareil » (device code, `link.tidal.com`) : manifeste `application/vnd.tidal.bts`, **AAC 320 kbps maximum**, même en demandant `LOSSLESS` ou `HI_RES_LOSSLESS`. Inutilisable pour l'app.
  - Client PKCE (identifiant Android embarqué dans tidalapi, redirection vers `https://tidal.com/android/login/auth?code=…`) : manifeste `application/dash+xml` pour toutes les qualités. **C'est le flux de connexion à implémenter en phase 1** (la webview Tauri peut intercepter la redirection, ce qui évite le copier-coller).
- **Formats reçus (client PKCE)** :

  | Demandé | Reçu | Codec | Format |
  |---|---|---|---|
  | `LOW` | LOW | HE-AAC `mp4a.40.5` | ~96 kbps |
  | `HIGH` | HIGH | AAC-LC `mp4a.40.2` | ~320 kbps |
  | `LOSSLESS` | LOSSLESS | FLAC dans fMP4 | 16/44,1 |
  | `HI_RES_LOSSLESS` | HI_RES_LOSSLESS | FLAC dans fMP4 | 24/44,1 et 24/48 vus |

  Un titre sans version hi-res renvoie LOSSLESS 16/44,1 quand on demande HI_RES. Un titre Dolby Atmos renvoie du FLAC stéréo. Pas encore vu de 24/96 ni de 24/192.
- **Pas de DRM** : aucun élément `ContentProtection`, aucun `cenc:default_KID`/`pssh` dans le MPD, aucune boîte `pssh`/`tenc`/`sinf`/`enca` dans le segment d'initialisation. Attention : le MPD déclare **toujours** `xmlns:cenc`, même en clair, donc ce n'est pas un marqueur de DRM.
- **Métadonnées** : `track.audioQuality` vaut `LOSSLESS` même pour un titre hi-res, la disponibilité hi-res se lit dans `mediaMetadata.tags` (`HIRES_LOSSLESS`, `DOLBY_ATMOS`). Le format réel (`bitDepth`, `sampleRate`) n'est connu qu'avec `playbackinfopostpaywall`.
- **Lecture** : le MPD utilise `SegmentTemplate` + `SegmentTimeline` avec des URLs absolues signées. mpv le lit via le démuxeur DASH de ffmpeg s'il est servi en HTTP. Le spike le sert depuis la mémoire sur `127.0.0.1` (rien sur disque). Le backend Rust devra faire de même (petit serveur local) ou valider une autre approche. mpv sort en `s32` pour du 24 bits, c'est normal.
- À surveiller : un avertissement ffmpeg `dash: Error when loading first fragment of playlist` vu une fois sur un titre 24/48, sans effet sur la lecture.

## Connexion et garde DRM

- **Identifiant client** : `TIDAL_CLIENT_ID` / `TIDAL_CLIENT_SECRET` (client PKCE) dans `.env`, injectés à la compilation par `build.rs`. Une variable d'environnement au lancement reste prioritaire.
- **Connexion** : fenêtre webview `login` (sans aucune capability) sur `login.tidal.com/authorize` ; `on_navigation` intercepte `https://tidal.com/android/login/auth?code=…` et bloque la navigation. Refresh token dans le Credential Manager (service `seaglass`, utilisateur `tidal-refresh-token`). L'access token (4 h) n'est jamais persisté, il est rafraîchi 60 s avant expiration ou sur 401, **une seule fois** pour toutes les requêtes en attente (revérifié sous le verrou en écriture, #148). Erreurs réseau sans leur URL (`From<reqwest::Error>` → `without_url`, #144) : celle du segment d'init est signée et finirait dans les journaux et les toasts.
- **Garde DRM** : avant chaque lecture, `tidal::manifest` rejette les MPD avec `ContentProtection` / `cenc:default_KID` / `cenc:pssh` / UUID Widevine, puis le segment d'initialisation (lu en mémoire) s'il contient `pssh`/`tenc`/`sinf`/`enca`.

## Catalogue (phase 3)

- **Endpoints** (vérifiés, test `cargo test live_catalog -- --ignored --nocapture`) : `search?types=TRACKS,ALBUMS,ARTISTS,PLAYLISTS`, `albums/{id}` + `/tracks`, `artists/{id}` + `/toptracks` + `/albums` (`filter=EPSANDSINGLES` pour les singles), `playlists/{uuid}` + `/tracks`, `users/{id}/favorites/{tracks,albums,artists}` (`order=DATE&orderDirection=DESC`, éléments `{created, item}`), `users/{id}/playlistsAndFavoritePlaylists` (éléments `{type, playlist}`), v2 `home/feed/static?deviceType=BROWSER&platform=WEB&locale=<fr_FR|en_US>` (langue de l'app, #7).
- **Ordre des titres d'une recherche** (#232, `tidal/rank.rs`, testé) : pour un mot courant (« yellow », « stay », « creep »), TIDAL intercale les titres d'artistes dont le nom contient le mot (Yellow Claw, Creep-P…), vu le 2026-11-06. `titles_first` (appelé par `search`) remonte, par tri stable, les titres au nom égal à la requête, puis ceux qui la contiennent ou y sont contenus (mots entiers, casse, ponctuation et apostrophes ignorées) ; une recherche d'artiste garde l'ordre de TIDAL. `topHit` de la réponse (`TRACKS` ou `ARTISTS`) n'est pas lu.
- **Pagination** : avancer selon `totalNumberOfItems`, pas selon le nombre d'éléments reçus (les titres indisponibles sont filtrés : 97 reçus pour `limit=100`). Pages de 100, sauf `playlistsAndFavoritePlaylists` qui refuse plus de 50.
- **Accueil v2** : lignes `{type, title, items: [{type, data}]}`. Seuls `ALBUM`, `ARTIST`, `PLAYLIST` et `MIX` (depuis 0.4.8) sont gardés ; `TRACK` (sans album) et `DEEP_LINK` sont ignorés. Les titres de lignes suivent `locale` (`fr_FR` / `en_US`, vérifié par `cargo test live_locale -- --ignored --nocapture`). Chaque ligne a un `moduleId` stable, indépendant de la langue (`BECAUSE_YOU_LISTENED_TO_ALBUM`, `YOUR_FAVORITE_ARTISTS`…) → `HomeRow::key` ; « Parce que vous avez écouté » porte son contexte dans un `header` séparé. **Pagination** (0.4.77, #207, `tidal/home.rs`, testé ; `cargo test live_home_pages -- --ignored --nocapture`) : `page.cursor` repassé en `cursor=` avec les mêmes paramètres, `null` sur la dernière page ; deux pages vues le 2026-11-05 (11 puis 7 lignes, dont un `TRACK_LIST` ignoré), `moduleId` tous différents, ~0,5 s par page, 5 pages lues au plus. Plusieurs lignes peuvent partager une clé (regroupées par `home_layout`), donc aucune déduplication. Commande `home` → `HomeFeed { sections, more }` (première page seule, affichée aussitôt), puis `home_rest` → tout l'accueil disposé, à partir de la première page gardée par le client (`HomeCache`, relue si le compte ou la langue ont changé) ; une page suivante en échec est journalisée et l'accueil garde les précédentes. `Home.svelte` garde l'album « À la une » déjà montré quand la suite arrive (`featuredId`).
- **Date d'ajout** : chaque titre de `playlists/{uuid}/tracks` porte `dateAdded` (`2024-04-12T22:51:56.872+0000`), les favoris `created` (date du like). Les deux deviennent `TrackEntry::added_at` (ms UTC, `tidal/date.rs`). `TrackEntry` est sérialisé à plat (`#[serde(flatten)]`) : côté UI, un `Track` avec `addedAt`. La date ne va ni dans le cache ni dans la file.
- **Images** : `resources.tidal.com/images/<id avec / à la place des ->/<n>x<n>.jpg`. Pochettes 160 (`AlbumRef::cover_small_url` : lignes de titres, barre de lecture, « À suivre », infos du titre), 320 (cartes) et 640 (`cover_large_url` : « En lecture », bandeau d'accueil, en-tête d'album) ; un `AlbumRef` enregistré avant 0.4.36 n'a que la 320, les deux autres en sont déduites à la relecture (`StoredAlbumRef`, #89) ; côté UI `coverSmall` / `coverLarge` (`lib/format.ts`), photos d'artiste et playlists (`squareImage`) en 320.
- **`MediaItem`** est sérialisé avec l'étiquette `kind` : aucun type qu'il contient ne doit avoir de champ `kind` (d'où `AlbumSummary::album_type`, test `media_item_tag_is_unique`).

## Fil d'actualité, mixes, radios, paroles

- **Fil d'actualité** (0.4.8, #14, `tidal/feed.rs`, vue `views/Feed.svelte`, route `feed`) : v2 `feed/activities?userId=…&deviceType=BROWSER&platform=WEB&locale=<langue>` → `{ activities: [{ followableActivity: { activityType, occurredAt, album | historyMix }, seen }], stats }`. Types vus : `NEW_ALBUM_RELEASE` (album complet) et `NEW_HISTORY_MIX` (`historyMix` : mix `HISTORY_MONTHLY_MIX` au format de `favorites/mixes`, lu par `RawMix`, ouvert par `pages/mix` comme les autres, 0.4.9). `FeedItem::item` est un `MediaItem` (album ou mix). **Pas de pagination** : `offset` ignoré, `limit` tronque, fenêtre d'environ 50 activités (vérifié le 2026-10-30). `seen` est lu (pastille « Nouveau »), jamais écrit. L'UI groupe par Aujourd'hui / Cette semaine / mois et réutilise `Card`. Aperçu : `?route=feed`.
- **Mixes et radios** (0.4.8, #11, `tidal/mix.rs`) : `MediaItem::Mix(MixSummary)` (id alphanumérique, titre, sous-titre, image 320, `mixType`). Un même mix arrive sous trois formes, toutes lues par `RawMix` (tests) : accueil v2 (`titleTextInfo.text`, `subtitleTextInfo.text`, `mixImages: [{size, url}]`, `type`), v2 `favorites/mixes` et `pages/mix` (`title`, `subTitle`, `images: {SMALL|MEDIUM|LARGE: {url}}`, `mixType`). URLs d'image signées par l'API (`images.tidal.com/…?token=`), gardées telles quelles ; cet hôte doit figurer dans `img-src` de la CSP (`tauri.conf.json`), sinon WebView2 bloque les images alors que `pnpm dev`, sans CSP, les affiche (#56, 0.4.16). Commandes `mix(id)` (en-tête de `pages/mix?mixId=` + titres de `mixes/{id}/items`, éléments `{item, type}` dont seuls les `track` sont gardés), `radio(seed: track|artist, id)` (`tracks/{id}/radio` : 96 titres vus, `artists/{id}/radio` : 100) et `library_mixes` (v2 `favorites/mixes`, curseur ; 14 mixes sur le compte de test). Les mixes ne vont pas dans le cache (contenu changeant), leurs titres oui. UI : vue `Mix.svelte` partagée par les routes `mix` et `radio` ; bouton Radio sur chaque ligne de titre (`TrackRow`) et dans l'en-tête d'un artiste (`PageHeader` `onRadio`) ; onglet « Mixes » de la bibliothèque. **Enregistrer un mix** (0.4.78, #204) : voir « Écritures dans la bibliothèque » ; pas encore pour les radios (l'id du mix d'une radio, `mixes.TRACK_MIX` de `tracks/{id}` ou `ARTIST_MIX` d'`artists/{id}`, n'est pas encore lu).
- **Paroles** (0.4.8, #5, `tidal/lyrics.rs`) : `GET v1/tracks/{id}/lyrics` (vérifié, test `cargo test live_lyrics -- --ignored --nocapture`) renvoie `{lyricsProvider, isRightToLeft, lyrics, subtitles}`, `subtitles` en LRC ; **404 = pas de paroles** (instrumental, classique), traduit en `None`. `Lyrics::text` = `Synced` (lignes en ms, triées, ligne vide = passage instrumental) ou `Plain` (repli si `subtitles` est vide ou illisible). Parsing LRC testé : horodatages multiples sur une ligne, `mm:ss[.x|.xx|.xxx]`, en-têtes `[ar:…]` ignorés. Commande `lyrics(trackId)`. UI : `components/Lyrics.svelte` dans un panneau de « En lecture », exclusif avec la file (`ui.nowPlayingPanel: "queue" | "lyrics" | null`). La ligne courante suit `estimatedPosition` (comme `Progress`) et reste centrée par défilement doux, suivi suspendu 4 s après un défilement manuel ; clic sur une ligne = seek. Marges de défilement en `cqh` (`container-type: size`) : des `vh` ou `%` débordaient du panneau. Crédit du fournisseur (Musixmatch) sous les paroles. **Paroles + file** (0.4.48, #119) : `ui.nowPlayingPanel` vaut aussi `both`. Fenêtre de 1400 px ou plus (`matchMedia`, jamais sur Android) : les boutons Paroles et File sont indépendants, les deux ouverts = deux colonnes (paroles 460 px, file 380 px ; pochette au-dessus des commandes sous 1800 px). Plus étroite : un seul panneau, `both` montre les paroles. Paroles sans la file à côté : bande « À suivre » (`.np-next`, 3 prochains titres en `TrackRow` compactes, lien « Toute la file » `.np-next-all`). Aperçu : `?nowplaying=1&lyrics=1&queue=1`.

## Écritures dans la bibliothèque (0.4.12, #4 ; favoris albums / artistes / playlists 0.4.25, #81 ; vérifiées le 2026-10-30)

Test `cargo test live_collection -- --ignored --nocapture` (`tidal/live_collection.rs`, **modifie le compte** : titre, album, artiste et playlist d'un autre utilisateur **absents** des favoris ajoutés puis retirés (un élément déjà présent est sauté, jamais retiré), playlist jetable créée, remplie, vidée puis supprimée, nettoyage même en cas d'échec). Client dans `tidal/collection.rs`, requêtes génériques `api::Call` (méthode, formulaire, `If-None-Match`) ; les erreurs v2 (`errors[].detail`) sont lues.

- **Mixes** (#204, vérifié le 2026-11-05) : `favorites/ids` n'a **pas** de clé `MIX` ; ensemble lu par GET v2 `favorites/mixes/ids?limit=50` → `{content: ["<id>", …], cursor}` (curseur, trié par id), en parallèle de `favorites/ids` (`LikedIds::mixes`), remplacé à chaque lecture complète de l'onglet Mixes (`library_mixes` émet aussi `likes`). Ajout : PUT v2 `favorites/mixes/add?mixIds=<id>&onArtifactNotFound=FAIL` (query, sans corps) ; retrait : PUT v2 `favorites/mixes/remove?mixIds=<id>`, idempotent. Le mix ajouté arrive **en fin** de `favorites/mixes`. `LikeTarget::Mix { id }` (id vérifié par `is_mix_id`) ; cœur dans l'en-tête d'un mix (`Mix.svelte`, pas d'une radio) et entrée du menu des cartes de mix.
- **Favoris en mémoire** (`tidal/likes.rs`, quatre ensembles depuis #81, cinq avec les mixes) : GET v1 `users/{id}/favorites/ids` → `{TRACK: ["<id>", …], ALBUM, ARTIST, PLAYLIST, VIDEO, …}` (identifiants en chaînes, toute la bibliothèque en une requête). Il compte aussi les titres indisponibles (450 contre 424 dans `favorites/tracks`) : c'est un sur-ensemble ; albums et artistes y correspondent exactement à leurs listes (115 / 39). `PLAYLIST` contient les playlists suivies **et parfois une des vôtres** (1 sur 2 sur le compte de test). Ensembles chargés au premier `likes`, tenus à jour par `set_liked`, remplacés catégorie par catégorie à chaque lecture complète de la bibliothèque (Titres, Albums, Artistes ; Playlists : seulement celles des autres), vidés à la déconnexion. Un seul événement `likes` (`LikedIds` : `tracks`, `albums`, `artists`, `playlists`, listes triées) après chaque écriture et chaque lecture complète ; l'UI (`lib/stores/likes.svelte.ts`) ne fait que l'afficher, l'état change à la confirmation du backend (pas d'affichage optimiste).
- **Ajout aux favoris** : POST v1 `users/{id}/favorites/{tracks|albums|artists|playlists}` (formulaire `trackIds` / `albumIds` / `artistIds` / `uuids`, `onArtifactNotFound=FAIL`). Titres, albums et artistes arrivent aussitôt en tête de leur liste (tri par date) ; une playlist suivie arrive en fin de `playlistsAndFavoritePlaylists`. Retrait : DELETE `users/{id}/favorites/<type>/{id ou uuid}`, **idempotent** (retirer un favori absent répond 2xx).
- **Créer une playlist** : PUT v2 `my-collection/playlists/folders/create-playlist?name=…&description=…&folderId=root` → `{data: {uuid}}` ; visible aussitôt dans `playlistsAndFavoritePlaylists` (`mine = true`). Supprimer : PUT v2 `my-collection/playlists/folders/remove?trns=trn:playlist:<uuid>`, puis `playlists/{uuid}` répond 404.
- **Ajouter à une playlist** : POST v1 `playlists/{uuid}/items` (formulaire `trackIds` séparés par des virgules, `onArtifactNotFound=FAIL`, `onDupes=SKIP`), sans `toIndex` = à la fin, dans l'ordre donné. Réponse `{lastUpdated, addedItemIds: [...]}` : un doublon est ignoré sans erreur et absent de `addedItemIds` (« Déjà dans … » côté UI). Envoi par paquets de 100 (`limit` de l'API), ETag relu avant chacun.
- **Retirer** : DELETE v1 `playlists/{uuid}/items/{index}` (index 0 = premier titre). Avant, `playlists/{uuid}/items?offset=<index>&limit=1` vérifie que c'est bien le titre attendu (playlist modifiée ailleurs depuis l'affichage → `TidalError::Conflict`, rien n'est retiré). L'ETag est lu avant cette vérification : une modification entre les deux donne un 412.
- **ETag obligatoire** : chaque modification de playlist exige l'`ETag` de GET `playlists/{uuid}` en `If-None-Match`. Un ETag périmé (playlist modifiée entre-temps) → **412** « You must send the correct Etag value… », traduit en `TidalError::Conflict`.
- **Cohérence à terme** (#201, vu le 2026-11-05) : juste après une écriture, `playlists/{uuid}` peut renvoyer l'ancien ETag, et une écriture envoyée avec lui à une réplique en retard y est **acceptée et appliquée sur l'ancien état** (un déplacement appliqué avant l'ajout qui le précédait). L'ETag vaut `lastUpdated` en ms : `tidal/versions.rs` (testé) retient la plus récente version vue après chaque écriture de l'app (`settle` relit l'ETag jusqu'à le voir changer), et `fresh_etag` relit un ETag plus ancien au lieu de l'envoyer ; un 412 est relancé deux fois à 400 ms (`retry_stale!`, macro : une fermeture asynchrone cassait l'inférence de `Send` des commandes). Relire les titres juste après une écriture peut aussi renvoyer l'ancien ordre : l'UI applique un déplacement confirmé sans relire.
- **Déplacer** (#201) : POST v1 `playlists/{uuid}/items/{index}` avec `toIndex` **en formulaire** (en query : 200 mais ignoré), ETag requis, corps vide. `toIndex` = position finale (`[a,b,c,d]`, 0 → 2 donne `[b,c,a,d]`), au-delà de la fin = à la fin ; plusieurs index à la fois possibles (`items/0,1`). Titre attendu vérifié à `index` comme pour le retrait (`checked_etag`).
- **Renommer / description** (#201) : POST v1 `playlists/{uuid}` (formulaire `title`, `description`, chacun facultatif), visible aussitôt ; accepté même sans ETag (envoyé quand même). Dossiers : v2 `my-collection/playlists/folders?folderId=root` (`itemType`, `parent`), pas traités (aucun sur le compte de test).
- **Commandes** (`commands/collection.rs`) : `likes` → `LikedIds`, `set_liked(target, liked)` (`LikeTarget` étiqueté par `kind` : `track` / `album` / `artist` avec `id`, `playlist` avec `uuid` vérifié, `mix` avec `id` vérifié), `own_playlists` (playlists `mine` seulement), `add_to_playlist(uuid, trackIds)` → nombre ajouté, `create_playlist(title, trackIds)` → uuid (titre non vide, 200 caractères au plus), `remove_from_playlist(uuid, index, trackId)`, `move_in_playlist(uuid, from, to, trackId)`, `edit_playlist(uuid, title, description)` (description 2 000 caractères au plus), `delete_playlist(uuid)` (#201) ; chaque écriture efface la copie gardée (#152, #181).
- **Gérer ses playlists** (0.4.78, #201) : sur vos playlists seulement, bouton « Modifier » (`.edit-playlist`, crayon) dans l'en-tête → `components/PlaylistEditor.svelte` (`.playlist-editor` : titre, description, « Supprimer la playlist… » puis confirmation ; après suppression : épingle retirée, onglet Playlists rechargé, retour). Réordonner quand la liste n'est ni triée ni filtrée (`TrackList` `onMove`) : glisser-déposer (`.track-item`, repères `.drop-before` / `.drop-after`, pas sur Android : il gênerait l'appui long), Alt+↑ / Alt+↓ (le focus suit), « Monter / Descendre » du menu (le seul moyen sur Android) ; un déplacement à la fois, ordre local mis à jour à la confirmation, relecture sur refus. Aperçu : `?route=playlist&mine=1`.
- **UI** : `LikeButton` (cœur) sur chaque `TrackRow` (un cœur plein reste visible hors survol), dans la barre de lecture et dans « En lecture » (avec « Ajouter à une playlist ») ; menu contextuel : « Ajouter aux titres likés » / « Retirer… », « Ajouter à une playlist… », « Retirer de cette playlist » sur vos playlists (position d'origine, même triée ou filtrée). `PlaylistPicker.svelte` (ouvert par `openPlaylistPicker`, `lib/stores/playlistPicker.svelte.ts`) : vos playlists rechargées à chaque ouverture, filtre, « Nouvelle playlist… ». Bouton « Ajouter à une playlist » dans l'en-tête Album / Playlist (tous les titres). Après une modification, `notePlaylistChange(uuid)` recharge la page de cette playlist si elle est ouverte. Backend factice : `?mine=1` rend la playlist de démonstration modifiable. Classes surchargées par les thèmes : `.like-button`, `.playlist-picker`, `.picker-item`, `.picker-new-form`, `.now-actions`.
- **Albums, artistes, playlists** (#81) : `FavoriteButton.svelte` dans l'en-tête (`PageHeader` `favorite`) : cœur pour un album et une playlist **des autres** (aucun bouton sur les vôtres), « Suivre » / « Suivi » en texte pour un artiste ; la barre d'actions s'affiche aussi sans titres. Menu contextuel des cartes (`lib/cardMenu.ts`, clic droit, touche Menu, Maj+F10 ; carte en évidence par `.menu-open`) : Ouvrir, Ajouter à la bibliothèque / Retirer (Suivre / Ne plus suivre), Aller à l'artiste (album) ou Radio de l'artiste, Copier le lien (`tidal.com/browse/<type>/<id>`) ; un mix n'a que Ouvrir et le lien. Après un changement confirmé, l'onglet de bibliothèque concerné est rechargé s'il était déjà chargé (`toggleFavorite`). Backend factice : les listes de la bibliothèque suivent les ajouts et retraits. Classes : `.favorite-button` (`.follow`, `.liked`), déjà couvertes par les règles `.info .actions button` des thèmes.

## Plus tard (0.4.80, #196, vérifié le 2026-11-05)

- **API officielle** : la liste « Save for later » de TIDAL n'existe que dans l'API JSON:API `https://openapi.tidal.com/v2/` (`api::OPEN_API`), qui accepte le token du client PKCE (`countryCode` ajouté comme partout). `Call::json` envoie un corps `application/vnd.api+json` (refusé sous un autre type). Test `cargo test live_later -- --ignored --nocapture` (**modifie le compte** : un titre et un album absents de la liste ajoutés, relus, retirés).
- **Endpoints** (`tidal/later.rs`, logique pure testée) : GET `userCollectionSaveForLaters/me/relationships/items` → `{data: [{id, type, meta: {addedAt}}], links: {next, meta: {nextCursor}}}`, plus récent en tête, 20 par page (`page[cursor]`, 50 pages lues au plus) ; `type` = `tracks` / `albums` / `artists` / `playlists` / `videos` (ignorées). POST (ajout) et DELETE (retrait) sur le même chemin, corps `{data: [{id, type}]}` (20 au plus) : doublon dans `meta.skipped` (`ALREADY_PRESENT`) sans erreur, retrait idempotent. `include=items` renverrait les objets au format JSON:API, non utilisé : titres relus par `tracks/{id}` (cache d'abord), albums par v1 `albums?ids=` (par 50), artistes et playlists une requête chacun, 6 en vol ; un élément introuvable (4xx sauf 401) ou illisible est omis. ~330 ms pour 3 éléments.
- **État** : identifiants dans un second `Likes` (`TidalClient::later`, mixes toujours vides), chargés par `later_ids` à la connexion, remplacés à chaque lecture complète, vidés à la déconnexion ; événement `later` (`LikedIds`) après chaque écriture et lecture. Commandes `later_ids`, `save_for_later` → `LibraryList<LaterItem>` (`kind` : `track` avec `addedAt`, `album`, `artist`, `playlist`), `set_saved_for_later(target, saved)` (`LikeTarget`, mix refusé). Pas de copie sur disque (#181).
- **UI** : `lib/stores/later.svelte.ts` ; onglet « Plus tard » de la bibliothèque (aussi sur Android) : Lecture / Aléatoire et titres, puis « Albums, artistes et playlists » en cartes ; source de lecture `{kind: "later"}` (« Joué depuis »). ## Infos du titre (0.4.14, #3, vérifiées le 2026-10-30)

- **Choix confirmé par l'utilisateur dans l'issue** : un panneau à la demande, pas de format sur chaque ligne des listes (une requête `playbackinfopostpaywall` par titre serait lente et appellerait l'API de lecture sans lire).
- **Données** (`tidal/info.rs`, test `cargo test live_track_info -- --ignored --nocapture`) : `tracks/{id}` porte aussi `bpm`, `key` (formes mêlées : `B`, `FSharp`, `Bb`), `keyScale` (`MAJOR` / `MINOR`), `copyright`, `trackNumber`, `volumeNumber` ; `playbackinfopostpaywall` porte `trackReplayGain`, `trackPeakAmplitude`, `albumReplayGain`, `albumPeakAmplitude`. Le **débit** vient de l'attribut `bandwidth` (bit/s) de la `Representation` du MPD : ~893–1 026 kbps en FLAC 16/44,1, ~5 071 kbps en 24/192, ~329 kbps en AAC, ~97 kbps en HE-AAC ; absent des manifestes BTS.
- **`TidalClient::playback`** : requête + décodage du manifeste (garde DRM du MPD comprise), sans lire le segment d'initialisation ; `stream` y ajoute ce contrôle avant toute lecture. `StreamFormat::bitrate` (kbps) part aussi dans `player-state`.
- **Commande** `track_info(trackId)` → `TrackInfo` : format servi en qualité maximale (ou `streamError`), tags, ReplayGain (affiché ; appliqué seulement par la normalisation, #82), métadonnées, et l'édition hi-res éventuelle avec son format. `HiresEdition::played` est calculé par la commande (réglage `hires_upgrade` et `player::is_better`), l'UI ne déduit rien.
- **UI** : `components/TrackInfo.svelte` (ouvert par `openTrackInfo`, `lib/stores/trackInfo.svelte.ts`), entrée « Infos du titre » du menu contextuel et bouton ⓘ dans « En lecture ». Tonalité en notation française (`musicalKey`, `lib/format.ts`), forme inconnue rendue telle quelle. Chaîne audio : « Hi-Res · 5 071 kbps » sous la source (info-bulle seulement dans la barre resserrée de Studio) ; un flux AAC y est désormais dit « Avec perte » au lieu de « Lossless ». Aperçu : `?trackinfo=1` (avec `?hiresedition=` sur un titre non hi-res). Classes surchargées par les thèmes : `.track-info`, `.info-section`, `.info-tag` ; surchargeables : `.info-credits`, `.credit-artist` (#84).
- **Crédits** (0.4.25, #84, `tidal/credits.rs`, test `cargo test live_track_credits -- --ignored --nocapture`, vérifié le 2026-10-31) : GET v1 `tracks/{id}/credits?includeContributors=true` → `[{type, contributors: [{name, id?}]}]`. `type` est un texte libre anglais aux formes mêlées (`Lyricist` / `Lyrics`, `Vocal` / `Vocals`, `Background Vocal` / `Backing Vocals`, `OtherInstrument`…). `id` est un identifiant d'artiste ; **sans `includeContributors`, ingénieurs et producteurs n'en ont souvent pas** (avec, tous ceux de *Bohemian Rhapsody* ouvrent une page d'artiste). Titre sans crédits ou inexistant : `[]`, pas de 404. Pas de pagination. `TrackInfo::credits` (`CreditGroup { role, contributors: [{name, artistId}] }`), demandé en parallèle des autres requêtes de `track_info` ; une erreur est journalisée et donne une liste vide. Côté Rust : noms nettoyés, doublons et groupes vides retirés, rôles identiques (casse ignorée) fusionnés, groupes rangés (écriture, interprètes et instruments, production, technique, édition ; ordre de l'API dans chaque catégorie). UI : section « Crédits » en fin de `TrackInfo.svelte` (masquée si vide), rôles traduits par `creditRole` (`lib/format.ts`, dictionnaire `t.info.roles` par clé normalisée : minuscules sans espaces ni ponctuation), rôle inconnu affiché tel quel ; contributeur lié = lien `.credit-artist` vers la page d'artiste (le panneau se ferme). Aperçu : `?trackinfo=1` (crédits factices, dont un rôle inconnu). **Album entier** (0.4.75, #206, `album_credits`, test `cargo test live_album_credits -- --ignored --nocapture`, vérifié le 2026-11-05) : GET v1 `albums/{id}/items/credits?includeContributors=true`, **paginé** (`totalNumberOfItems`, `limit` respecté, lu par `get_all`), éléments `{type, item, credits}` (`item` = titre complet, `credits` de la forme ci-dessus ; types autres que `track` ignorés). Chaque titre passe par le même nettoyage, puis tout est réuni par rôle et par personne (`AlbumCreditGroup { role, contributors: [{name, artistId, tracks}] }`) ; `tracks` = identifiants des titres, **vide si la personne est sur tous** ; des identifiants plutôt que des numéros, l'UI les place dans la liste affichée (titres indisponibles). UI : `components/AlbumCredits.svelte` sous la liste des titres de `Album.svelte`, repliée (bouton `.album-credits-toggle`), demandée au premier clic ; « Batterie : X (titres 1–3, 5) » (`.credit-tracks`). Aperçu : `?route=album`, puis « Crédits de l'album ».

## Performances du backend (#90)

- **Pagination parallèle** (`tidal/paging.rs`, `get_all`) : la première page seule (elle donne `totalNumberOfItems`), puis les pages jusqu'au plafond en une vague de requêtes, 4 au plus en vol, remises dans l'ordre des offsets (`try_join_bounded`, maison sur `poll_fn` : pas de crate `futures`). Si des titres indisponibles laissent la liste sous le plafond, une vague de plus pour le reste. Sans total : repli séquentiel, arrêt à la première page incomplète. Construire les futures dans une boucle, pas dans un `map(|o| self.page(…))` : la fermeture fait échouer l'inférence de `Send` des commandes Tauri (« FnOnce is not general enough »). Mesuré avec `live_catalog` (2026-10-30, 5 pages chacun) : playlist de 484 titres 1,2–2,1 s → 0,6–0,85 s, 424 titres likés 0,9–1,5 s → 0,6–0,75 s (un pic à 1,4 s) ; l'ordre des favoris (date du like décroissante) est vérifié par le test.
- **Cache borné** (`tidal/cache.rs`) : 20 000 titres, éviction des moins récemment utilisés (horloge mise à jour à la lecture comme à l'écriture), par lots jusqu'à 95 % de la limite pour ne pas trier à chaque insertion. Les titres de la file (`Queue::referenced_ids`) sont épinglés par l'acteur (`pin_queue_tracks`, à chaque `mark_queue_dirty` et à la restauration) et jamais évincés, même au-delà de la limite : `queue_view` et la sauvegarde les relisent.
- **Persistance incrémentale** (`store/mod.rs`, tests dans `store/tests.rs`) : le `Store` tient l'ensemble des ids de la table `tracks` (lu à l'ouverture, mis à jour après le commit seulement, donc juste même si une sauvegarde échoue). `save_player(queue, position, lookup)` n'appelle `lookup` (le cache) que pour les titres référencés absents de la table, et supprime dans la même transaction les lignes qui ne sont plus référencées : les bases des versions précédentes sont purgées à la première sauvegarde. Un titre absent du cache n'est pas compté comme écrit et sera redemandé. L'acteur ne copie plus que la file.
- **Réglages en mémoire** : les valeurs `kv` lues par `get_setting` restent en mémoire sous un verrou distinct de la connexion (absence comprise), modifiées seulement sous le verrou de la connexion pour suivre l'ordre des écritures : `ui_settings`, `playback_settings` et `track_info` n'attendent plus une sauvegarde de la file. Une valeur écrite directement en base n'est donc vue qu'au redémarrage.
- **Plafond de la bibliothèque** (#91) : `LIBRARY_MAX` = 10 000 (2 000 avant), pour les titres, albums, artistes et playlists ; `const _: () = assert!(LIBRARY_MAX <= MAX_CONTEXT_LEN)` dans `commands/player.rs` garantit que lire ou mélanger toute la liste reste accepté. `get_list` (`paging.rs`) renvoie un `LibraryList { items, truncated, total }` : `truncated` vient de la pagination (pages restantes au plafond, ou plus de `max` reçus), **pas** de `total > items.len()` (le total compte les indisponibles : 450 annoncés pour 424 titres likés reçus sur le compte de test, vérifié le 2026-10-31). Les commandes `library_tracks` / `_albums` / `_artists` / `_playlists` renvoient ce type (`library_mixes` reste une liste). `likes.replace` seulement si la liste n'est pas coupée. UI : badge « 10000+ » sur l'onglet et bandeau `.library-truncated` « Les 10 000 titres likés les plus récents sur N sont affichés » (sans « sur N » si le total est inconnu). Aperçu : `?route=library&tab=tracks&truncated=1` (total 12 345) ou `truncated=nototal`. `fixtures.json` garde de simples tableaux (le backend factice les enveloppe).
- **Pages de playlist gardées** (0.4.59, #152, `tidal/playlist.rs`, logique pure testée) : l'ETag de GET `playlists/{uuid}` vaut `lastUpdated` en ms (`"1793747577268"`), stable sans modification, changé par chaque ajout et retrait (vérifié le 2026-11-03, aussi sur la playlist d'un autre utilisateur : `cargo test live_playlist_etag -- --ignored --nocapture`, crée puis supprime une playlist jetable). Cache mémoire des 20 dernières pages (20 000 titres au plus, la plus récente toujours gardée), avec l'ETag en `PlaylistPage::revision`. Commandes : `cached_playlist(uuid)` (copie gardée ou `null`, sans réseau, ses titres remis dans le cache des métadonnées) et `playlist(uuid, revision)` → `null` si l'ETag vaut `revision`, sinon la page (titres gardés si l'ETag est celui de la copie, sinon relus ; sans copie ni révision, en-tête et titres en parallèle comme avant). Ajout, retrait et suppression dans l'app effacent la copie ; la déconnexion vide tout (`mine` dépend du compte). `Playlist.svelte` affiche la copie aussitôt puis la remplace seulement si elle a changé ; « Chargement… » n'apparaît qu'après 300 ms ; une erreur avec une copie affichée part en toast. Mesuré sur 486 titres : lecture complète 690 ms, revalidation 210 ms (derrière la page déjà affichée). Une playlist modifiée sur un autre appareil s'affiche un instant dans son ancien état. Gardées aussi d'un lancement à l'autre depuis 0.4.72 (voir « Copies des listes »). Aperçu : `?route=playlist&slow=1500`.
- **Copies des listes** (0.4.72, #181, `store/snapshots.rs`, `commands/snapshots.rs`, tests) : table `snapshots` (`key`, `used_at` = horloge logique, `size` en titres, `json`) : pages de playlist (`playlist:<uuid>`, 20 au plus et 20 000 titres, les moins récemment lues ou écrites élaguées, la plus récente toujours gardée) et onglets Titres likés, Albums, Artistes, Playlists de la bibliothèque (`library:<onglet>` ; pas les mixes : images signées qui expirent). Écrites après chaque lecture complète (page avec ETag seulement) en `spawn_blocking` sans attendre ; copie d'une playlist effacée par l'ajout et le retrait dans l'app ; tout effacé à la connexion et à la déconnexion (attendu). Copie illisible (format d'une autre version) effacée. `cached_playlist` (asynchrone, plus sur le thread principal) : mémoire, sinon disque, copie remise en mémoire (`restore_playlist`) pour la revalidation par ETag. `cached_library(tab)` : copie de l'onglet, titres remis dans le cache des métadonnées ; `loadLibrary` l'affiche au premier chargement du lancement puis relit toujours la liste en entier (pas de révision), une erreur avec une copie affichée part en toast ; « Chargement… » de la bibliothèque après 300 ms. **Rendu par morceaux** (`TrackList`) : 40 lignes aussitôt, puis 80 par tâche (`setTimeout`), contexte de lecture complet. Mesuré dans l'app de dev (2026-11-05, WebView2 par CDP, port de débogage `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333`) : playlist de 486 titres en mémoire, première ligne 120 ms → 25 ms ; première ouverture après un redémarrage 715 ms avec « Chargement… » → 46 ms ; titres likés (427) après redémarrage 758 ms → 29 ms. Pas encore mesuré sur le S21.
- **Compression** : l'API TIDAL **ne compresse jamais** ses réponses (mesuré le 2026-11-03, #148 : `gzip`, `br`, `zstd`, HTTP/1.1 ou 2, en-têtes de l'app ; 118 836 o pour 100 titres likés, 146 106 o pour l'accueil, à l'identique). Inutile d'activer la décompression de `reqwest`.
- **Résolution d'un titre** : sans édition hi-res possible (Android, réglage « Non »), `tracks/{id}` et le flux partent en parallèle (#148).
- Non traité : la mise à jour téléchargée reste en mémoire jusqu'à la fermeture quand on choisit « Plus tard » (quelques dizaines de Mo, acceptable).
