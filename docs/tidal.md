# TIDAL API

Seaglass implementation notes, read on demand (index in [`CLAUDE.md`](../CLAUDE.md)). Everything TIDAL-related lives in `src-tauri/src/tidal/`; check an endpoint before relying on it.

## Spike results (2026-10-29, tidalapi 0.8.11, HI_RES subscription, country CH)

Observed with `spike/play.py probe` then real decoding in mpv 0.41.

- **The sign-in type determines the quality, not the subscription.**
  - "Device" client (device code, `link.tidal.com`): manifest `application/vnd.tidal.bts`, **AAC 320 kbps maximum**, even when requesting `LOSSLESS` or `HI_RES_LOSSLESS`. Unusable for the app.
  - PKCE client (Android identifier embedded in tidalapi, redirect to `https://tidal.com/android/login/auth?code=…`): manifest `application/dash+xml` for every quality. **This is the sign-in flow to implement in phase 1** (the Tauri webview can intercept the redirect, which avoids copy and paste).
- **Formats received (PKCE client)**:

  | Requested | Received | Codec | Format |
  |---|---|---|---|
  | `LOW` | LOW | HE-AAC `mp4a.40.5` | ~96 kbps |
  | `HIGH` | HIGH | AAC-LC `mp4a.40.2` | ~320 kbps |
  | `LOSSLESS` | LOSSLESS | FLAC in fMP4 | 16/44.1 |
  | `HI_RES_LOSSLESS` | HI_RES_LOSSLESS | FLAC in fMP4 | 24/44.1 and 24/48 seen |

  A track without a hi-res version returns LOSSLESS 16/44.1 when HI_RES is requested. A Dolby Atmos track returns stereo FLAC. No 24/96 or 24/192 seen yet.
- **No DRM**: no `ContentProtection` element, no `cenc:default_KID`/`pssh` in the MPD, no `pssh`/`tenc`/`sinf`/`enca` box in the init segment. Beware: the MPD **always** declares `xmlns:cenc`, even in the clear, so it is not a DRM marker.
- **AI-generated music** (#369, verified on 2026-11-12): `ai` field (boolean, undocumented) on v1 tracks and albums, absent from artists. The Velvet Sundown: tracks and album `ai: true`; search "ai music": 44/50 true (the other 6 are human tracks named "AI Music"); "Taylor Swift", "jazz", "lofi", "love", "suno": 0/250. Read as `Option<bool>` (`null` or absent = false) in `Track::ai` / `AlbumSummary::ai`. It is the service's tagging: it may miss tracks.
- **Dolby Atmos** (#367, verified on 2026-11-12, refused): `playbackinfopostpaywall` with `audioquality=DOLBY_ATMOS` answers 404 to the PKCE client; `immersiveaudio=true`, `audiomode=DOLBY_ATMOS` or `/v4` return stereo FLAC (`audioMode: STEREO`). The Atmos mix is only served to client identifiers of certified devices (E-AC-3 JOC / AC-4, usually under Widevine): outside principle 1, and mpv cannot render it (HDMI passthrough only).
- **Official `trackManifests`** (`openapi.tidal.com/v2`, verified on 2026-11-22, not usable): accepts the PKCE client's token and answers a **full** track (`trackPresentation: FULL`, hi-res FLAC), but **always under DRM**: Widevine for `MPEG_DASH` (`drmData` + `ContentProtection` in the MPD), FairPlay for `HLS`, whatever the formats asked (`FLAC_HIRES`, `FLAC` alone, even `AACLC` alone); `EAC3_JOC` (Atmos) answers 403. Outside principle 1: playback stays on `playbackinfopostpaywall` (v1). Probed with a throwaway ignored test (`Call::get(OPEN_API, "trackManifests/<id>", …)` with the required `manifestType`, `uriScheme` (`DATA` | `HTTPS`), `usage=PLAYBACK`, `adaptive=false` and one `formats` pair per format), not kept to avoid a version bump. The schema also has `previewReason` (`FULL_REQUIRES_HIGHER_ACCESS_TIER`…), the 30 s previews of third-party clients.
- **Metadata**: `track.audioQuality` is `LOSSLESS` even for a hi-res track, hi-res availability is read in `mediaMetadata.tags` (`HIRES_LOSSLESS`, `DOLBY_ATMOS`). The real format (`bitDepth`, `sampleRate`) is only known with `playbackinfopostpaywall`.
- **Playback**: the MPD uses `SegmentTemplate` + `SegmentTimeline` with signed absolute URLs. mpv plays it through ffmpeg's DASH demuxer if it is served over HTTP. The spike serves it from memory on `127.0.0.1` (nothing on disk). The Rust backend will have to do the same (small local server) or validate another approach. mpv outputs `s32` for 24-bit, that is expected.
- To watch: an ffmpeg warning `dash: Error when loading first fragment of playlist` seen once on a 24/48 track, with no effect on playback.

## Sign-in and DRM guard

- **Client identifier**: `TIDAL_CLIENT_ID` / `TIDAL_CLIENT_SECRET` (PKCE client) in `.env`, injected at build time by `build.rs`. An environment variable at launch still takes priority.
- **Sign-in**: `login` webview window (without any capability) on `login.tidal.com/authorize`; `on_navigation` intercepts `https://tidal.com/android/login/auth?code=…` and blocks the navigation. **Linux** (#17): sign-in in the system browser (`login_in_browser`, see `docs/linux.md`). **Private browsing** (0.4.101, #258): `incognito(true)`, TIDAL's cookies do not outlive the window (switching accounts possible, nothing in the WebView2 profile); signing out also clears the `main` window's browsing data (`clear_all_browsing_data`, leftovers from earlier sign-ins; the UI uses neither cookies nor web storage). Android: `SeaglassPlugin.login` empties `CookieManager` and the web storage of the TIDAL origins before and after the page. Refresh token in the Credential Manager (service `seaglass`, user `tidal-refresh-token`), the Secret Service on Linux. The access token (4 h) is never persisted, it is refreshed 60 s before expiry or on 401, **only once** for all pending requests (rechecked under the write lock, #148). **Refusals and outages** (0.4.109, #252, #259): only 400 / 401 / 403 from `oauth2/token` are a refusal (`TidalError::Auth`) that erases the refresh token; 429 and 5xx stay `Api` (before, they erased the session). At launch, a transient error (network not ready yet when Windows starts) leaves the token in place: the sign-in screen says so and `auth_status` is retried (5 s, doubled up to 60 s). A refusal midway clears the state, erases the token and emits `session-lost` (the UI goes back to sign-in) instead of staying "signed in" with a dead token. Refreshing does **not** return a new refresh token and the old one stays valid (verified on 2026-11-10, `cargo test live_refresh_rotation -- --ignored --nocapture`); if it returned one, it would be saved (`keep_rotated`). Network errors without their URL (`From<reqwest::Error>` → `without_url`, #144): the init segment's URL is signed and would end up in logs and toasts.
- **DRM guard**: before each playback, `tidal::manifest` rejects MPDs with `ContentProtection` / `cenc:default_KID` / `cenc:pssh` / Widevine UUID, then the init segment (read in memory) if it contains `pssh`/`tenc`/`sinf`/`enca`.

## Catalog (phase 3)

- **Endpoints** (verified, test `cargo test live_catalog -- --ignored --nocapture`): `search?types=TRACKS,ALBUMS,ARTISTS,PLAYLISTS`, `albums/{id}` + `/tracks`, `artists/{id}` + `/toptracks` + `/albums` (`filter=EPSANDSINGLES` for singles), `playlists/{uuid}` + `/tracks`, `users/{id}/favorites/{tracks,albums,artists}` (`order=DATE&orderDirection=DESC`, items `{created, item}`), `users/{id}/playlistsAndFavoritePlaylists` (items `{type, playlist}`), v2 `home/feed/static?deviceType=BROWSER&platform=WEB&locale=<fr_FR|en_US>` (the app's language, #7).
- **Order of search tracks** (#232, `tidal/rank.rs`, tested): for a common word ("yellow", "stay", "creep"), TIDAL interleaves tracks by artists whose name contains the word (Yellow Claw, Creep-P…), seen on 2026-11-06. `titles_first` (called by `search`) moves up, through a stable sort, the tracks whose name equals the query, then those that contain it or are contained in it (whole words, case, punctuation and apostrophes ignored); an artist search keeps TIDAL's order. The answer's `topHit` (`TRACKS` or `ARTISTS`) is not read.
- **Pagination**: advance according to `totalNumberOfItems`, not the number of items received (unavailable tracks are filtered out: 97 received for `limit=100`). Pages of 100, except `playlistsAndFavoritePlaylists` which refuses more than 50.
- **Home v2**: rows `{type, title, items: [{type, data}]}`. Only `ALBUM`, `ARTIST`, `PLAYLIST` and `MIX` (since 0.4.8) are kept; `TRACK` (without album) and `DEEP_LINK` are ignored. Row titles follow `locale` (`fr_FR` / `en_US`, verified by `cargo test live_locale -- --ignored --nocapture`). Each row has a stable `moduleId`, independent of the language (`BECAUSE_YOU_LISTENED_TO_ALBUM`, `YOUR_FAVORITE_ARTISTS`…) → `HomeRow::key`; "Because you listened to" carries its context in a separate `header`. **Pagination** (0.4.77, #207, `tidal/home.rs`, tested; `cargo test live_home_pages -- --ignored --nocapture`): `page.cursor` passed back as `cursor=` with the same parameters, `null` on the last page; two pages seen on 2026-11-05 (11 then 7 rows, including an ignored `TRACK_LIST`), all `moduleId`s different, ~0.5 s per page, 5 pages read at most. Several rows can share a key (grouped by `home_layout`), so no deduplication. Command `home` → `HomeFeed { sections, more }` (first page only, shown at once), then `home_rest` → the whole home laid out, starting from the first page kept by the client (`HomeCache`, reread if the account or language changed); a failing next page is logged and the home keeps the previous ones. `Home.svelte` keeps the "Featured" album already shown when the rest arrives (`featuredId`).
- **Date added**: each track of `playlists/{uuid}/tracks` carries `dateAdded` (`2024-04-12T22:51:56.872+0000`), favorites carry `created` (date of the like). Both become `TrackEntry::added_at` (ms UTC, `tidal/date.rs`). `TrackEntry` is serialized flat (`#[serde(flatten)]`): on the UI side, a `Track` with `addedAt`. The date goes neither into the cache nor into the queue.
- **Images**: `resources.tidal.com/images/<id with / instead of ->/<n>x<n>.jpg`. Covers 160 (`AlbumRef::cover_small_url`: track rows, playback bar, "Up next", track info), 320 (cards) and 640 (`cover_large_url`: "Now playing", home banner, album header); an `AlbumRef` saved before 0.4.36 only has the 320, the other two are derived from it on reread (`StoredAlbumRef`, #89); on the UI side `coverSmall` / `coverLarge` (`lib/format.ts`), artist photos and playlists (`squareImage`) at 320.
- **`MediaItem`** is serialized with the `kind` tag: no type it contains may have a `kind` field (hence `AlbumSummary::album_type`, test `media_item_tag_is_unique`).

## Feed, mixes, radios, lyrics

- **Bottom of the album page** (0.5.32, #350, `tidal/album_related.rs`, pure tested logic; `cargo test live_album_related -- --ignored --nocapture`, verified on 2026-11-12): v1 `pages/album?albumId=&deviceType=BROWSER&locale=` (~160 ms, 55–80 kB) → `rows[].modules[]`: `ALBUM_HEADER`, `ALBUM_ITEMS`, some `ALBUM_LIST` (`pagedList.items` = v1 albums without `type`) and an `ARTIST_LIST`. Module titles are **translated** ("Other Versions", "More Albums by …", "Related Albums"): each module is recognized by a UUID stable from one album to another, in `id` (base64 JSON, field `m`) and in `showMore.apiPath`; `7f62f3ef-…` = other versions (*Nevermind*: 5 editions), `3f410242-…` = other albums by the artist (20 at most), `d788041e-…` = related albums (not shown). Album missing in the country (*Thriller 25*, 1632061) → **404**: empty lists. Command `album_related(id)` → `AlbumRelated { versions, byArtist }` (displayed album and duplicates removed, unreadable item omitted, error logged = empty lists), through the content filter. **Not a replacement for the hi-res twin** (#55/#59): for *Hotel California (2013 Remaster)*, the versions give the 40th Anniversary but not the hi-res album with the same title (68709104); the UI only removes from the row the twin already shown by the banner. UI: `Album.svelte` requests it after the tracks are shown, two `CardGrid`s as scrolling rows under the copyright (`.album-related`), absent if empty; "More by <artist>" (main artist) with the "See the artist" link (`more` prop of `CardGrid`, `.card-grid-more`). Preview: `?route=album`.
- **Feed** (0.4.8, #14, `tidal/feed.rs`, view `views/Feed.svelte`, route `feed`): v2 `feed/activities?userId=…&deviceType=BROWSER&platform=WEB&locale=<language>` → `{ activities: [{ followableActivity: { activityType, occurredAt, album | historyMix }, seen }], stats }`. Types seen: `NEW_ALBUM_RELEASE` (full album) and `NEW_HISTORY_MIX` (`historyMix`: `HISTORY_MONTHLY_MIX` mix in the `favorites/mixes` format, read by `RawMix`, opened through `pages/mix` like the others, 0.4.9). `FeedItem::item` is a `MediaItem` (album or mix). **No pagination**: `offset` ignored, `limit` truncates, window of about 50 activities (verified on 2026-10-30). `seen` is read, never written. The UI groups by Today / This week / month and reuses `Card`. Preview: `?route=feed`.
- **New releases from followed artists** (0.5.63, #415, `tidal/releases.rs` and `commands/feed.rs`, pure tested logic; `cargo test live_feed_coverage -- --ignored --nocapture`, verified on 2026-11-13): the feed **is not enough**. Over 60 days and 35 followed artists, it was missing 9 of the 37 releases from `artists/{id}/albums`. Some are normal (features, another edition with the same title), but releases by the main artist were missing too (an album from 2026-11-05). `artists/{id}/albums` (with and without `filter=EPSANDSINGLES`) is sorted by release date descending: `limit=10` per list is enough, 2 requests per artist, 6 artists in parallel (~4 s for 35 artists, against 7 to 8 s sequentially), copy kept for 30 min per account (`ReleasesCache`). `feed_with_releases` adds to the feed the releases of the last 90 days (not future dates); an album is already present if its id is there, or if an album by the same main artist, of the same type (`ALBUM`/`EP`/`SINGLE`) and with the same title (case and spaces ignored) is there (explicit and clean editions). Date = `releaseDate` at midnight UTC; sorted by date descending. If the artists cannot be read, the feed alone is returned. **"Seen" locally** (setting `feed_seen`: `{user, keys}`, keys `album-<id>` / `mix-<id>`, 1,000 at most): on the first read for an account, it takes TIDAL's `seen` and treats as seen what is more than 14 days old or has no date. Opening the page calls `mark_feed_seen` (the whole last feed read, kept in `FeedState`); the "New" badges stay shown during that visit. **Badge**: `feed-unseen` event (count), emitted after `feed`, `mark_feed_seen` and by `spawn_watch` (20 s after launch, then every 6 h, retry after 5 min without a session); `lib/stores/feed.svelte.ts`, `.nav-badge` counter next to "Feed" (sidebar), `.tab-dot` on the Feed tab (Android). The page reloads the feed if the counter is not zero. No system notification.
- **Mixes and radios** (0.4.8, #11, `tidal/mix.rs`): `MediaItem::Mix(MixSummary)` (alphanumeric id, title, subtitle, 320 image, `mixType`). The same mix arrives in three forms, all read by `RawMix` (tests): home v2 (`titleTextInfo.text`, `subtitleTextInfo.text`, `mixImages: [{size, url}]`, `type`), v2 `favorites/mixes` and `pages/mix` (`title`, `subTitle`, `images: {SMALL|MEDIUM|LARGE: {url}}`, `mixType`). Image URLs signed by the API (`images.tidal.com/…?token=`), kept as is; this host must be in the CSP's `img-src` (`tauri.conf.json`), otherwise WebView2 blocks the images while `pnpm dev`, without CSP, shows them (#56, 0.4.16). Commands `mix(id)` (header from `pages/mix?mixId=` + tracks from `mixes/{id}/items`, items `{item, type}` of which only `track`s are kept), `radio(seed: track|artist, id)` (`tracks/{id}/radio`: 96 tracks seen, `artists/{id}/radio`: 100) and `library_mixes` (v2 `favorites/mixes`, cursor; 14 mixes on the test account). Mixes do not go into the cache (changing content), their tracks do. UI: `Mix.svelte` view shared by the `mix` and `radio` routes; Radio button on each track row (`TrackRow`) and in an artist's header (`PageHeader` `onRadio`); "Mixes" tab of the library. **Saving a mix** (0.4.78, #204): see "Library writes"; not yet for radios (a radio's mix id, `mixes.TRACK_MIX` of `tracks/{id}` or `ARTIST_MIX` of `artists/{id}`, is not read yet).
- **Lyrics** (0.4.8, #5, `tidal/lyrics.rs`): `GET v1/tracks/{id}/lyrics` (verified, test `cargo test live_lyrics -- --ignored --nocapture`) returns `{lyricsProvider, isRightToLeft, lyrics, subtitles}`, `subtitles` in LRC; **404 = no lyrics** (instrumental, classical), translated to `None`. `Lyrics::text` = `Synced` (lines in ms, sorted, empty line = instrumental passage) or `Plain` (fallback if `subtitles` is empty or unreadable). LRC parsing tested: multiple timestamps on one line, `mm:ss[.x|.xx|.xxx]`, `[ar:…]` headers ignored. Command `lyrics(trackId)`. UI: `components/Lyrics.svelte` in a "Now playing" panel, exclusive with the queue (`ui.nowPlayingPanel: "queue" | "lyrics" | null`). The current line follows `estimatedPosition` (like `Progress`) and stays centered through smooth scrolling, following suspended for 4 s after a manual scroll; click on a line = seek. Scroll margins in `cqh` (`container-type: size`): `vh` or `%` overflowed the panel. Provider credit (Musixmatch) under the lyrics. **Lyrics + queue** (0.4.48, #119): `ui.nowPlayingPanel` can also be `both`. Window of 1400 px or more (`matchMedia`, never on Android): the Lyrics and Queue buttons are independent, both open = two columns (lyrics 460 px, queue 380 px; cover above the controls under 1800 px). Narrower: a single panel, `both` shows the lyrics. Lyrics without the queue alongside: "Up next" band (`.np-next`, 3 next tracks as compact `TrackRow`s, "Whole queue" link `.np-next-all`). Preview: `?nowplaying=1&lyrics=1&queue=1`.

## Library writes (0.4.12, #4; album / artist / playlist favorites 0.4.25, #81; verified on 2026-10-30)

Test `cargo test live_collection -- --ignored --nocapture` (`tidal/live_collection.rs`, **modifies the account**: a track, album, artist and another user's playlist **absent** from favorites added then removed (an item already present is skipped, never removed), throwaway playlist created, filled, emptied then deleted, cleanup even on failure). Client in `tidal/collection.rs`, generic requests `api::Call` (method, form, `If-None-Match`); v2 errors (`errors[].detail`) are read.

- **Mixes** (#204, verified on 2026-11-05): `favorites/ids` has **no** `MIX` key; set read through GET v2 `favorites/mixes/ids?limit=50` → `{content: ["<id>", …], cursor}` (cursor, sorted by id), in parallel with `favorites/ids` (`LikedIds::mixes`), replaced on each full read of the Mixes tab (`library_mixes` also emits `likes`). Add: PUT v2 `favorites/mixes/add?mixIds=<id>&onArtifactNotFound=FAIL` (query, no body); remove: PUT v2 `favorites/mixes/remove?mixIds=<id>`, idempotent. The added mix arrives **at the end** of `favorites/mixes`. `LikeTarget::Mix { id }` (id checked by `is_mix_id`); heart in a mix's header (`Mix.svelte`, not a radio's) and an entry in the mix cards' menu.
- **Favorites in memory** (`tidal/likes.rs`, four sets since #81, five with mixes): GET v1 `users/{id}/favorites/ids` → `{TRACK: ["<id>", …], ALBUM, ARTIST, PLAYLIST, VIDEO, …}` (identifiers as strings, the whole library in one request). It also counts unavailable tracks (450 against 424 in `favorites/tracks`): it is a superset; albums and artists match their lists exactly (115 / 39). `PLAYLIST` contains followed playlists **and sometimes one of yours** (1 out of 2 on the test account). Sets loaded on the first `likes`, kept up to date by `set_liked`, replaced category by category on each full read of the library (Tracks, Albums, Artists; Playlists: only other people's), emptied on sign-out. A single `likes` event (`LikedIds`: `tracks`, `albums`, `artists`, `playlists`, sorted lists) after each write and each full read; the UI (`lib/stores/likes.svelte.ts`) only displays it, the state changes on the backend's confirmation (no optimistic display).
- **Adding to favorites**: POST v1 `users/{id}/favorites/{tracks|albums|artists|playlists}` (form `trackIds` / `albumIds` / `artistIds` / `uuids`, `onArtifactNotFound=FAIL`). Tracks, albums and artists arrive at once at the top of their list (sorted by date); a followed playlist arrives at the end of `playlistsAndFavoritePlaylists`. Remove: DELETE `users/{id}/favorites/<type>/{id or uuid}`, **idempotent** (removing an absent favorite answers 2xx).
- **Creating a playlist**: PUT v2 `my-collection/playlists/folders/create-playlist?name=…&description=…&folderId=root` → `{data: {uuid}}`; visible at once in `playlistsAndFavoritePlaylists` (`mine = true`). Deleting: PUT v2 `my-collection/playlists/folders/remove?trns=trn:playlist:<uuid>`, then `playlists/{uuid}` answers 404.
- **Putting a track back in its place** (0.5.19, #349, `insert_in_playlist`, command `restore_to_playlist`): the same POST v1 `playlists/{uuid}/items` accepts `toIndex` **as form data**: the track is inserted at that position (0 = first; verified at the start, in the middle and in last position). With `onDupes=ADD`, a track already present elsewhere is added anyway (verified: `[a, b, a, c, d]`), which is what undoing the removal of a duplicate needs. The date added is that of the restore. Verified on 2026-11-11: `cargo test live_playlist_insert -- --ignored --nocapture` (throwaway playlist, no favorite touched). Out of eight chained writes, one ended in 412 despite `retry_stale` on one run out of two: the UI then shows "modified elsewhere, try again" and reloads the playlist.
- **Adding to a playlist**: POST v1 `playlists/{uuid}/items` (form `trackIds` separated by commas, `onArtifactNotFound=FAIL`, `onDupes=SKIP`), without `toIndex` = at the end, in the given order. Answer `{lastUpdated, addedItemIds: [...]}`: a duplicate is ignored without error and absent from `addedItemIds` ("Already in …" on the UI side). Sent in batches of 100 (the API's `limit`), ETag reread before each.
- **Removing**: DELETE v1 `playlists/{uuid}/items/{index}` (index 0 = first track). Before that, `playlists/{uuid}/items?offset=<index>&limit=1` checks that it is the expected track (playlist modified elsewhere since display → `TidalError::Conflict`, nothing is removed). The ETag is read before this check: a change between the two gives a 412.
- **Batch writes** (0.5.56, #332, `tidal/collection/batch.rs`, verified on 2026-11-12 through `cargo test live_batch -- --ignored --nocapture`: throwaway playlist, tracks absent from favorites): DELETE v1 `playlists/{uuid}/items/0,2,4` removes several positions in **one** request (a single ETag); each position is checked first (`checked_etag_many`, tracks reread by pages of 100 between the first and last position), everything is refused if one has changed. Batches of 100 positions, from the bottom up (a removed batch does not shift the next ones). Undo: `insert_in_playlist` position by position, from the smallest to the largest. Favorites: POST v1 `users/{id}/favorites/tracks` with `trackIds=a,b,c` and DELETE `…/favorites/tracks/a,b,c` (batches of 100). Commands `set_tracks_liked(trackIds, liked)`, `remove_many_from_playlist(uuid, items)` and `restore_many_to_playlist(uuid, items)` (`items`: `{index, trackId}`).
- **ETag required**: every playlist change requires the `ETag` from GET `playlists/{uuid}` as `If-None-Match`. A stale ETag (playlist changed in the meantime) → **412** "You must send the correct Etag value…", translated to `TidalError::Conflict`.
- **Eventual consistency** (#201, seen on 2026-11-05): right after a write, `playlists/{uuid}` can return the old ETag, and a write sent with it to a lagging replica is **accepted and applied to the old state** (a move applied before the addition that preceded it). The ETag equals `lastUpdated` in ms: `tidal/versions.rs` (tested) remembers the most recent version seen after each of the app's writes (`settle` rereads the ETag until it sees it change), and `fresh_etag` rereads an older ETag instead of sending it; a 412 is retried twice at 400 ms (`retry_stale!`, a macro: an async closure broke `Send` inference for the commands). Rereading the tracks right after a write can also return the old order: the UI applies a confirmed move without rereading.
- **Moving** (#201): POST v1 `playlists/{uuid}/items/{index}` with `toIndex` **as form data** (as a query: 200 but ignored), ETag required, empty body. `toIndex` = final position (`[a,b,c,d]`, 0 → 2 gives `[b,c,a,d]`), beyond the end = at the end; several indexes at once possible (`items/0,1`). Expected track checked at `index` as for removal (`checked_etag`).
- **Renaming / description** (#201): POST v1 `playlists/{uuid}` (form `title`, `description`, each optional), visible at once; accepted even without an ETag (sent anyway). Folders: see "Playlist folders" (#331).
- **Commands** (`commands/collection.rs`): `likes` → `LikedIds`, `set_liked(target, liked)` (`LikeTarget` tagged by `kind`: `track` / `album` / `artist` with `id`, `playlist` with checked `uuid`, `mix` with checked `id`), `own_playlists` (`mine` playlists only), `add_to_playlist(uuid, trackIds)` → number added, `create_playlist(title, trackIds)` → uuid (non-empty title, 200 characters at most), `remove_from_playlist(uuid, index, trackId)`, `move_in_playlist(uuid, from, to, trackId)`, `edit_playlist(uuid, title, description)` (description 2,000 characters at most), `delete_playlist(uuid)` (#201); each write erases the kept copy (#152, #181).
- **Managing your playlists** (0.4.78, #201): on your playlists only, "Edit" button (`.edit-playlist`, pencil) in the header → `components/PlaylistEditor.svelte` (`.playlist-editor`: title, description, "Delete the playlist…" then confirmation; after deletion: pin removed, Playlists tab reloaded, back). ## Cleaning up a list (0.5.37, #382, verified on 2026-11-12)

- **Unavailable tracks** (`cargo test live_cleanup_probe -- --ignored --nocapture`, read-only): `playlists/{uuid}/tracks` returns **all** tracks, unavailable ones included, with `streamReady` **and** `allowStreaming` set to `false` ("Hall of Fame": 489/489 of which 8; same counts in `/items`): positions stay correct. `favorites/tracks` **hides** some (433 received for 460 announced, only one marked); the hidden ones answer 404 to `tracks/{id}` ("Track not found"): neither title nor ISRC, nothing to offer, they are not handled.
- **Adding an unavailable track again is refused**: POST `playlists/{uuid}/items` → 404 "Track not found". "Undo" therefore cannot put back an unavailable track that was removed or replaced: the operation is skipped (`skipped`) and the following positions realigned (`cleanup/ops.rs`, `Skips`, tested). The dialog says so before applying, and an unavailable track **without** a replacement is not checked by default (`suggested`).
- **Rules** (`tidal/cleanup/rules.rs`, pure tested logic): same song = same id, or duration within ±2 s and either the same ISRC, or the same main artist, same title and same version once edition marks are removed (`remaster`, `single version`, `album version`, in parentheses, brackets or after "-"). Live and remix stay separate. Per group, the first playable occurrence is kept; the others are duplicates (`sameTrack` if same id). An unavailable track whose replacement is already in the list becomes a duplicate.
- **Replacement**: `tracks?isrc=` (playable only), otherwise `search?types=TRACKS` "artist title" (20 results) with the same-song rule; preferred: same album title, same explicit marking, then hi-res. 4 searches in flight (`try_join_bounded`), an error counts as "none" (logged). Measured (`cargo test live_cleanup_report -- --ignored --nocapture`): 489 tracks in 4.6 s (6 replacements out of 8 unavailable, one edition duplicate), 433 favorites in 3.3 s.
- **Writes**: from the last position to the first (`ops::forward`, one position per change, insertions refused), each checked like a removal (#201). Replacing = inserting the replacement at the position (`toIndex`, `onDupes=ADD`) then removing the old one at the next position; if the removal fails, the replacement is removed. Stop at the first error; the result (`ListOpsResult`: `applied`, `skipped`, `undo`, `error`) gives the inverse of the applied operations, from the last to the first, returned as is for undoing. About 1 s per change (2.8 s for a removal and a replacement). Favorites: replacing = liking the replacement then removing the old one. Test `cargo test live_cleanup_apply -- --ignored --nocapture` (throwaway playlist: duplicate removed, replacement, undo with an unavailable track skipped, then deletion).
- **Commands** (`commands/cleanup.rs`): `playlist_cleanup(uuid)` / `liked_cleanup()` → `CleanupReport { items, scanned }`, each item (`kind: duplicate` with `kept`, `keptIndex`, `sameTrack`; `unavailable` with `replacement`) carries its `op` and `suggested`; `clean_playlist(uuid, ops)`, `undo_playlist_cleanup(uuid, ops)`, `clean_liked(ops)` (applies or undoes, emits `likes`). 10,000 operations at most; each playlist write erases the kept copy.
- **UI**: `components/CleanupDialog.svelte` (`.cleanup-dialog`, `.cleanup-row`, `.lost` for an unavailable track without a replacement): duplicates then unavailable tracks, one box per change, "Apply (n)", "Undo" toast. Playlist: "Clean up the playlist…" link (`.cleanup-link`) in "Edit the playlist", positions shown. Library › Tracks: "Clean up" button next to the pin, without positions. Preview: `?route=playlist&mine=1`, then the pencil; `?route=library&tab=tracks`.

## Play log (#34, spike verified on 2026-11-25)

- **Why**: requesting `playbackinfopostpaywall` is not a listen (the format panel calls it without playing). Official clients report each listen separately, and Seaglass did not until #34.
- **Source**: the official open-source SDKs, `tidal-music/tidal-sdk-web` (`player/src/internal/event-tracking/play-log/`, `event-producer/`) and `tidal-sdk-android` (`eventproducer/`, `player/events/`). Their Cypress tests (`player/cypress/e2e/play-log/`, including `case-gapless`) act as the spec.
- **Transport**: `POST https://ec.tidal.com/api/event-batch`, `Authorization: Bearer <token>`, form-encoded SQS `SendMessageBatch` (10 entries at most): `SendMessageBatchRequestEntry.<n>.Id` (event uuid), `.MessageBody` (event JSON), `.MessageAttribute.1` `Name` = event name, `.MessageAttribute.2` `Headers` = JSON (`app-name`, `app-version`, `os-name`, `client-id`, `consent-category: NECESSARY`, `requested-sent-timestamp`, `authorization` = the raw token again, so the body must never be logged). The answer is SQS XML: `SendMessageBatchResultEntry/Id` = accepted, `BatchResultErrorEntry` with `SenderFault=true` = malformed.
- **Event**: `{group: "play_log", name: "playback_session", version: 2, ts, uuid, payload}` (web shape; Android also embeds `user` and `client` read from the token's JWT claims `uid`, `sid`, `cid`, not needed). Payload: `playbackSessionId`, `startTimestamp` / `endTimestamp` (ms), `startAssetPosition` / `endAssetPosition` (s), `actions` (`PLAYBACK_START` / `PLAYBACK_STOP` with `assetPosition`, `timestamp`, on pause and resume), `isPostPaywall` (`assetPresentation == FULL`), `productType: TRACK`, `requestedProductId`, `actualProductId` (`trackId` of the answer), `actualAssetPresentation`, `actualAudioMode`, `actualQuality` (all three from the `playbackinfopostpaywall` answer), `sourceType` (`ALBUM`, …), `sourceId`.
- **Correlation**: `playbackSessionId` is the streaming session id, a UUID the client creates and sends as the `x-tidal-streamingsessionid` header on `playbackinfopostpaywall`. One per track played; in gapless, the first session ends at the track's duration and the next starts at 0.
- **Spike** (`spike/playlog.py`): `listen` plays a track for real in mpv and writes the event (no token), `send [--dry-run]` prints then posts it. A real 44 s listen (track 77599598) was answered HTTP 200 with the entry accepted. That only proves the collector took it, not that the listen counts.
- **In the app** (0.5.114): `tidal::playlog` (event body, SQS form, `Headers` attribute, XML answer, v4 UUIDs from `rand`; tested) and `TidalClient::send_play_logs` (current token, one refresh on 401). `stream(id, quality, StreamUse)` creates the streaming session and sends `x-tidal-streamingsessionid`, plus `x-tidal-prefetch: true` for a gapless preload as the web SDK does; the format panel and the hi-res offer send neither (nothing played). The session travels with the stream (`Stream::session`), the preloaded one with `next_loaded`. `requestedProductId` is the id asked for: the hi-res edition's when the stream comes from one (#18).
- **Listen tracking** (`player/playlog.rs`, pure, tested): a session starts at the first position while playing, at the load position (a resumed track starts mid-way). Ends: gapless move at the previous track's duration (metadata, the engine may already report the next one's) with the next starting at 0 at the same instant; natural end at the duration; anything else (skip, previous, jump, error reload, handoff, engine stop, exclusive failure, closing) at the last position. Pause / resume and seeks are actions (seek: `STOP` at the old position, `START` at the target if playing), as in the SDK's `basePlayer.ts`. Every stream heard is reported, short skips included; nothing during a blind test (#434), and the listens received from the linked device (#430) never are.
- **Queue and sending** (`player/report.rs`, `store/playlogs.rs`): the body (event `uuid` and `ts` fixed at queue time, so a resend is the same event) is queued with the TIDAL user id, 10,000 at most; no token on disk. A task sends batches of 10 under the current session, drops listens of another account, retries with backoff (30 s to 30 min) on network errors, 5xx, 429 or entries not taken, isolates then drops a listen refused with another 4xx, drops `SenderFault` entries. Closing the app queues the current listen in the closing save (#260). Each queued body is logged at debug level (`RUST_LOG=seaglass_lib::player::report=debug`): it holds no token; the form is never logged.
- **Not verified on TIDAL's side**: whether a listen accepted by the collector is counted (an SQS ack only says it was received); repeat One loops without reloading, so each loop after the first is a new session under a fresh id that no stream request carried; `sourceType` values other than `ALBUM` (`PLAYLIST`, `MIX`, `ARTIST`) come from the SDK demos' naming, not from a captured official event; other sources (liked tracks, search, radio…) are reported under the track's album. On Android there is no closing save: a listen in progress when the system or the user kills the app is lost (a finished one is already queued).

## One stream per account (#35, spike verified on 2026-11-25)

- **Not the play log**: #34's play log is fire-and-forget (an SQS ack), so a client cannot learn from it that another one took over. The official clients use a push service, "Pushkin" (`tidal-sdk-web`, `player/src/internal/services/pushkin.ts`; `handlers/load.ts` calls `Pushkin.ensure()`, `handlers/play.ts` sends the user action).
- **Connection**: `POST https://api.tidal.com/v1/rt/connect` (`Authorization: Bearer <token>`, `Content-Type: application/json`, no body) answers `{"url": ...}`, a `wss://pushkin-v2.tidal.com/...` URL (never logged, it may carry a credential). The PKCE client's token is accepted.
- **Idle cut**: the server drops a connection after exactly 5 s without traffic, with no close frame, whatever the `Origin`. Client pings (answered by pongs) every 2 s keep it open (3 min without a drop). The web SDK sends no ping and listens for a `'closed'` event that does not exist (the WebSocket event is `close`), so it probably relies on reconnecting at each `load()`: do not copy that.
- **Client → server**: `{"type": "USER_ACTION", "payload": {"startedAt": <ms>}}`, only on an explicit Play (not gapless moves or preloads). Verified: sent while the Android app played, it paused that app. The local clock is fine (offset to the server's `Date` within ±0.5 s; the SDK uses a synced clock).
- **Server → client**: `{"type": "PRIVILEGED_SESSION_NOTIFICATION", "payload": {"clientDisplayName": "Android", "sessionId": "<uuid>"}}` (no `endsAt` / `updatedAt` in practice, unlike the SDK's type). Received as soon as Play was pressed on the Android app after our `USER_ACTION`, then again on its later actions (13 in 3 min), so it must be handled idempotently. `sessionId` is the other client's, not our token's `sid`. A second connection under the same token got nothing when the first one's session sent `USER_ACTION`: the server only notifies other sessions. `RECONNECT` (fetch a new URL) was not seen.
- **No server enforcement**: with no Pushkin message at all, a second stream (`playbackinfopostpaywall` then the DASH segments) was served and played to the end while the Android app kept playing. Enforcement is entirely the clients' cooperation.
- **Spike**: `spike/pushkin.py` (`listen [--user-action] [--duration s]`, `play <track> [--no-pushkin] [--ao null]`), with `websocket-client` in `spike/requirements.txt`.

The credits' `id` is the artist's; unknown id: 404. `contributor(artistId, offset)` reads **200 tracks per call** (`BATCH`): offset 0 = the page + 3 data pages in parallel (~0.6 s); afterwards the page is reread (the only source of the path) then 4 pages. `ContributorPage { artist, total, tracks: [{track, roles}], nextOffset }`: `nextOffset` counts in API offsets, not in kept tracks (content filter #368 applied on output, tracks without album omitted), `null` at the end. Roles = `name`, deduplicated, the API's order. UI: see "Contributor page" in `interface.md`.

## Backend performance (#90)

- **Rate limiting** (0.5.113, #37, `tidal/backoff.rs`, pure tested logic): a 429 on any API call (`TidalClient::send`) sets a pause shared by every request: `Retry-After` in seconds (capped at 10 min; the HTTP date form is not parsed, no date crate), otherwise 2 s doubled up to 60 s, back to 2 s after a success; parallel 429s never shorten it. `call` waits for the pause before sending, retries the request that got the 429 once, then returns the error; a request facing more than 30 s of pause fails at once ("too many requests, try again in N s") without reaching TIDAL. Not covered: `oauth2/token` (its 429 stays a transient `Api` error, #252) and the init segment probe. Releases of followed artists (`releases.rs`) are read 3 artists at a time (6 before): the background watch reads them every 6 h.
- **Parallel pagination** (`tidal/paging.rs`, `get_all`): the first page alone (it gives `totalNumberOfItems`), then the pages up to the cap in one wave of requests, 4 in flight at most, put back in offset order (`try_join_bounded`, home-made on `poll_fn`: no `futures` crate). If unavailable tracks leave the list under the cap, one more wave for the rest. Without a total: sequential fallback, stop at the first incomplete page. Build the futures in a loop, not in a `map(|o| self.page(…))`: the closure makes `Send` inference for Tauri commands fail ("FnOnce is not general enough"). Measured with `live_catalog` (2026-10-30, 5 pages each): 484-track playlist 1.2–2.1 s → 0.6–0.85 s, 424 liked tracks 0.9–1.5 s → 0.6–0.75 s (one peak at 1.4 s); the order of favorites (like date descending) is checked by the test.
- **Bounded cache** (`tidal/cache.rs`): 20,000 tracks, least recently used evicted (clock updated on read as on write), in batches down to 95 % of the limit so as not to sort on every insertion. Queue tracks (`Queue::referenced_ids`) are pinned by the actor (`pin_queue_tracks`, on every `mark_queue_dirty` and on restore) and never evicted, even beyond the limit: `queue_view` and saving reread them.
- **Incremental persistence** (`store/mod.rs`, tests in `store/tests.rs`): the `Store` holds the set of ids in the `tracks` table (read on opening, updated after the commit only, hence correct even if a save fails). `save_player(queue, position, lookup)` only calls `lookup` (the cache) for referenced tracks missing from the table, and deletes in the same transaction the rows that are no longer referenced: databases from earlier versions are purged on the first save. A track missing from the cache is not counted as written and will be requested again. The actor now only copies the queue.
- **Settings in memory**: `kv` values read by `get_setting` stay in memory under a lock separate from the connection (absence included), modified only under the connection's lock to follow the order of writes: `ui_settings`, `playback_settings` and `track_info` no longer wait for a queue save. A value written directly to the database is therefore only seen after a restart.
- **Library cap** (#91): `LIBRARY_MAX` = 10,000 (2,000 before), for tracks, albums, artists and playlists; `const _: () = assert!(LIBRARY_MAX <= MAX_CONTEXT_LEN)` in `commands/player.rs` guarantees that playing or shuffling the whole list stays accepted. `get_list` (`paging.rs`) returns a `LibraryList { items, truncated, total }`: `truncated` comes from pagination (pages left at the cap, or more than `max` received), **not** from `total > items.len()` (the total counts unavailable ones: 450 announced for 424 liked tracks received on the test account, verified on 2026-10-31). The `library_tracks` / `_albums` / `_artists` / `_playlists` commands return this type (`library_mixes` stays a list). `likes.replace` only if the list is not cut. UI: "10000+" badge on the tab and `.library-truncated` banner "The 10,000 most recent liked tracks out of N are shown" (without "out of N" if the total is unknown). Preview: `?route=library&tab=tracks&truncated=1` (total 12,345) or `truncated=nototal`. `fixtures.json` keeps plain arrays (the mock backend wraps them).
- **Cached playlist pages** (0.4.59, #152, `tidal/playlist.rs`, pure tested logic): the ETag from GET `playlists/{uuid}` equals `lastUpdated` in ms (`"1793747577268"`), stable without changes, changed by each addition and removal (verified on 2026-11-03, also on another user's playlist: `cargo test live_playlist_etag -- --ignored --nocapture`, creates then deletes a throwaway playlist). In-memory cache of the last 20 pages (20,000 tracks at most, the most recent always kept), with the ETag as `PlaylistPage::revision`. Commands: `cached_playlist(uuid)` (kept copy or `null`, without network, its tracks put back into the metadata cache) and `playlist(uuid, revision)` → `null` if the ETag equals `revision`, otherwise the page (tracks kept if the ETag is the copy's, otherwise reread; without a copy or revision, header and tracks in parallel as before). Addition, removal and deletion in the app erase the copy; signing out empties everything (`mine` depends on the account). `Playlist.svelte` shows the copy at once then only replaces it if it changed; "Loading…" only appears after 300 ms; an error with a copy shown goes to a toast. Measured on 486 tracks: full read 690 ms, revalidation 210 ms (behind the already shown page). A playlist modified on another device shows its old state for a moment. Also kept from one launch to the next since 0.4.72 (see "List copies"). Preview: `?route=playlist&slow=1500`.
- **List copies** (0.4.72, #181, `store/snapshots.rs`, `commands/snapshots.rs`, tests): table `snapshots` (`key`, `used_at` = logical clock, `size` in tracks, `json`): playlist pages (`playlist:<uuid>`, 20 at most and 20,000 tracks, the least recently read or written pruned, the most recent always kept) and the library's Liked tracks, Albums, Artists, Playlists tabs (`library:<tab>`; not mixes: signed images that expire). Written after each full read (page with ETag only) in `spawn_blocking` without waiting; a playlist's copy erased by addition and removal in the app; everything erased at sign-in and sign-out (awaited). Unreadable copy (another version's format) erased. `cached_playlist` (asynchronous, no longer on the main thread): memory, otherwise disk, copy put back in memory (`restore_playlist`) for ETag revalidation. `cached_library(tab)`: the tab's copy, tracks put back into the metadata cache; `loadLibrary` shows it on the launch's first load then always rereads the whole list (no revision), an error with a copy shown goes to a toast; the library's "Loading…" after 300 ms. **Rendering in chunks** (`TrackList`): 40 rows at once, then 80 per task (`setTimeout`), full playback context. Measured in the dev app (2026-11-05, WebView2 through CDP, debug port `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333`): 486-track playlist in memory, first row 120 ms → 25 ms; first opening after a restart 715 ms with "Loading…" → 46 ms; liked tracks (427) after restart 758 ms → 29 ms. Not yet measured on the S21.
- **Compression**: the TIDAL API **never compresses** its answers (measured on 2026-11-03, #148: `gzip`, `br`, `zstd`, HTTP/1.1 or 2, the app's headers; 118,836 bytes for 100 liked tracks, 146,106 bytes for the home page, identical). No point enabling `reqwest`'s decompression.
- **Resolving a track**: without a possible hi-res edition (Android, "Off" setting), `tracks/{id}` and the stream go out in parallel (#148).
- Not handled: the downloaded update stays in memory until shutdown when "Later" is chosen (a few tens of MB, acceptable).
