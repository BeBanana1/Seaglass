# Android (#24)

Seaglass implementation notes, read on demand (index in [`CLAUDE.md`](../CLAUDE.md)).

## Status and notes

To pick it up again: first read the last "Progress update" comment of issue #24, then this file ("Status" bullet).

- **A single crate**: Tauri compiles `src-tauri` for Android (`cdylib`), without a workspace. Desktop-only code under `#[cfg(desktop)]` (cfg set by `tauri-build`): notification area, autostart, single instance, updater (all of `updater.rs`), stopping mpv on exit. Desktop plugins in `[target.'cfg(not(any(target_os = "android", target_os = "ios")))'.dependencies]` of `Cargo.toml`, with `tauri`'s `tray-icon` feature. `autostart_enabled` answers `false` on Android; `set_autostart` and the updater commands are not registered there.
- **Engine**: `engine::Launch` / `engine::ActiveEngine` per platform. Desktop: `mpv::engine::Launch` (config + `ProcessGuard`). Android: `media3::Launch` / `Media3Engine` (0.4.44); `engine::diagnose()` is `None` there, so no mpv banner. The `mpv` module compiles on Android (settings types) but is never launched there (`allow(dead_code)` on mobile).
- **Media3 playback** (0.4.44): `media3.rs` translates `Op` into arguments of the Kotlin `engine` command (`op_args`, `CacheSize` and `OutputDevice` ignored) and the JSON events of `Playback.kt` into `Event` (`translate`); pure logic tested on desktop (module also compiled under `test`). Events through a `tauri::ipc::Channel` created on the Rust side (`Channel::new`), called back on Android's main thread: unbounded queue drained by a task, so that this thread never waits for the actor (which may wait for it). `Playback.kt` (process-wide object) holds the ExoPlayer (Media3 1.5.1, the spike's version) on the main thread, 2-entry window like mpv: `play` = `setMediaItem` + `prepare` + `playWhenReady`, `preload` = `addMediaItem`, `Advanced` on `onMediaItemTransition` with reason `AUTO` only, `Ended` on `STATE_ENDED` / `onPlayerError` (limited message, signatures masked), position every 2 s during playback (1 s before #473), every 5 s without visible activity (`ProcessLifecycleOwner`, #147; the UI interpolates), right after a seek or a pause, format from `onAudioTrackInitialized`, `audiotrack` driver. Volume = mpv's cubic curve × normalization gain, **capped at 0 dB** (ExoPlayer's volume does not go above 1). **No manifest server on Android**: the MPD goes as a `data:application/dash+xml;base64,…` URL (`media3::data_url`, MIME type set on the Kotlin side), nothing listens on a port. Requested quality (`player/quality.rs`, pure tested logic; Settings › Playback › Quality, Android only): tiers **Low** (`LOW`), **High** (`HIGH`), **Lossless** (default) or **Max** (`HI_RES_LOSSLESS`) (0.5.22, #325; 4 tiers in 0.5.27, #366). Since 0.5.30 (#365): `wifi_quality` (unmetered network) and `cellular_quality` (metered network: mobile data, hotspot, or no network); the old `mobileQuality` becomes both when settings are read (`PlaybackSettings::from_saved`). `low_battery_quality` (off by default) caps: under 50 % High at most, under 20 % or battery saver Low at most, nothing while charging (plugged in, even full); the battery has the last word over the network. **Cap shown** (0.5.94, #492): invisible before, it made the setting look ignored (battery saver turned on by hand, everything stayed in Low with Wi-Fi in Max). `QualityPolicy::cap` (pure, tested; `pick` uses it) returns the applied quality, the setting's and the reason only when the battery actually lowers the quality; Android command `quality_cap`, note under the switch in Settings › Playback, reread when settings change and on return to the foreground. `QualityPolicy::current` reads the state on **each track resolution** through `Bridge` (`deviceConditions`, `DeviceConditions.kt`: `ConnectivityManager.isActiveNetworkMetered`, sticky intent `ACTION_BATTERY_CHANGED`, `PowerManager.isPowerSaveMode`; `ACCESS_NETWORK_STATE` permission), without a listener: a network or battery change counts on the next track (preloaded 30 s before the end), never mid-track. Unreadable state: the lower of the two network qualities. Desktop ignores all this and stays in Hi-Res Lossless (`QualityPolicy::ceiling`). In Max, the hi-res edition follows the `hires_upgrade` setting as on desktop (Automatic by default, setting not shown on Android). Verified on 2026-11-12 with the PKCE client (`cargo test live_mobile_qualities -- --ignored --nocapture`, 4 tracks including 97320484 in 24/96): same clear MPD in all 4 tiers (`SegmentTemplate` + `SegmentTimeline`, hence the same `data:` URL); `LOW` = `mp4a.40.5` (HE-AAC) at 97 kbit/s, `HIGH` = `mp4a.40.2` at 322 kbit/s, neither `bitDepth` nor `sampleRate` for AAC; `LOSSLESS` = FLAC 16/44.1 (526 to 1,026 kbit/s); `HI_RES_LOSSLESS` = FLAC 24/96 at ~3,000 kbit/s on a hi-res track, FLAC 16/44.1 otherwise; ReplayGain gain and peaks identical in all 4. **Max and 24-bit**: `Playback.kt` does not enable float PCM output, so Android decodes 24-bit FLAC to 16-bit (Android spike); the original rate stays. Enabling it (`DefaultRenderersFactory`) is still to be tested on the S21, useful only with a USB DAC (Bluetooth re-encodes). A setting change removes the preloaded next track (old quality) without reloading the current one.
- **Equalizer** (0.5.82, #467, `EqAudioProcessor.kt`): same setting and same profiles as desktop (`player::eq`, #428). A custom `AudioProcessor` rather than `android.media.audiofx.Equalizer` (the device's fixed bands, often 5: an AutoEQ profile would only be approximated, and behavior varies by manufacturer). Plugged in at the end of the `DefaultAudioSink` chain (`DefaultRenderersFactory.buildAudioSink` overridden in `Playback.build`, `setAudioProcessors`): it receives 16-bit PCM (without float output, the sink brings 24-bit down to 16 before the processors) or float; preamp then RBJ biquads in `double` (transposed direct form II, one memory per channel), saturation at the output, filters at 0 dB or beyond 0.49 × the sample rate ignored. Always active for these two formats, passthrough without a profile: activation happens live, without reconfiguring the sink. The profile (effective preamp + filters, `media3::eq_args`) goes with `play` and `currentGain`, not with `preload`: it applies to the whole playback; set from the main thread (`@Volatile`), picked up at the next buffer on the audio thread, coefficients recomputed on each `flush` (stream's sample rate). Log: `SeaglassPlayback` "equalizer: n filters at … Hz". **Verified on the S21 on 2026-11-18** (release APK 0.5.82): AutoEQ import pasted into the app, profile applied live during playback then removed without a gap, gapless transition with 10 filters (Media3 flushes the chain between two streams: coefficients recomputed, filter memory reset, no hole), `ExoPlayer:Playback` thread at ~3 % of a core without equalizer, ~4 % with 1 filter, ~5 % with 10 (FLAC 16/44.1, `top -H`). The normalization gain stays applied by ExoPlayer's volume, after the equalizer.
- **Burst buffering** (0.5.20, #323, `Playback.build`): `DefaultLoadControl` with 60 s minimum buffer, 5 min maximum and a 64 MB limit (`setTargetBufferBytes`); default start thresholds. Media3 1.5.1's defaults (minimum = maximum = 50 s, 13 MB) made it reload drip by drip during the whole playback. The player now loads up to 5 min ahead in one go and requests nothing until it is back down to 1 min; the buffer also covers the preloaded track (a single allocator for the window). In memory only. Measured on the S21 on 2026-11-11 (Wi-Fi, app in the background, bytes received by `wlan0` read every 5 s from `/proc/net/dev`): in 0.5.18, 450 to 1,000 KB every 5 s without interruption; in 0.5.20, 18 MB in 5 s when resuming a track, then nothing for 3 min, 30 MB in 10 s when preloading the next one, then nothing. Transition to the preloaded track without error. Memory (`dumpsys meminfo`): Java heap 21 → 49 MB, RSS 184 → 266 MB. Not measured: the battery itself (`batterystats` over 30 min), 4G, a track resumed after a long pause with an expired URL (unchanged path: playback error, then a new URL requested once).
- **Screen-off playback** (0.5.88, #474, `Playback.build`): **removed in 0.5.92** (#491): frequent micro-dropouts on Bluetooth headphones (Galaxy Buds 2, A2DP) in FLAC, where offload is inactive; no underrun in `logcat`; the only change of the period that affects FLAC, and no more dropouts when listening without it (APK 0.5.93, 2026-11-18). The option can only be set on the `Builder` (not per output, short of recreating the player). Sleeping in offload does not depend on it: `ExoPlayerImplInternal` enables `offloadSchedulingEnabled` from `RendererConfiguration.offloadModePreferred` (read in Media3 1.5.1's bytecode), so AAC in offload keeps its gain; only screen-off FLAC goes back toward the 0.5.85 figures. Original measurements: ExoPlayer's dynamic scheduling (`experimentalSetDynamicSchedulingEnabled`, present in Media3 1.5.1): the `ExoPlayer:Playback` thread (4.4 % of a core screen off in 0.5.85, out of ~12 % for the app) no longer runs every 10 ms when the audio buffer is full. **Measured on 2026-11-18 on the S21** (release APK 0.5.90, `scripts/android-perf.sh 1800 nogfx`, same conditions as in 0.5.85): app **8.5 %** of a core screen off (11.9 % in 0.5.85, TIDAL app 20.5 %), `ExoPlayer:Playback` thread 2.0 % (4.4 %); `batterystats` 5.3 mAh of CPU in 30 min (8.1); wakelocks unchanged (`AudioMix` and `ExoPlayer:WakeLockManager` held throughout playback). In the foreground, this thread goes from 3.2 % to 1 %. **Audio offload** (0.5.90, `AudioOffload.update`, in `Playback.updateOffload` until #45): **no effect for FLAC**. Media3 1.5.1's `MimeTypes.getEncoding` does not know `audio/flac` (only MP3, AAC, AC3 / E-AC3, AC4, DTS, TrueHD, Opus), and Android has no public FLAC encoding for `AudioTrack`: no app can send compressed FLAC to the audio chip, even if the S21's decodes it (`compressed_offload` output of `dumpsys media.audio_policy`: FLAC up to 48 kHz, MP3, AAC). Seen on the S21: "offload allowed" then "AudioTrack: offload inactive", decoding by `c2.sec.flac.decoder` in the app. The code (`AudioOffloadPreferences` set to `ENABLED`, `setIsGaplessSupportRequired(true)`, turned off while an equalizer profile is active because `AudioProcessor`s are bypassed in offload, `offload` format "decoded by the audio chip" in the signal path) serves the AAC qualities (Low, High: the default on mobile data). **Verified in AAC on the S21** (APK 0.5.90, High quality, 10 min screen off each time): with offload, app **1.6 %** of a core, no decoder left in the app, `batterystats` 0.4 mAh of CPU and 2.1 of wakelock (`AudioOffload`, held by the audio system); without offload, **17 %** (`MediaCodec_loop` 7.8 %: `c2.android.aac.decoder` is a software decoder, more expensive than FLAC), 3.5 mAh of CPU and 2.8 of wakelock. Three tracks chained on the same `AudioTrack` in offload (transition accepted by the system, no gap heard). **Dolby Atmos (One UI setting) blocks offload**: "isOffloadSupportedStatus: do not support offload in Dolby" in `logcat`, hence "offload inactive"; it also costs the system (uid `1041`, audioserver: 8.2 mAh of CPU in 10 min with Dolby, 0.2 without). Toggling it during playback cuts the sound for less than a second (output reconfiguration). **Also active on Bluetooth headphones** (Galaxy Buds 2, A2DP, Dolby Atmos off): "profile found", "AudioTrack: offload active", app 2.5 % of a core in 3 min screen off (`dumpsys media.audio_policy` reports `BtOffloadEnabled: 0`, with no consequence here). Not verified: offload being turned off with an active equalizer profile. **HE-AAC excluded** (0.5.93, #492, `AudioOffload.support`, the sink's `AudioOffloadSupportProvider` wrapping Media3's): in Low quality (`mp4a.40.5`) on Bluetooth headphones, AudioFlinger opens the `compressed_offload` output to A2DP but the HAL never renders anything (`get_render_position: No data available` in a loop, 1,184 times in 5 min); ExoPlayer recreates the `AudioTrack` every ~5 s, with no sound at all. HE-AAC is decoded in the app (slightly higher CPU in Low only).
- **Media session**: `PlaybackService` (`MediaSessionService`, `foregroundServiceType="mediaPlayback"`, exported for system controllers) started through `startService` when the engine launches and on each `play`, session added through `addSession` in `onCreate` (otherwise no controller connects); stopped by `onTaskRemoved` if nothing plays. **Foreground while paused** (0.5.15, #247): Media3 1.5.1 only keeps the service in the foreground during playback; when paused, app not visible, Android stopped it after a minute (`Stopping service due to app idle` in `logcat`, then `Destroying … media3.session` and `Media button session is changed to null`), and the next press on the earbuds reached nobody (process still alive though). `PlaybackService.onUpdateNotification`, through which every notification update goes, therefore keeps the foreground for 10 minutes after the last playback as long as a track is loaded (like Media3 ≥ 1.6), then lets go. Beyond that, the session disappears as before: the next step would be a `MediaButtonReceiver` in the manifest, ruled out without trying it on the phone (a service relaunched by it must go to the foreground within a few seconds, otherwise the app crashes; when the service is recreated, the notification's controller is not connected yet and Media3 may ignore the key). Audio focus and headphone unplugging handled by ExoPlayer (pause → `paused` event). The session sees a `RemotePlayer` (`ForwardingPlayer`): play, pause, seek, next, previous go back to Rust (`integrations/media_session.rs`, Kotlin command `sessionStart`) as `Cmd`, like SMTC; next / previous always offered. Title, artist, album, cover: observer `Observers::media_session`, sent only if the track changes (`nowPlaying` command, `replaceMediaItem` of the current entry, same URI so no reload). **Notification** (0.4.63, #163): tap = `setSessionActivity` to `NowPlayingActivity` (plugin, without UI, empty affinity), which sends the `openNowPlaying` action then relaunches the launcher intent and closes; Rust keeps the request (`integrations::request_now_playing`, taken by the `take_now_playing_request` command) and emits `open-now-playing`: the UI opens "Now playing" on the event or at its startup (WebView rebuilt after a swipe). Shuffle and repeat buttons = custom `CommandButton`s (`ICON_SHUFFLE_*`, `ICON_REPEAT_*`, session commands `dev.seaglass.SHUFFLE` / `REPEAT` granted in `onConnect`); a press sends `shuffle` / `repeat`, Rust computes the next state from the last one sent (Off → All → One) and sends the state back through the Kotlin `sessionModes` command (with translated labels) only if it changes. **Standard controller commands** (0.4.117, #254): `RemotePlayer`'s `setRepeatMode` / `setShuffleModeEnabled` send the requested state (`setRepeat` / `setShuffle` actions, `Cmd::SetRepeat` / `SetShuffle`); `getRepeatMode` / `getShuffleModeEnabled` return the last state received from Rust (`Playback.modes`), not ExoPlayer's (its repeat only serves "repeat the track"). The session takes the value from **events** and does not reread the getters: `RemotePlayer` keeps its listeners and sends them `onRepeatModeChanged` / `onShuffleModeEnabledChanged` on each `sessionModes` (ExoPlayer emits its own repeat first, Rust's state comes after). `COMMAND_SET_MEDIA_ITEM`, `COMMAND_CHANGE_MEDIA_ITEMS`, `COMMAND_SET_SPEED_AND_PITCH` and `COMMAND_SET_VOLUME` are removed from `getAvailableCommands` and from the commands granted in `onConnect` (`RemotePlayer.BLOCKED`): ExoPlayer's window and volume belong to the engine. No controller is filtered (#145). Verified on the S21 on 2026-11-10 (release APK 0.4.117): `dumpsys media_session` no longer announces `SET_PLAYBACK_SPEED` or the `PLAY_FROM_*` / `PREPARE_FROM_*`, keeps `SET_REPEAT_MODE` and `SET_SHUFFLE_MODE`; pause, play, next keys unchanged. Not verified: a repeat or shuffle sent by a real external controller (`adb` can only send keys). Actions are tested through an `Action` enum and not as `Cmd`: dropping a `Cmd` in a test pulls in the notification area code and the Windows test binary no longer starts (`STATUS_ENTRYPOINT_NOT_FOUND`, comctl32 v6).
- **HTTPS**: `reqwest` verifies certificates with Android's store through `rustls-platform-verifier`, which requires a JNI initialization before the first request (otherwise the panic "Expect rustls-platform-verifier to be initialized"): `android::init_tls()` at the start of `setup`, with the JVM and context set by tao (`ndk-context`). Its Kotlin component comes from rustls's Maven repository (`org.rustls:rustls-platform-verifier`, filtered group), at the version of the `rustls-platform-verifier-android` crate read from `Cargo.lock` (`gen/android/app/build.gradle.kts`); `-keep` rule in `proguard-rules.pro`.
- **Native bridge**: local Tauri plugin `src-tauri/plugins/seaglass-mobile/` (crate `tauri-plugin-seaglass-mobile`, Android-only dependency, Kotlin in `android/`, `dev.seaglass.mobile.SeaglassPlugin`). No command or permission exposed to the UI: the app calls it from Rust, in two ways. **Plugin commands** (`tauri_plugin_seaglass_mobile::native(app)`, `login` or `call(command, args)`): Tauri runs them in the **activity's** `PluginManager` (`wry::android::dispatch`), which panics ("no available activity") when the app is swiped away; reserved for what has the activity at hand (`engineStart` and `sessionStart` at launch, `login`, `installApk` from the UI) and refused by a guard (`set_activity`, set by `android::keep_alive`) between the window's destruction and rebuild. **Direct JNI** (#169, 0.4.65, `direct::call` / `direct::call_blocking`, Kotlin object `Bridge`, `-keep` rule in `consumer-rules.pro`): everything sent during playback (`engine`, `nowPlaying`, `sessionModes`, Keystore secrets). Class loaded on the first command through the application context's class loader (`ndk-context`, a native thread cannot find the app's classes with `FindClass`), call on a `spawn_blocking` thread attached to the JVM; `Bridge` runs the player and the session on the main thread and waits for them to finish (10 s at most), the secrets on the calling thread. JSON answer `{"ok": …}` / `{"error": …}`. Kotlin → Rust events (`Channel`) do not go through the activity. Any new command sent outside the UI goes into `Bridge`.
- **Sign-in**: Android only has one WebView for the app; a second `WebviewWindow` replaces the interface there (IPC callbacks lost, redirect never intercepted). `commands::auth::login_page`: dedicated window on desktop, the plugin's full-screen native WebView on Android (`SeaglassPlugin.login`: `shouldOverrideUrlLoading` + `onPageStarted` safety net, redirect URL returned to Rust, Back = cancelled; `https` navigations only, no files or content providers, #145), then the same `auth::redirect_code`. Verified on the S21 on 2026-11-03: sign-in, then library shown.
- **App swiped from recents** (0.4.44, `android::keep_alive`): the activity is destroyed, tao treats it as the last window closing and Tauri **quit the process** (`exited cleanly (0)`), player included, despite the foreground service. `RunEvent::ExitRequested { code: None }` → `prevent_exit`; on reopening, Android creates a new activity that tao leaves without a window: the config's main window is rebuilt there (`WebviewWindowBuilder::from_config`) on `MainEventsCleared`, **at least 1 s after the destruction** (tao signals the destruction before forgetting the activity: rebuilding at once attached it to the dying activity, its WebView crashed and killed the app). The Kotlin plugin's commands stay usable afterwards.
- **Verified on the S21 on 2026-11-03**: FLAC 16/44.1 (`c2.sec.flac.decoder`), preload 30 s before the end then transition without reload, seek, media keys (pause, play, next) and notification metadata, 90 s with the screen off (`mediaPlayback` service in the foreground), app swiped then reopened during playback. Not yet: the Buds' real buttons (simulated through `adb shell input keyevent KEYCODE_MEDIA_*`), incoming call / audio focus.
- **Secrets** (0.4.45): `keyring` has no Android store (fake in-memory store, sign-in lost on every launch): `android::install_keystore`, at the start of `setup`, gives it a backend (`keyring::set_default_credential_builder`) that calls the Kotlin plugin; `tidal/auth.rs` is unchanged. `SecretStore.kt`: AES-256 GCM key generated in the Android Keystore (alias `seaglass-secrets`, not exportable), only IV + ciphertext in base64 in the private preferences `seaglass-secrets` (key `seaglass/tidal-refresh-token`). Commands `secretGet` (`value` absent = `NoEntry`), `secretSet`, `secretDelete` (`existed`). **Blocking** calls (`direct::call_blocking`, #169): `keyring` is synchronous; its callers run on tokio, never on Android's main thread. Unreadable ciphertext (key lost, backup restored elsewhere) = erased, sign in again. `seaglass-secrets.xml` is excluded from backups and device transfer (`res/xml/backup_rules.xml`, `data_extraction_rules.xml`, #145); the database stays backed up. Error messages without values. Verified on the S21 on 2026-11-03: sign-in, `am force-stop`, relaunched signed in; sign-out → empty preferences, relaunched signed out.
