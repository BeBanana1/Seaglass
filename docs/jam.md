# Jam (#25)

Notes d'implémentation de Seaglass, lues à la demande (index dans [`CLAUDE.md`](../CLAUDE.md)). Le relais est une crate à part (`relay/`, déploiement dans `relay/README.md`).

## Historique par étape

Notes chronologiques : une étape plus récente l'emporte sur une plus ancienne. En particulier, le relais laisse **30 min** à l'hôte pour revenir depuis la 0.4.85 (5 min avant), et les mesures de l'étape 4 datent du délai de 5 min. Points relevés par l'audit du 2026-11-10 : #253, #256, #257.

- **Jam locale** (0.4.79, #25, étape 1, bureau seulement ; `src-tauri/src/jam/`, tests) : des invités sur le même réseau ajoutent des titres à la file depuis leur navigateur, sans app ni compte ; seule la machine de l'hôte lit. Choix de l'issue : pas de connexion aux comptes des invités (jetons d'autrui, autres catalogues).
- **Serveur** (`server.rs`, HTTP écrit à la main dans `http.rs` comme `mpv::serve`, aucune dépendance) sur `0.0.0.0:47800` (sinon un port libre), adresse locale = interface de la route par défaut (`lan_ip` : `connect` UDP, rien n'est envoyé) ; requête de 8 Kio, corps de 2 Kio, 5 s pour lire et écrire, 15 s pour TIDAL, 32 connexions. Windows demande l'autorisation du pare-feu au premier démarrage.
- **Page** (`jam/page/`, `include_str!`) : `index.html`, `jam.js` (tout en `textContent`), `jam.css`, CSP stricte (`img-src https://resources.tidal.com`), français / anglais selon `navigator.language`, code gardé dans `localStorage`.
- **API** (POST JSON, code dans l'en-tête `X-Jam-Code`, qui impose aussi une requête CORS préalable que le serveur ignore : pas d'appel depuis un autre site) : `join`, `search` (titres seulement, 30, compte de l'hôte), `add` (fin de la file manuelle, `Cmd::AddToQueue`, prénom facultatif), `state` (titre en cours et 20 titres de la suite).
- **Garde-fous** (`guard.rs`, logique pure) : code de 6 caractères sans 0/O/1/I tiré à chaque Jam, comparé en temps constant ; 10 essais ratés = adresse bloquée jusqu'à la fin de la Jam ; 60 recherches (30 en 0.4.79) et 10 ajouts par minute et par adresse ; seuls les titres sortis des recherches de la Jam peuvent être ajoutés ; erreurs de l'app journalisées, la page ne reçoit qu'un type d'erreur. Commandes `jam_status`, `start_jam` (→ `JamStatus`), `stop_jam` (`JamState`, tâche annulée = port fermé, code invalide). UI : Réglages › Application › Jam (`.jam-fields`, `.jam-code`, boutons `.update-check`). Aperçu : `?route=settings&tab=app&jam=1`. Testée sur un vrai téléphone par l'utilisateur (étape 1, jugée peu réactive).
- **Étape 2** (0.4.81) : **QR code** (crate `qrcode`, feature `svg`, `JamStatus::qr_svg` sans la déclaration XML, inséré par `{@html}` dans `.jam-qr` sur fond blanc) de `url#code` : le code après `#` n'atteint jamais le serveur, la page le lit puis le retire de l'adresse (`history.replaceState`). **Prénom** facultatif (`guests.rs` : 24 caractères, contrôles retirés, 500 titres retenus, le dernier invité l'emporte), envoyé avec l'ajout ; gardé dans le module Jam, en mémoire, **pas dans la file du lecteur** (persistée, sans notion d'invité) : `JamStatus::guests` + événement `jam-guests` → `lib/stores/jam.svelte.ts` (`guestOf`) → `TrackRow` `addedBy` (`.added-by`, file manuelle de `QueueList`) ; la page montre aussi « ajouté par ». **État en direct** : `GET /api/events?code=…` (Server-Sent Events, `EventSource` ne pose pas d'en-tête, d'où le code en query), 64 flux au plus hors des 32 connexions ordinaires, commentaire toutes les 20 s ; `push_loop` relit le lecteur toutes les secondes **seulement si une page écoute** et aussitôt après un ajout ou une nouvelle page, n'envoie que si le JSON change (`watch::send_if_modified`) ; l'émetteur vit dans `serve` : Jam arrêtée = flux fermés. Page : recherche pendant la saisie (400 ms, réponses périmées ignorées, 60 recherches par minute), « Recherche… », ✓ affiché aussitôt et annulé sur refus. Aperçu : `?route=settings&tab=app&jam=1&manual=1&queue=1` (QR factice, « ajouté par Léa »).
- **Besoin précisé** (issue, 2026-11-05) : en soirée, **sans Wi-Fi**, tout le monde en données mobiles ; partage de connexion écarté ; hôte surtout **le téléphone** ; toute app Seaglass doit pouvoir ouvrir une Jam (pas de jeton à saisir).
- **Étape 3a** (0.4.82) : **relais** `relay/` (crate séparée, sans workspace, `axum` + WebSocket, `README.md` pour le déploiement : DNS `jam.bebanana.ch`, `docker compose up -d --build`, bloc Caddy `reverse_proxy 127.0.0.1:47880` : Caddy du serveur en `network_mode: host`, port du relais publié sur la boucle locale seulement). L'hôte se connecte en sortie à `/host` (`Authorization: Bearer <SEAGLASS_RELAY_KEY>`, clé de build qui écarte les robots, pas un secret), protocole JSON dans `relay/src/protocol.rs` (`hello` code + reprise → `ready` id, secret, url ; `request` / `response` par `rid`, `client` = adresse de l'invité pour les limites de l'hôte ; `state` poussé, servi en SSE par le relais, qui vérifie le code des flux). Invités sur `/j/<id>/` (id de 128 bits), page de l'app embarquée par `include_str!` (d'où les **chemins relatifs** `jam.js`, `api/…` dans la page, valables aussi à `/`). Limites : 20 Jams, 10 créations par adresse et par heure, 12 h de vie, **30 min pour revenir** après une coupure (même id, même QR ; 5 min jusqu'au 2026-11-06), 120 appels par minute et par adresse, 64 pages par Jam, réponse de l'hôte en 15 s, 10 codes faux. Page : `offline` / `busy` (hôte coupé) et `ended`. Tests : unitaires + `relay/tests/relay.rs` (faux hôte tokio-tungstenite). CI : étape « Relais » ; `check-version.sh` exclut `relay/` (déployé à part). Déployé le 2026-11-05 sur `jam.bebanana.ch` (Caddy du serveur en `network_mode: host`).
- **Étape 3b** (0.4.83) : l'app se connecte au relais. **Règles communes** dans `jam/api.rs` (`Core` : code, limites, titres proposés, prénoms, `state_json`), servies par `server.rs` (réseau local) et `relay.rs` (en ligne) ; faux lecteur des tests dans `jam/testing.rs`. **Client** `relay.rs` : WebSocket sortant (`tokio-tungstenite`, fonctionnalité interne `__rustls-tls` avec un `Connector::Rustls` construit sur `rustls-platform-verifier` et le fournisseur `aws_lc_rs` : magasin de certificats du système, comme `reqwest`, prêt pour Android), clé `SEAGLASS_RELAY_KEY` du `.env` (`build.rs` → `SEAGLASS_SEAGLASS_RELAY_KEY`, variable au lancement prioritaire), `SEAGLASS_RELAY_URL` pour un autre relais. Types du protocole recopiés dans `jam/protocol.rs` (test de forme JSON). Requêtes des invités traitées en tâches parallèles, état poussé toutes les secondes s'il change et aussitôt après un ajout, ping toutes les 20 s, connexion perdue sans message pendant 60 s. **Reprise** : reconnexion de 1 s à 30 s avec `resume` (même adresse, même QR pendant 30 min) ; sinon nouvelle Jam, adresse et QR mis à jour ; clé refusée (401) = arrêt (`Connection::Failed`). `JamInfo` : `mode` (`online` / `local`), `url` (`None` avant `ready`), `connection` (`connecting`, `online`, `reconnecting`, `failed`), `reason` traduite ; événement `jam-status` (`relay_notify`, `apply` testé). Commandes `start_jam(mode)`, `jam_online_available`. UI : « Démarrer la Jam » (en ligne) et « Sur le réseau local », ligne `.jam-connection` (`.warn`, `.jam-reason`) ; sans clé compilée, seulement le réseau local. Tests : faux relais (`accept_hdr_async`) pour la transmission, l'état, la reprise et la clé refusée ; **`cargo test live_relay -- --ignored --nocapture`** contre le vrai relais (page en HTTPS, rejoindre, recherche, code faux, flux d'état à travers Caddy : vérifié le 2026-11-06). Aperçu : `?route=settings&tab=app&jam=1|local|reconnecting`.
- **Étape 4** (0.4.84, en cours) : module `jam`, commandes et `JamState` sur toutes les plateformes (`qrcode` dans les dépendances communes) ; sur Android, **en ligne seulement** (`JamMode::Local` refusé sous `cfg!(mobile)`, bouton « Sur le réseau local » masqué), groupe Jam de Réglages › Application affiché si une clé de relais est compilée. Ligne de démarrage `.setting-row.jam-start` qui passe à la ligne (le bouton débordait en Cyberpunk sur le S21). **Mesuré sur le S21 le 2026-11-06** (APK release 0.4.83, Wi-Fi) : Jam ouverte en 0,3 s, rejoindre, recherche réelle faite par le téléphone et état en direct depuis le PC ; **en pause, écran éteint, Android coupe le réseau de l'app au bout d'environ 1 min 30** (`failed to lookup address information`, DNS refusé), la Jam est fermée par le relais après 5 min, puis rouverte avec une nouvelle adresse au réveil (QR mis à jour à l'écran). **Pas encore mesuré** : musique en lecture écran éteint (une seule mesure à 0 min, réussie). Pistes si ça ne tient pas, ou pour la pause : allonger le délai de reprise du relais (5 → 30 min), garder le service au premier plan tant qu'une Jam tourne (type de service à choisir), ou une exception à l'optimisation de la batterie.
- **0.4.85** : délai de reprise du relais porté à **30 min** (`Config::grace`) : une pause écran éteint (réseau coupé par Android) ne change plus l'adresse des invités ; à redéployer sur le serveur (`git pull`, `docker compose up -d --build`).
- **Accès rapide** : bouton `.jam-open` (icône `jam`, `.active` à l'accent quand une Jam tourne) dans `.now-actions` de « En lecture », qui ouvre `components/JamDialog.svelte` (`.jam-backdrop`, `.jam-dialog`, jetons `--dialog-*`, `jam.dialogOpen`, `openJamDialog` / `closeJamDialog`, fermé par Échap et par Retour d'Android avant « En lecture »).
- **Rangement** : tout le contenu de la Jam (démarrage, connexion, QR, adresse, code, arrêt) dans `components/JamPanel.svelte`, partagé par Réglages et la fenêtre ; il garde les classes `.setting-row` et `.update-check` (styles de base recopiés, les thèmes les habillent par nom de classe). Aperçu : `?nowplaying=1&jam=1`, puis le bouton Jam.
- **Lecture / pause par les invités** (0.4.87, #222) : `POST api/pause` `{paused}` (explicite, pas une bascule) → `Backend::set_paused` → `Cmd::SetPaused` ; choix de l'hôte `Core::controls` (activé par défaut, par Jam, non persisté), commande `set_jam_guest_controls(enabled)`, `JamStatus::guestControls`, interrupteur `.setting-switch` dans `JamPanel` (`.jam-controls`) ; refusé = 403 `controls` ; 6 par minute et par adresse (`Action::Control`) ; `GuestState::controls` → bouton `.play-pause` dans le bloc « En lecture » de la page.
- **Liens d'autres services** (0.4.91, #229, #225, module `foreign/`, logique pure testée ; `cargo test live_foreign_links -- --ignored --nocapture`, 10 liens vérifiés le 2026-11-06, 0,2 à 0,9 s) : une recherche de la Jam reconnue comme lien par `foreign::find` (texte de partage compris) passe par `Backend::link` au lieu de la recherche ; la réponse porte `link: true`. Deezer : API publique (`api.deezer.com/track|album/<id>`) → ISRC ou UPC → `tracks?isrc=` / `albums?upc=` de TIDAL (`tidal/lookup.rs`), éditions de l'album du lien en tête (`rank_editions`) ; Spotify : page publique (`og:title`, `og:description`, `music:duration`) et oEmbed pour un album ; Apple Music : `itunes.apple.com/lookup` ; YouTube : oEmbed, titre nettoyé (« Artiste - Titre (Official …) », chaîne « … - Topic ») ; TIDAL : titre ou album direct. Sans ISRC, recherche TIDAL « titre artiste » classée par titre, artiste, durée (±3 s) et album (`matching.rs`), 10 résultats au plus. Seuls ces hôtes sont contactés, client `reqwest` à part sans redirection automatique (8 s) ; un lien court (`spotify.link`, `link.deezer.com`) n'est suivi que vers un lien reconnu, 3 fois au plus. L'invité confirme toujours (« + ») : rien n'est ajouté d'office. `MAX_QUERY_CHARS` = 300 (liens Apple). Page : ligne `.apps` « Chercher dans : » puis cinq boutons ronds `.app` (TIDAL, Spotify, YouTube Music, Deezer, Apple Music ; 0.4.94, logos SVG de Simple Icons (CC0) intégrés à la page, couleur de la marque par `--brand`, nom en `title` / `aria-label`, `target=_blank`), indication `.hint` sous la recherche, « Rien trouvé pour ce lien » ; onglets seulement s'il y a des titres et des albums. La page des invités (#224) a une croix `.clear` qui remplace celle de `type="search"`.
- **Albums et retrait** (0.4.88, #223) : `search` avec `albums: true` renvoie `{tracks, albums}` (20 albums, `view::GuestAlbum`), sans lui un tableau de titres (page d'avant #223). `POST api/add-album` `{albumId}` : album proposé par une recherche de la Jam seulement, compte pour un ajout, 30 premiers titres (`MAX_ALBUM_TRACKS`, `Backend::album_tracks` = `tidal.album`) en fin de file manuelle (`Cmd::Enqueue`). Chaque ajout forme un **lot** (`Guests::new_batch`) noté avec le prénom et le **jeton du navigateur** (`guest`, 32 hex tirés par `crypto.getRandomValues` dans `localStorage`, `sanitize_token`) ; `add` / `add-album` renvoient `batch`. `GuestTrack::batch` dans l'état poussé ; la page garde ses lots par code de Jam (`seaglass-jam-mine`) et montre ✕ (`.remove`) sur ses titres et « Retirer l'album » (`.batch-head`) avant le premier titre d'un de ses albums. `POST api/remove` `{guest, batch, trackId?}` : `Guests::take` ne rend que les titres dont l'invité est l'auteur (un titre ajouté de nouveau par un autre ne l'est plus), puis `Cmd::RemoveFromQueueIds` retire une entrée de la file manuelle par identifiant, la première trouvée ; 30 retraits par minute. Le prénom n'est pas une identité, le jeton si. Page : onglets Titres / Albums (`.tabs`, `.tab`) quand la recherche trouve des albums. Le relais embarque la page : le redéployer après un changement de `jam/page/`.
