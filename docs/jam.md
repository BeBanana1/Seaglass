# Jam (#25)

Seaglass implementation notes, read on demand (index in [`CLAUDE.md`](../CLAUDE.md)). The relay is a separate crate (`relay/`, deployment in `relay/README.md`).

## History by step

Chronological notes: a more recent step wins over an older one. In particular, the relay gives the host **30 min** to come back since 0.4.85 (5 min before), and the step 4 measurements date from the 5 min delay. The per-address limits and the blocking until the end of the Jam described in the first steps were replaced in 0.4.116 (#256, last entry).

- **Local Jam** (0.4.79, #25, step 1, desktop only; `src-tauri/src/jam/`, tests): guests on the same network add tracks to the queue from their browser, with no app or account; only the host's machine plays. The issue's choice: no connection to the guests' accounts (other people's tokens, other catalogs).
- **Server** (`server.rs`, HTTP written by hand in `http.rs` like `mpv::serve`, no dependency) on `0.0.0.0:47800` (otherwise a free port), local address = interface of the default route (`lan_ip`: UDP `connect`, nothing is sent); 8 KiB request, 2 KiB body, 5 s to read (head and small body, counted from the first byte; a large handoff body accepted after the code check gets 1 s more per 256 KiB, up to 20 s, the phone's own limit: `http::read_time`, #60) and 5 s to write, 15 s for TIDAL, 32 connections. Windows asks for firewall permission on first start.
- **Page** (`jam/page/`, `include_str!`): `index.html`, `jam.js` (all through `textContent`), `jam.css`, strict CSP (`img-src https://resources.tidal.com`), French / English depending on `navigator.language`, code kept in `localStorage`.
- **API** (POST JSON, code in the `X-Jam-Code` header, which also forces a CORS preflight that the server ignores: no call from another site): `join`, `search` (tracks only, 30, host's account), `add` (end of the manual queue, `Cmd::AddToQueue`, optional first name), `state` (current track and the next 20 tracks).
- **Safeguards** (`guard.rs`, pure logic): 6-character code without 0/O/1/I drawn for each Jam, compared in constant time; 10 failed attempts = address blocked until the end of the Jam (a quarter hour since #256); 60 searches (30 in 0.4.79) and 10 additions per minute per address; only tracks coming from the Jam's searches can be added; app errors logged, the page only receives an error type. Commands `jam_status`, `start_jam` (→ `JamStatus`), `stop_jam` (`JamState`, task cancelled = port closed, code invalid). UI: Settings › Application › Jam (`.jam-fields`, `.jam-code`, `.update-check` buttons). Preview: `?route=settings&tab=app&jam=1`. Tested on a real phone by the user (step 1, found not very responsive).

- **Per-guest limits and queue cap** (0.4.116, #256, raised by the 2026-11-10 audit): on mobile data (IPv4), several guests often go out through the same address. **Limits** (`guard.rs`): each action is counted for the guest (key `owner_key`: browser token, otherwise `ip:<address>`) at the previous thresholds (10 additions, 60 searches, 6 play / pause, 30 removals per minute) **and** for the address at 5 times these thresholds (`IP_FACTOR`); an action is only counted if both allow it (a refusal from the address does not weigh on the guest). ## Remote control (#336, 0.5.39, desktop)

Drive the PC's player from a phone's browser, on the local network. Module `jam/remote/`: reuses the Jam server, but **on another port** (47801, otherwise a free port) rather than a Jam's, unlike the issue's proposal: the remote must run without a Jam and from one launch to the next, and two servers separate permissions by construction.

- **Shared server**: `server.rs` serves a `Site` (page files, `check_code`, `api`, `state_json`, `refresh`); `JamSite` (the Jam's Core + Backend) and `RemoteSite` (`Owner` + `Remote`) plug into it. The Jam server answers 404 to the remote's commands and to `remote.js` (test `guests_never_reach_the_owner_commands`); a Jam code or a similar code opens nothing on the remote (`only_the_owner_code_opens_the_remote`).
- **Owner code**: 12 characters from the Jam alphabet (`guard::code_of_len`, 60 bits), compared in constant time, case and dashes ignored (shown as `XXXX-XXXX-XXXX`), 10 failed attempts per quarter hour per address (`Limits`). **Storage** (0.5.120, #61, `commands/remote/stored.rs`): the switches (`enabled`, `handoff`) in SQLite (`remote` setting), the code and the tunnel identity (id, secret, key, #430) as one JSON entry of the credential store (`seaglass` / `remote-link`), like the TIDAL token: together they reach the PC's handoff and history routes from anywhere. Values found in SQLite are the newest (before 0.5.120, or a credential store that refused a write, logged) and move to the credential store as soon as it takes them. A credential store that cannot be **read** fails the remote commands and skips the launch restore, rather than drawing a new code that would unpair every phone. Damaged values are dropped and drawn again. The custom relay key stays in `relay.settings`: it is not a secret by design. Tested with a fake store (`Vault` trait). Handing the key out is limited to the pairing window (#62). "New code" (`renew_remote_code`, `Owner::set_code`) refuses the old one at once; the page then goes back to the code screen.
- **API** (`remote/api.rs`, POST, `X-Jam-Code` header): `join`, `state`, `pause {paused}` (explicit), `next`, `previous`, `seek {seconds}`, `volume {level}` (0–100, `Volume::validate`), `mute {muted}`, `shuffle {enabled}`, `repeat {mode}`, `jump {part, index, trackId}` (`Cmd::PlayFromQueue`), `remove {trackId}` (manual queue, `RemoveFromQueueIds`), `play {trackId}`, `enqueue {trackId, next}`, `play-album {albumId, shuffle}`, `play-playlist {uuid, shuffle}` (uuid checked by `is_uuid`, "Playing from" source set), `search {query}` (30 tracks, 20 albums, 20 playlists, content filter applied), `playlists` (library, read-only). **Nothing writes to the account.** The API produces a `Command` (testable enum) translated into `Cmd` by `to_cmd`: a `Cmd` dropped in a test breaks the Windows test binary (`docs/android.md`). Limits: 120 commands per minute (`Action::Command`), 60 searches (`Action::Search`).
- **Pushed state** (`/api/events`, like the Jam): `RemoteView` (track, pause, loading, position in whole seconds, duration, volume, mute, shuffle, repeat, 50 tracks of the manual queue and the continuation). The position changes every second while playing: one send per second as long as a page listens; the page interpolates in between.
- **Page** (`remote/page/`: `index.html`, `remote.js`, `remote.css`, plus `jam.css` also served): sticky player at the top (position and volume sliders sent on release), Queue / Search / Playlists tabs, the app's icons (`Icon.svelte`) as SVG in the page, code in `localStorage` (`seaglass-remote-code`), QR code `url#code` like the Jam. **Preview** with a fake player: `cargo test remote_page_preview -- --ignored --nocapture`, then `http://127.0.0.1:47899/#AB23CDEF45GH` (30 min).
- **UI**: Settings › Application › Remote (`components/RemotePanel.svelte`, desktop only): `.setting-switch` (remembered, turned back on at launch by `commands::remote::restore`), QR code, address, code, "Copy address", "New code". Commands `remote_status`, `start_remote`, `stop_remote`, `renew_remote_code` (refused on Android). Preview: `?route=settings&tab=app&remote=1`. "Accept handoffs" switch on the same server: next section.
- **Address given to the phone** (`jam/lan.rs`, #425, local Jam as well as remote): the default route (UDP `connect`) gives the tunnel's address when a VPN is active (measured with ProtonVPN/WireGuard: `10.2.0.2` instead of `192.168.1.105`, server reachable on `0.0.0.0` all the same). On Windows, `GetAdaptersAddresses` lists the adapters: private IPv4 address of an active adapter **with a gateway**, excluding tunnels (types 23, 24, 53 = WireGuard, 108, 131); Hyper-V / WSL adapters without a gateway are ruled out by themselves. The default route is kept if it is among the candidates, otherwise the lowest metric, otherwise the default route. Elsewhere (Linux), default route only. On the VPN side, incoming local network traffic must still be allowed (ProtonVPN's "Allow LAN connections"). Check on a machine: `cargo test lan_ip_here -- --ignored --nocapture`.

## Playback handoff (#414, 0.5.66, desktop ↔ Android)

"Resume here" on the phone: the PC's playback moves to the phone, the PC pauses. "Continue on the computer": the reverse. **The issue's choice** (2026-11-13): local network through the remote's server rather than through the relay (no new protocol, no permanent connection to the relay, the relay does not see the queue; the relay can carry the same `Handoff` later); **the phone always acts** (client), the PC stays the server: Android cuts an app's network with the screen off, and a "Continue on the phone" on the PC side would require unlocking the phone anyway.

- **What travels** (`player/handoff.rs`): `Handoff { queue, position, tracks }` = the `Queue` as persistence writes it (context, order, manual queue, history, repeat, shuffle, "Playing from" source), the position and the metadata of the current track, the manual queue and the next 100 tracks (the others are read when they are played). **Never a stream URL**: the device that takes over requests its own. `Cmd::TakeHandoff` returns the snapshot **then pauses** in the same actor round (TIDAL limits simultaneous playback per account); `Cmd::ApplyHandoff` replaces the queue, invalidates the preload and loads the current track at the received position.
- **Received queue checked** (`player/queue/check.rs`, `Queue::received`): the actor indexes `context[order[pos]]` without rechecking, a malformed queue would make it panic. Current track required, `order` = permutation of `0..context.len()`, `pos` within `order`, 20,000 context tracks and 2,000 manual queue tracks at most, history reduced to 500, source cleaned (`PlaySource::sanitize`), played format (#524, optional `format`, not sent when unknown) dropped if its quality is not one this version knows or its codec is odd (`PlayFormat::sanitize`), the listen kept; finite and positive position, 2,500 metadata entries at most (`Handoff::received`).
- **PC** (`jam/remote/api/handoff.rs`): `POST api/handoff/take` (JSON snapshot, 409 `idle` if nothing plays) and `POST api/handoff/give` (body = `Handoff`, 400 `body` if inconsistent) on the remote's server, same owner code and same limits (`Action::Command`). **Separate switch** "Accept handoffs" (setting `remote.handoff`, command `set_handoff_accepted`): the server runs if the remote **or** handoffs are on (`Features`, `Owner::set_features`); handoffs alone = the remote's page, state and commands answer 404, only `join` answers; handoffs refused = 403 `handoff`. `RemoteStatus::remote` / `handoff`; `start_remote` / `stop_remote` now return `RemoteStatus | null`. "Copy address" copies `url#code`, like the QR code.
- **Large bodies**: `give` exceeds the 2 KiB of the other routes (a 2,000-track playlist is about 30 KiB). `Site::large_body(path)` allows it route by route, up to 4 MiB (`http::MAX_LARGE_BODY`), and **the code is checked from the header before reading the body** (a wrong code counts as a failed attempt; connection closed without an answer).
- **Phone** (`src-tauri/src/handoff/`: `mod.rs` for the link, `transport.rs` for the calls and refusal messages, `credentials.rs` for the secrets manager; `commands/handoff.rs`): link entered once in Settings › Application › Linked computer (`LinkedComputerPanel.svelte`): address and code typed by hand (`192.168.1.20:47801 XXXX-XXXX-XXXX`, `http://` optional) or `url#code` pasted (`Link::parse`, tested); checked through `join` before being kept in the **secrets manager** (`keyring`, entry `seaglass/handoff-link`, Keystore on Android): the code gives control of the PC's playback. `reqwest` client without proxy, 4 s to connect, 20 s per request. `push` pauses, sends, and **resumes playback here if the PC refuses**. Messages per refusal (`refusal`: code refused, handoffs not accepted, nothing playing, PC too old = 404). Commands `linked_computer`, `link_computer`, `unlink_computer`, `handoff_pull`, `handoff_push`. UI: `.handoff-open` button (`devices` icon) in `.now-actions` of "Now playing" on Android when a computer is linked, which opens a menu with both actions; also in Settings (without a current track, "Now playing" is not reachable). Store `lib/stores/handoff.svelte.ts`.
- **Tests**: `cargo test handoff` (received queue, link, routes actually served, phone client against the real server: `the_phone_client_talks_to_the_server`). Preview: PC `?route=settings&tab=app&handoff=1` (handoffs only, without QR code); phone `?route=settings&tab=app&platform=android` (link), `?platform=android&linked=1&nowplaying=1` ("Now playing" button).
- **Not yet tried** between the real PC and the S21.

## Synced listening history (#430, 0.5.68, desktop ↔ Android)

Stats, recap, "Played in Seaglass" and smart playlists see the listens of both devices. **The issue's choice** (2026-11-13): **local** clearing only; going **through the relay too** was requested, done in two steps: local network first (this version), relay next.

- **Identity of a listen**: (track, timestamp in ms), without a constraint set on existing data: the merge inserts `WHERE NOT EXISTS` (index `plays_track`). Resending a batch duplicates nothing. Column `plays.device` (migration in `plays::migrate`): origin device of a received listen, `NULL` = played here; device identifier drawn once (setting `device.id`, UUID v4 format).
- **Order**: the "most recent" rankings (`recent_albums`, `top_albums`, `top_tracks`, artists) sort by `MAX(played_at)` and no longer by `MAX(id)` (a received listen has a recent id but an old date), `MAX(id)` as tie-breaker; pruning at 50,000 keeps the most recent **by date** (`COUNT(*)` then `ORDER BY played_at DESC … OFFSET`).
- **Protocol** (`handoff/history.rs`, `store/sync.rs`, tests): `POST api/plays/sync` on the remote's server, same code and same limits (`Action::Command`), served if "Accept handoffs" is on (403 `handoff` otherwise), large body allowed (`Site::large_body`). The phone sends `{device, since, plays}`: its own listens (`device IS NULL`) after its send cursor, in batches of 1,000 (`PlayBatch`: listens + `Track` / `AlbumSummary` records, about 1 MB); the PC merges and answers `{device, cursor, more, plays}` with its listens after `since`, **except those that came from this phone** (several phones see each other through the PC). Received records do not replace local ones (`INSERT OR IGNORE`).
- **Cursors**: `plays.id` values (AUTOINCREMENT: never reused, even after "Clear"; clearing therefore stays local, nothing comes back). Kept **on the phone only** (setting `history.sync`: `peer`, `pulled`, `pushed`, `syncedAt`); the PC remembers nothing. PC identifier changed (reinstalled) = cursors reset, everything goes through again and is deduplicated. 100 exchanges at most per sync.
- **Checking** (`PlayBatch::received`, `SyncRequest::received`): 1,000 listens at most, no more records than listens, device in UUID format, date between 0 and now + 1 day, duration from 0 to 7 days, ids within `i64`, artist name cut at 300 characters, source cleaned (`PlaySource::sanitize`); an invalid listen is discarded, a batch that is too big refused (400 `body`).
- **When** (always the phone, `handoff::history::sync_now`, one sync at a time): 5 s after launch, right after linking the computer, after "Resume here" / "Continue on the computer", when opening stats and recap (skipped if the last one was less than 30 s ago), and the "Sync" button in Settings › Application › Linked computer (`.handoff-history`, date of the last sync, `LinkInfo::syncedAt`). Automatic failures only logged (PC off or elsewhere). Command `sync_history(force)`. Added listens emit `history-synced` (count) **on both sides**: `watchHistory` (`lib/stores/handoff.svelte.ts`) reloads the home page, stats and recap.
- **Tests**: `cargo test sync` and `cargo test history` (merge, cursors, local clearing, checking, route actually served and phone ↔ server convergence over more than one batch: `the_phone_and_the_computer_converge`). Preview: `?route=settings&tab=app&platform=android&linked=1`.
- **Not yet tried** between the real PC and the S21.
- **Step 2, relay** (0.5.69): next section.

## Handoff and history through the relay (#430, 0.5.69)

Outside the local network, the phone reaches its computer through the Jam relay, **end-to-end encrypted** (the user's choice, 2026-11-13): the relay reads neither the history nor the transferred queue.

- **Key**: random, 256 bits, drawn by the PC (not derived from the link code: 60 bits, attackable offline by whoever sees the traffic). The PC also draws its tunnel's identifier and secret (128 bits each). All three are kept with the remote's settings (`remote.tunnel`, `TunnelSettings`, drawn on first activation or at launch for older settings). "New code" also changes the key: an unlinked phone no longer gets through.
- **Encryption** (`handoff/sealed.rs`, tested): ChaCha20-Poly1305 from `aws-lc-rs`, added as a direct dependency but already compiled as rustls's provider (same features, nothing more to compile). Random 96-bit nonce per packet; packet = base64(nonce ‖ ciphertext ‖ tag). Associated data: direction and tunnel identifier, plus the request's nonce for a response. The relay therefore cannot modify a packet, replay a response on another request, or send a request back as a response. The plaintext request contains its date, the path, the owner code and the body: the PC refuses a date off by more than 5 min and a nonce already seen (`Replay`, 4,096 nonces at most).
- **Relay** (`relay/src/devices.rs`, `device.rs`, tests `relay/tests/devices.rs`): `GET /device` over WebSocket (same build key as `/host`), `hello {id, secret}` → `ready {url}` or `error`. The tunnel only exists during the connection: nothing is created or kept. The same PC coming back (same secret) replaces its old connection; another secret is refused ("identifier already in use"). `POST /d/<id>`: opaque packet forwarded as `request {rid, client, body}`, response `response {rid, status, body}` sent back as is; 404 `offline` if the PC is not connected. Limits: 200 tunnels, 3 per address, 120 calls per minute per address, 8 MiB body (separate route, Jams keep 2 KiB), 4 MiB messages from the PC (12 MiB until 2026-11-25; largest measured: about 2.4 MiB, a handoff at the limits the phone accepts), answer awaited for 30 s. **Relay to redeploy.** Since the 2026-11-25 audit: bodies are read by the handlers (`read_body` in `relay/src/lib.rs`) only **after** the rate limit and the Jam or device lookup, never by an `axum` extractor (it buffered up to 8 MiB before any check, in a 128 MiB container); phone packets in memory share a 16 MiB budget (`Relay::device_uploads`, reserved from `Content-Length`, the maximum without one, 503 `busy` beyond, which the phone treats as an unreachable PC); a declared or actual body over the limit gets 413 `too_large` unread. Every per-address limit counts an IPv6 client by its **/64** (`limits::network`, applied in `client_ip`, also the address passed to the host): a provider hands out at least a /64, whose addresses would otherwise each get their own limits, or fill the 50,000-address tables. **A PC's connection is only read while its phone awaits an answer** (`Device::awaits_answer`, `device::run`), and with one of 4 read slots shared by all PCs (`Relay::device_reads`), kept until the next complete message: a PC can no longer make the relay hold messages nobody asked for (before, 200 tunnels × 12 MiB). What it sends meanwhile waits in the socket buffer. A slot held 60 s without a complete message closes the connection (a live PC answers the relay's pings every 20 s). Trade-off: an idle connection is no longer read, so a PC that died silently stays attached until a ping cannot be written, or until it comes back and replaces it; meanwhile its phone gets 503 `busy` after 30 s rather than 404 `offline` at once. The memory sum is written above `DEVICE_READ_SLOTS` in `relay/src/lib.rs` (about 85 MiB of the container's 128).
- **PC** (`jam/remote/tunnel.rs`): tunnel open as long as "Accept handoffs" is on and a relay is usable (`Running::sync_tunnel`, `RelayConfig::current()`, #452). Reconnection from 1 s to 30 s, 10 min after a refusal (build key, identifier taken, relay without `/device`). Each packet is decrypted then served by `Owner::api`, the same code as on the local network (code, limits per address as seen by the relay, permissions); **only the phone's routes** get through (`join`, `handoff/…`, `plays/…`), never the page or the remote's commands. Unreadable packet = 403 `key` at the relay level, without serving anything.
- **Path learned on the local network**: `POST api/relay` (owner code, handoffs accepted) → `{url, key}`, 404 `relay` as long as the tunnel is not open; never served through the tunnel. **Pairing window** (0.5.118, #62): only answered for `PAIRING_WINDOW` (10 min) after "Link a phone" (`open_handoff_pairing`, `Owner::open_pairing`), otherwise 403 `pairing`. The owner code travels in clear on the local network (plain HTTP, header and stream query string): without the window, whoever read it once could fetch the tunnel key at any time and reach the handoff and history routes from anywhere. "Link a phone" also draws a **new tunnel key** (same identifier and secret: `RemoteState::open_pairing` → `replace_tunnel`, the tunnel reconnects under the same address), so a key read before stops working at the next pairing; phones linked in the same window share it, phones linked before keep the local network and get 403 `key` through the relay ("code refused: link the computer again") until linked again during a window. The panel shows the window's end (`RemoteStatus::pairingUntil`), and only offers the button and these texts when a relay is set up (`RemoteStatus::relay`, `RelayConfig::current()` read at each status): without one, linking on the local network works at any time and the old instruction is shown. Phones from before 0.5.118 treat the 403 like "no route" and keep the link. Ruled out: a new key per request of the route (two phones linked in a row would cancel each other), TLS on the local network (the browser remote page would show a certificate warning). The phone requests it when linking the computer and on each sync as long as it does not have it, and keeps it in the secrets manager (`seaglass/handoff-relay`, next to the link; "Unlink" clears both). Settings › Linked computer shows "Also reachable away from home" (`LinkInfo::online`).
- **Phone** (`Link::post`): local network first, then the relay if the PC does not answer there (connection refused or 4 s). After a success through the relay, the following calls go there first (`PREFER_RELAY`, until the next launch or a failure), otherwise each call would wait 4 s. Through the relay: 10 s to connect, 45 s per call. 403 from the relay (stale key) = "code refused: link the computer again".

In `relay/`: `cargo test` (3 MB packet round trip, PC absent, secret).
