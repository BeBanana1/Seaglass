# Jam (#25)

Notes d'implémentation de Seaglass, lues à la demande (index dans [`CLAUDE.md`](../CLAUDE.md)). Le relais est une crate à part (`relay/`, déploiement dans `relay/README.md`).

## Historique par étape

Notes chronologiques : une étape plus récente l'emporte sur une plus ancienne. En particulier, le relais laisse **30 min** à l'hôte pour revenir depuis la 0.4.85 (5 min avant), et les mesures de l'étape 4 datent du délai de 5 min. Les limites par adresse et le blocage jusqu'à la fin de la Jam décrits dans les premières étapes ont été remplacés en 0.4.116 (#256, dernière entrée).

- **Jam locale** (0.4.79, #25, étape 1, bureau seulement ; `src-tauri/src/jam/`, tests) : des invités sur le même réseau ajoutent des titres à la file depuis leur navigateur, sans app ni compte ; seule la machine de l'hôte lit. Choix de l'issue : pas de connexion aux comptes des invités (jetons d'autrui, autres catalogues).
- **Serveur** (`server.rs`, HTTP écrit à la main dans `http.rs` comme `mpv::serve`, aucune dépendance) sur `0.0.0.0:47800` (sinon un port libre), adresse locale = interface de la route par défaut (`lan_ip` : `connect` UDP, rien n'est envoyé) ; requête de 8 Kio, corps de 2 Kio, 5 s pour lire et écrire, 15 s pour TIDAL, 32 connexions. Windows demande l'autorisation du pare-feu au premier démarrage.
- **Page** (`jam/page/`, `include_str!`) : `index.html`, `jam.js` (tout en `textContent`), `jam.css`, CSP stricte (`img-src https://resources.tidal.com`), français / anglais selon `navigator.language`, code gardé dans `localStorage`.
- **API** (POST JSON, code dans l'en-tête `X-Jam-Code`, qui impose aussi une requête CORS préalable que le serveur ignore : pas d'appel depuis un autre site) : `join`, `search` (titres seulement, 30, compte de l'hôte), `add` (fin de la file manuelle, `Cmd::AddToQueue`, prénom facultatif), `state` (titre en cours et 20 titres de la suite).
- **Garde-fous** (`guard.rs`, logique pure) : code de 6 caractères sans 0/O/1/I tiré à chaque Jam, comparé en temps constant ; 10 essais ratés = adresse bloquée jusqu'à la fin de la Jam (un quart d'heure depuis #256) ; 60 recherches (30 en 0.4.79) et 10 ajouts par minute et par adresse ; seuls les titres sortis des recherches de la Jam peuvent être ajoutés ; erreurs de l'app journalisées, la page ne reçoit qu'un type d'erreur. Commandes `jam_status`, `start_jam` (→ `JamStatus`), `stop_jam` (`JamState`, tâche annulée = port fermé, code invalide). UI : Réglages › Application › Jam (`.jam-fields`, `.jam-code`, boutons `.update-check`). Aperçu : `?route=settings&tab=app&jam=1`. Testée sur un vrai téléphone par l'utilisateur (étape 1, jugée peu réactive).
- **Étape 2** (0.4.81) : **QR code** (crate `qrcode`, feature `svg`, `JamStatus::qr_svg` sans la déclaration XML, inséré par `{@html}` dans `.jam-qr` sur fond blanc) de `url#code` : le code après `#` n'atteint jamais le serveur, la page le lit puis le retire de l'adresse (`history.replaceState`). **Prénom** facultatif (`guests.rs` : 24 caractères, contrôles retirés, 500 titres retenus, le dernier invité l'emporte), envoyé avec l'ajout ; gardé dans le module Jam, en mémoire, **pas dans la file du lecteur** (persistée, sans notion d'invité) : `JamStatus::guests` + événement `jam-guests` → `lib/stores/jam.svelte.ts` (`guestOf`) → `TrackRow` `addedBy` (`.added-by`, file manuelle de `QueueList`) ; la page montre aussi « ajouté par ». **État en direct** : `GET /api/events?code=…` (Server-Sent Events, `EventSource` ne pose pas d'en-tête, d'où le code en query), 64 flux au plus hors des 32 connexions ordinaires, commentaire toutes les 20 s ; `push_loop` relit le lecteur toutes les secondes **seulement si une page écoute** et aussitôt après un ajout ou une nouvelle page, n'envoie que si le JSON change (`watch::send_if_modified`) ; l'émetteur vit dans `serve` : Jam arrêtée = flux fermés. Page : recherche pendant la saisie (400 ms, réponses périmées ignorées, 60 recherches par minute), « Recherche… », ✓ affiché aussitôt et annulé sur refus. Aperçu : `?route=settings&tab=app&jam=1&manual=1&queue=1` (QR factice, « ajouté par Léa »).

- **Limites par invité et plafond de la file** (0.4.116, #256, relevé par l'audit du 2026-11-10) : en données mobiles (IPv4), plusieurs invités sortent souvent par la même adresse. **Limites** (`guard.rs`) : chaque action est comptée pour l'invité (clé `owner_key` : jeton du navigateur, sinon `ip:<adresse>`) aux seuils d'avant (10 ajouts, 60 recherches, 6 lecture / pause, 30 retraits par minute) **et** pour l'adresse à 5 fois ces seuils (`IP_FACTOR`) ; une action n'est comptée que si les deux la permettent (un refus de l'adresse ne pèse pas sur l'invité). Le jeton n'est pas une identité forte : le plafond par adresse reste la borne ; les invités et adresses inactifs depuis une minute sont oubliés quand leur table est pleine (4096 invités, 1024 adresses), des jetons tirés à la volée ne la remplissent donc pas. **Essais ratés** : 10 codes faux par quart d'heure et par adresse (`FAILURE_WINDOW`), dans l'app et dans le relais (flux d'état), au lieu d'un blocage jusqu'à la fin de la Jam ; page : « Trop d'essais : réessayez dans un quart d'heure ». Le code se tente par adresse, pas par jeton (sinon un jeton neuf par essai). **Plafond de la Jam** (`rules::MAX_JAM_PENDING`) : 100 titres venus de la Jam en attente dans la file manuelle, tous invités confondus (`Guests::pending_total`) ; un album est coupé à la plus petite place (invité ou Jam), refus 429 `queue` (« La file de la Jam est pleine »), qui passe avant la limite de l'invité. Avec ce plafond, les 500 titres retenus par `guests.rs` ne débordent sur des titres encore en attente que si l'hôte en lit plus de 400 autres de la Jam avant eux. **Page** : code rangé par Jam (`seaglass-jam-code:<chemin>`, `/j/<id>/` sur le relais, `/` en local), l'ancienne clé commune est retirée : un ancien code ne gâche plus un essai sur une nouvelle Jam. **Relais** : 300 appels par minute et par adresse (120 avant). Relais **à redéployer** (page embarquée, limites).
- **Reprise et plafond par adresse** (#253, #257, relais seulement, à redéployer) : `Registry::resume` accepte la reprise avec le bon secret même si une connexion d'hôte est encore branchée. Avant, un téléphone qui changeait de réseau revenait en 1 s environ alors que le relais ne voyait la coupure qu'au bout de 60 à 80 s (`IDLE_TIMEOUT`) : reprise refusée, nouvelle Jam, nouvelle adresse et nouveau QR code. `Jam::attach` remplace l'ancienne connexion (son émetteur disparaît, ce qui la termine ; `host_gen` l'empêche de détacher la nouvelle) et fait échouer aussitôt ses requêtes en attente (« offline »). Tests : `a_host_resumes_while_its_old_connection_is_still_open`, `one_address_cannot_fill_the_relay` (`relay/tests/relay.rs`). Pas encore essayé sur un vrai changement de réseau du S21.

## Télécommande (#336, 0.5.39, bureau)

Piloter le lecteur du PC depuis le navigateur d'un téléphone, sur le réseau local. Module `jam/remote/` : réutilise le serveur de la Jam, mais **sur un autre port** (47801, sinon un port libre) plutôt que sur celui d'une Jam, contrairement à la proposition de l'issue : la télécommande doit tourner sans Jam et d'un lancement à l'autre, et deux serveurs séparent les droits par construction.

- **Serveur commun** : `server.rs` sert un `Site` (fichiers de la page, `check_code`, `api`, `state_json`, `refresh`) ; `JamSite` (Core + Backend de la Jam) et `RemoteSite` (`Owner` + `Remote`) le branchent. Le serveur de la Jam répond 404 aux commandes de la télécommande et à `remote.js` (test `guests_never_reach_the_owner_commands`) ; un code de Jam ou un code voisin n'ouvre rien sur la télécommande (`only_the_owner_code_opens_the_remote`).
- **Code de propriétaire** : 12 caractères de l'alphabet de la Jam (`guard::code_of_len`, 60 bits), comparé en temps constant, casse et tirets ignorés (affiché `XXXX-XXXX-XXXX`), 10 essais ratés par quart d'heure et par adresse (`Limits`). Gardé dans SQLite avec l'interrupteur (réglage `remote` : `enabled`, `code`, code abîmé remplacé) plutôt que dans le gestionnaire d'identifiants : il ne donne que le contrôle du lecteur depuis le réseau local et s'affiche en clair dans l'app. « Nouveau code » (`renew_remote_code`, `Owner::set_code`) refuse aussitôt l'ancien ; la page revient alors à l'écran du code.
- **API** (`remote/api.rs`, POST, en-tête `X-Jam-Code`) : `join`, `state`, `pause {paused}` (explicite), `next`, `previous`, `seek {seconds}`, `volume {level}` (0–100, `Volume::validate`), `mute {muted}`, `shuffle {enabled}`, `repeat {mode}`, `jump {part, index, trackId}` (`Cmd::PlayFromQueue`), `remove {trackId}` (file manuelle, `RemoveFromQueueIds`), `play {trackId}`, `enqueue {trackId, next}`, `play-album {albumId, shuffle}`, `play-playlist {uuid, shuffle}` (uuid vérifié par `is_uuid`, source « Joué depuis » posée), `search {query}` (30 titres, 20 albums, 20 playlists, filtre du contenu appliqué), `playlists` (bibliothèque, lecture seule). **Rien n'écrit dans le compte.** L'API produit une `Command` (enum testable) traduite en `Cmd` par `to_cmd` : un `Cmd` détruit dans un test casse le binaire de test Windows (`docs/android.md`). Limites : 120 commandes par minute (`Action::Command`), 60 recherches (`Action::Search`).
- **État poussé** (`/api/events`, comme la Jam) : `RemoteView` (titre, pause, chargement, position en secondes entières, durée, volume, sourdine, aléatoire, répétition, 50 titres de la file manuelle et de la suite). La position change chaque seconde en lecture : un envoi par seconde tant qu'une page écoute ; la page interpole entre deux.
- **Page** (`remote/page/` : `index.html`, `remote.js`, `remote.css`, plus `jam.css` servi aussi) : lecteur collant en haut (curseurs de position et de volume envoyés au relâchement), onglets File / Rechercher / Playlists, icônes de l'app (`Icon.svelte`) en SVG dans la page, code dans `localStorage` (`seaglass-remote-code`), QR code `url#code` comme la Jam. **Aperçu** avec un faux lecteur : `cargo test remote_page_preview -- --ignored --nocapture`, puis `http://127.0.0.1:47899/#AB23CDEF45GH` (30 min).
- **UI** : Réglages › Application › Télécommande (`components/RemotePanel.svelte`, bureau seulement) : interrupteur `.setting-switch` (retenu, rallumé au lancement par `commands::remote::restore`), QR code, adresse, code, « Copier l'adresse », « Nouveau code ». Commandes `remote_status`, `start_remote`, `stop_remote`, `renew_remote_code` (refusées sur Android). Aperçu : `?route=settings&tab=app&remote=1`. Interrupteur « Accepter les transferts » sur le même serveur : section suivante.
- **Adresse donnée au téléphone** (`jam/lan.rs`, #425, Jam locale comme télécommande) : la route par défaut (`connect` UDP) donne l'adresse du tunnel quand un VPN est actif (mesuré avec ProtonVPN/WireGuard : `10.2.0.2` au lieu de `192.168.1.105`, serveur pourtant joignable sur `0.0.0.0`). ## Transfert de la lecture (#414, 0.5.66, bureau ↔ Android)

« Reprendre ici » sur le téléphone : la lecture du PC passe sur le téléphone, le PC se met en pause. « Continuer sur l'ordinateur » : l'inverse. **Choix de l'issue** (2026-11-13) : réseau local par le serveur de la télécommande plutôt que par le relais (pas de nouveau protocole, pas de connexion permanente au relais, le relais ne voit pas la file ; le relais pourra porter le même `Handoff` plus tard) ; **le téléphone agit toujours** (client), le PC reste serveur : Android coupe le réseau d'une app écran éteint, et un « Continuer sur le téléphone » côté PC demanderait de toute façon de déverrouiller le téléphone.

- **Ce qui voyage** (`player/handoff.rs`) : `Handoff { queue, position, tracks }` = la `Queue` telle que la persistance l'écrit (contexte, ordre, file manuelle, historique, répétition, aléatoire, source « Joué depuis »), la position et les métadonnées du titre courant, de la file manuelle et des 100 titres suivants (les autres sont lus au moment de les jouer). **Jamais d'URL de flux** : l'appareil qui reprend redemande les siennes. `Cmd::TakeHandoff` renvoie l'instantané **puis met en pause** dans le même tour de l'acteur (TIDAL limite la lecture simultanée par compte) ; `Cmd::ApplyHandoff` remplace la file, invalide le préchargement et charge le titre courant à la position reçue.
- **File reçue vérifiée** (`player/queue/check.rs`, `Queue::received`) : l'acteur indexe `context[order[pos]]` sans revérifier, une file mal formée le ferait paniquer. Titre courant obligatoire, `order` = permutation de `0..context.len()`, `pos` dans `order`, 20 000 titres de contexte et 2 000 de file manuelle au plus, historique ramené à 500, source nettoyée (`PlaySource::sanitize`) ; position finie et positive, 2 500 métadonnées au plus (`Handoff::received`).
- **PC** (`jam/remote/api/handoff.rs`) : `POST api/handoff/take` (instantané JSON, 409 `idle` si rien ne joue) et `POST api/handoff/give` (corps = `Handoff`, 400 `body` si incohérent) sur le serveur de la télécommande, même code de propriétaire et mêmes limites (`Action::Command`). **Interrupteur à part** « Accepter les transferts » (réglage `remote.handoff`, commande `set_handoff_accepted`) : le serveur tourne si la télécommande **ou** les transferts sont activés (`Features`, `Owner::set_features`) ; transferts seuls = page, état et commandes de la télécommande en 404, seul `join` répond ; transferts refusés = 403 `handoff`. `RemoteStatus::remote` / `handoff` ; `start_remote` / `stop_remote` renvoient désormais `RemoteStatus | null`. « Copier l'adresse » copie `url#code`, comme le QR code.
- **Gros corps** : `give` dépasse les 2 Kio des autres routes (une playlist de 2 000 titres fait environ 30 Kio). `Site::large_body(path)` l'autorise route par route, jusqu'à 4 Mio (`http::MAX_LARGE_BODY`), et **le code est vérifié sur l'en-tête avant de lire le corps** (un code faux compte comme un essai raté ; connexion fermée sans réponse).
