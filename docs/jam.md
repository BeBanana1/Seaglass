# Jam (#25)

Notes d'implémentation de Seaglass, lues à la demande (index dans [`CLAUDE.md`](../CLAUDE.md)). Le relais est une crate à part (`relay/`, déploiement dans `relay/README.md`).

## Historique par étape

Notes chronologiques : une étape plus récente l'emporte sur une plus ancienne. En particulier, le relais laisse **30 min** à l'hôte pour revenir depuis la 0.4.85 (5 min avant), et les mesures de l'étape 4 datent du délai de 5 min. Les limites par adresse et le blocage jusqu'à la fin de la Jam décrits dans les premières étapes ont été remplacés en 0.4.116 (#256, dernière entrée).

- **Jam locale** (0.4.79, #25, étape 1, bureau seulement ; `src-tauri/src/jam/`, tests) : des invités sur le même réseau ajoutent des titres à la file depuis leur navigateur, sans app ni compte ; seule la machine de l'hôte lit. Choix de l'issue : pas de connexion aux comptes des invités (jetons d'autrui, autres catalogues).
- **Serveur** (`server.rs`, HTTP écrit à la main dans `http.rs` comme `mpv::serve`, aucune dépendance) sur `0.0.0.0:47800` (sinon un port libre), adresse locale = interface de la route par défaut (`lan_ip` : `connect` UDP, rien n'est envoyé) ; requête de 8 Kio, corps de 2 Kio, 5 s pour lire et écrire, 15 s pour TIDAL, 32 connexions. Windows demande l'autorisation du pare-feu au premier démarrage.
- **Page** (`jam/page/`, `include_str!`) : `index.html`, `jam.js` (tout en `textContent`), `jam.css`, CSP stricte (`img-src https://resources.tidal.com`), français / anglais selon `navigator.language`, code gardé dans `localStorage`.
- **API** (POST JSON, code dans l'en-tête `X-Jam-Code`, qui impose aussi une requête CORS préalable que le serveur ignore : pas d'appel depuis un autre site) : `join`, `search` (titres seulement, 30, compte de l'hôte), `add` (fin de la file manuelle, `Cmd::AddToQueue`, prénom facultatif), `state` (titre en cours et 20 titres de la suite).
- **Garde-fous** (`guard.rs`, logique pure) : code de 6 caractères sans 0/O/1/I tiré à chaque Jam, comparé en temps constant ; 10 essais ratés = adresse bloquée jusqu'à la fin de la Jam (un quart d'heure depuis #256) ; 60 recherches (30 en 0.4.79) et 10 ajouts par minute et par adresse ; seuls les titres sortis des recherches de la Jam peuvent être ajoutés ; erreurs de l'app journalisées, la page ne reçoit qu'un type d'erreur. Commandes `jam_status`, `start_jam` (→ `JamStatus`), `stop_jam` (`JamState`, tâche annulée = port fermé, code invalide). UI : Réglages › Application › Jam (`.jam-fields`, `.jam-code`, boutons `.update-check`). Aperçu : `?route=settings&tab=app&jam=1`. Testée sur un vrai téléphone par l'utilisateur (étape 1, jugée peu réactive).
- **Étape 2** (0.4.81) : **QR code** (crate `qrcode`, feature `svg`, `JamStatus::qr_svg` sans la déclaration XML, inséré par `{@html}` dans `.jam-qr` sur fond blanc) de `url#code` : le code après `#` n'atteint jamais le serveur, la page le lit puis le retire de l'adresse (`history.replaceState`). **Prénom** facultatif (`guests.rs` : 24 caractères, contrôles retirés, 500 titres retenus, le dernier invité l'emporte), envoyé avec l'ajout ; gardé dans le module Jam, en mémoire, **pas dans la file du lecteur** (persistée, sans notion d'invité) : `JamStatus::guests` + événement `jam-guests` → `lib/stores/jam.svelte.ts` (`guestOf`) → `TrackRow` `addedBy` (`.added-by`, file manuelle de `QueueList`) ; la page montre aussi « ajouté par ». **État en direct** : `GET /api/events?code=…` (Server-Sent Events, `EventSource` ne pose pas d'en-tête, d'où le code en query), 64 flux au plus hors des 32 connexions ordinaires, commentaire toutes les 20 s ; `push_loop` relit le lecteur toutes les secondes **seulement si une page écoute** et aussitôt après un ajout ou une nouvelle page, n'envoie que si le JSON change (`watch::send_if_modified`) ; l'émetteur vit dans `serve` : Jam arrêtée = flux fermés. - **Limites par invité et plafond de la file** (0.4.116, #256, relevé par l'audit du 2026-11-10) : en données mobiles (IPv4), plusieurs invités sortent souvent par la même adresse. **Limites** (`guard.rs`) : chaque action est comptée pour l'invité (clé `owner_key` : jeton du navigateur, sinon `ip:<adresse>`) aux seuils d'avant (10 ajouts, 60 recherches, 6 lecture / pause, 30 retraits par minute) **et** pour l'adresse à 5 fois ces seuils (`IP_FACTOR`) ; une action n'est comptée que si les deux la permettent (un refus de l'adresse ne pèse pas sur l'invité). Avec ce plafond, les 500 titres retenus par `guests.rs` ne débordent sur des titres encore en attente que si l'hôte en lit plus de 400 autres de la Jam avant eux. **Page** : code rangé par Jam (`seaglass-jam-code:<chemin>`, `/j/<id>/` sur le relais, `/` en local), l'ancienne clé commune est retirée : un ancien code ne gâche plus un essai sur une nouvelle Jam. **Relais** : 300 appels par minute et par adresse (120 avant). Relais **à redéployer** (page embarquée, limites).
- **Reprise et plafond par adresse** (#253, #257, relais seulement, à redéployer) : `Registry::resume` accepte la reprise avec le bon secret même si une connexion d'hôte est encore branchée. Avant, un téléphone qui changeait de réseau revenait en 1 s environ alors que le relais ne voyait la coupure qu'au bout de 60 à 80 s (`IDLE_TIMEOUT`) : reprise refusée, nouvelle Jam, nouvelle adresse et nouveau QR code. `Jam::attach` remplace l'ancienne connexion (son émetteur disparaît, ce qui la termine ; `host_gen` l'empêche de détacher la nouvelle) et fait échouer aussitôt ses requêtes en attente (« offline »). ## Télécommande (#336, 0.5.39, bureau)

Piloter le lecteur du PC depuis le navigateur d'un téléphone, sur le réseau local. Module `jam/remote/` : réutilise le serveur de la Jam, mais **sur un autre port** (47801, sinon un port libre) plutôt que sur celui d'une Jam, contrairement à la proposition de l'issue : la télécommande doit tourner sans Jam et d'un lancement à l'autre, et deux serveurs séparent les droits par construction.

- **Serveur commun** : `server.rs` sert un `Site` (fichiers de la page, `check_code`, `api`, `state_json`, `refresh`) ; `JamSite` (Core + Backend de la Jam) et `RemoteSite` (`Owner` + `Remote`) le branchent. Le serveur de la Jam répond 404 aux commandes de la télécommande et à `remote.js` (test `guests_never_reach_the_owner_commands`) ; un code de Jam ou un code voisin n'ouvre rien sur la télécommande (`only_the_owner_code_opens_the_remote`).
- **Code de propriétaire** : 12 caractères de l'alphabet de la Jam (`guard::code_of_len`, 60 bits), comparé en temps constant, casse et tirets ignorés (affiché `XXXX-XXXX-XXXX`), 10 essais ratés par quart d'heure et par adresse (`Limits`). Gardé dans SQLite avec l'interrupteur (réglage `remote` : `enabled`, `code`, code abîmé remplacé) plutôt que dans le gestionnaire d'identifiants : il ne donne que le contrôle du lecteur depuis le réseau local et s'affiche en clair dans l'app. « Nouveau code » (`renew_remote_code`, `Owner::set_code`) refuse aussitôt l'ancien ; la page revient alors à l'écran du code.
- **API** (`remote/api.rs`, POST, en-tête `X-Jam-Code`) : `join`, `state`, `pause {paused}` (explicite), `next`, `previous`, `seek {seconds}`, `volume {level}` (0–100, `Volume::validate`), `mute {muted}`, `shuffle {enabled}`, `repeat {mode}`, `jump {part, index, trackId}` (`Cmd::PlayFromQueue`), `remove {trackId}` (file manuelle, `RemoveFromQueueIds`), `play {trackId}`, `enqueue {trackId, next}`, `play-album {albumId, shuffle}`, `play-playlist {uuid, shuffle}` (uuid vérifié par `is_uuid`, source « Joué depuis » posée), `search {query}` (30 titres, 20 albums, 20 playlists, filtre du contenu appliqué), `playlists` (bibliothèque, lecture seule). **Rien n'écrit dans le compte.** L'API produit une `Command` (enum testable) traduite en `Cmd` par `to_cmd` : un `Cmd` détruit dans un test casse le binaire de test Windows (`docs/android.md`). Limites : 120 commandes par minute (`Action::Command`), 60 recherches (`Action::Search`).
- **État poussé** (`/api/events`, comme la Jam) : `RemoteView` (titre, pause, chargement, position en secondes entières, durée, volume, sourdine, aléatoire, répétition, 50 titres de la file manuelle et de la suite). La position change chaque seconde en lecture : un envoi par seconde tant qu'une page écoute ; la page interpole entre deux.
- **Page** (`remote/page/` : `index.html`, `remote.js`, `remote.css`, plus `jam.css` servi aussi) : lecteur collant en haut (curseurs de position et de volume envoyés au relâchement), onglets File / Rechercher / Playlists, icônes de l'app (`Icon.svelte`) en SVG dans la page, code dans `localStorage` (`seaglass-remote-code`), QR code `url#code` comme la Jam. **Aperçu** avec un faux lecteur : `cargo test remote_page_preview -- --ignored --nocapture`, puis `http://127.0.0.1:47899/#AB23CDEF45GH` (30 min).
- **UI** : Réglages › Application › Télécommande (`components/RemotePanel.svelte`, bureau seulement) : interrupteur `.setting-switch` (retenu, rallumé au lancement par `commands::remote::restore`), QR code, adresse, code, « Copier l'adresse », « Nouveau code ». Commandes `remote_status`, `start_remote`, `stop_remote`, `renew_remote_code` (refusées sur Android). Aperçu : `?route=settings&tab=app&remote=1`. Interrupteur « Accepter les transferts » sur le même serveur : section suivante.
- **Adresse donnée au téléphone** (`jam/lan.rs`, #425, Jam locale comme télécommande) : la route par défaut (`connect` UDP) donne l'adresse du tunnel quand un VPN est actif (mesuré avec ProtonVPN/WireGuard : `10.2.0.2` au lieu de `192.168.1.105`, serveur pourtant joignable sur `0.0.0.0`). Sous Windows, `GetAdaptersAddresses` liste les cartes : adresse IPv4 privée d'une carte active **avec une passerelle**, hors tunnels (types 23, 24, 53 = WireGuard, 108, 131) ; les cartes Hyper-V / WSL sans passerelle sont écartées d'elles-mêmes. On garde la route par défaut si elle est parmi les candidates, sinon la plus petite métrique, sinon la route par défaut. Ailleurs (Linux), route par défaut seule. Côté VPN, il faut encore laisser passer le réseau local en entrée (« Autoriser le réseau local » de ProtonVPN). Vérifier sur une machine : `cargo test lan_ip_here -- --ignored --nocapture`.

## Transfert de la lecture (#414, 0.5.66, bureau ↔ Android)

« Reprendre ici » sur le téléphone : la lecture du PC passe sur le téléphone, le PC se met en pause. « Continuer sur l'ordinateur » : l'inverse. **Choix de l'issue** (2026-11-13) : réseau local par le serveur de la télécommande plutôt que par le relais (pas de nouveau protocole, pas de connexion permanente au relais, le relais ne voit pas la file ; le relais pourra porter le même `Handoff` plus tard) ; **le téléphone agit toujours** (client), le PC reste serveur : Android coupe le réseau d'une app écran éteint, et un « Continuer sur le téléphone » côté PC demanderait de toute façon de déverrouiller le téléphone.

- **Ce qui voyage** (`player/handoff.rs`) : `Handoff { queue, position, tracks }` = la `Queue` telle que la persistance l'écrit (contexte, ordre, file manuelle, historique, répétition, aléatoire, source « Joué depuis »), la position et les métadonnées du titre courant, de la file manuelle et des 100 titres suivants (les autres sont lus au moment de les jouer). **Jamais d'URL de flux** : l'appareil qui reprend redemande les siennes. `Cmd::TakeHandoff` renvoie l'instantané **puis met en pause** dans le même tour de l'acteur (TIDAL limite la lecture simultanée par compte) ; `Cmd::ApplyHandoff` remplace la file, invalide le préchargement et charge le titre courant à la position reçue.

Titre courant obligatoire, `order` = permutation de `0..context.len()`, `pos` dans `order`, 20 000 titres de contexte et 2 000 de file manuelle au plus, historique ramené à 500, source nettoyée (`PlaySource::sanitize`) ; position finie et positive, 2 500 métadonnées au plus (`Handoff::received`).
- **PC** (`jam/remote/api/handoff.rs`) : `POST api/handoff/take` (instantané JSON, 409 `idle` si rien ne joue) et `POST api/handoff/give` (corps = `Handoff`, 400 `body` si incohérent) sur le serveur de la télécommande, même code de propriétaire et mêmes limites (`Action::Command`). **Interrupteur à part** « Accepter les transferts » (réglage `remote.handoff`, commande `set_handoff_accepted`) : le serveur tourne si la télécommande **ou** les transferts sont activés (`Features`, `Owner::set_features`) ; transferts seuls = page, état et commandes de la télécommande en 404, seul `join` répond ; transferts refusés = 403 `handoff`. `RemoteStatus::remote` / `handoff` ; `start_remote` / `stop_remote` renvoient désormais `RemoteStatus | null`. « Copier l'adresse » copie `url#code`, comme le QR code.
- **Gros corps** : `give` dépasse les 2 Kio des autres routes (une playlist de 2 000 titres fait environ 30 Kio). `Site::large_body(path)` l'autorise route par route, jusqu'à 4 Mio (`http::MAX_LARGE_BODY`), et **le code est vérifié sur l'en-tête avant de lire le corps** (un code faux compte comme un essai raté ; connexion fermée sans réponse).

Client `reqwest` sans proxy, 4 s pour se connecter, 20 s par requête. `push` met en pause, envoie, et **reprend la lecture ici si le PC refuse**. Messages par refus (`refusal` : code refusé, transferts non acceptés, rien ne joue, PC trop ancien = 404). ## Historique d'écoute synchronisé (#430, 0.5.68, bureau ↔ Android)

Les statistiques, la rétrospective, « Écoutés dans Seaglass » et les playlists intelligentes voient les écoutes des deux appareils. **Choix de l'issue** (2026-11-13) : effacement **local** seulement ; passage **aussi par le relais** demandé, fait en deux étapes : réseau local d'abord (cette version), relais ensuite.

- **Identité d'une écoute** : (titre, horodatage en ms), sans contrainte posée sur les données existantes : la fusion insère `WHERE NOT EXISTS` (index `plays_track`). Renvoyer un lot ne double rien. Colonne `plays.device` (migration de `plays::migrate`) : appareil d'origine d'une écoute reçue, `NULL` = écoutée ici ; identifiant d'appareil tiré une fois (réglage `device.id`, format UUID v4).
- **Ordre** : les classements « le plus récent » (`recent_albums`, `top_albums`, `top_tracks`, artistes) trient par `MAX(played_at)` et non plus par `MAX(id)` (une écoute reçue a un id récent mais une date ancienne), `MAX(id)` en départage ; l'élagage à 50 000 garde les plus récentes **par date** (`COUNT(*)` puis `ORDER BY played_at DESC … OFFSET`).
- **Protocole** (`handoff/history.rs`, `store/sync.rs`, tests) : `POST api/plays/sync` sur le serveur de la télécommande, même code et mêmes limites (`Action::Command`), servi si « Accepter les transferts » est activé (403 `handoff` sinon), gros corps permis (`Site::large_body`). Le téléphone envoie `{device, since, plays}` : ses propres écoutes (`device IS NULL`) après son curseur d'envoi, par lots de 1 000 (`PlayBatch` : écoutes + fiches `Track` / `AlbumSummary`, environ 1 Mo) ; le PC fusionne et répond `{device, cursor, more, plays}` avec ses écoutes après `since`, **sauf celles venues de ce téléphone** (plusieurs téléphones se voient par le PC). Les fiches reçues ne remplacent pas celles d'ici (`INSERT OR IGNORE`).
- **Curseurs** : des `plays.id` (AUTOINCREMENT : jamais réutilisés, même après « Effacer » ; l'effacement reste donc local, rien ne revient). Gardés **sur le téléphone seulement** (réglage `history.sync` : `peer`, `pulled`, `pushed`, `syncedAt`) ; le PC ne retient rien. Identifiant du PC changé (réinstallé) = curseurs remis à zéro, tout repasse et se dédoublonne. 100 échanges au plus par synchro.
- **Vérification** (`PlayBatch::received`, `SyncRequest::received`) : 1 000 écoutes au plus, pas plus de fiches que d'écoutes, appareil au format UUID, date entre 0 et maintenant + 1 jour, durée de 0 à 7 jours, ids dans `i64`, nom d'artiste coupé à 300 caractères, source nettoyée (`PlaySource::sanitize`) ; une écoute invalide est écartée, un lot trop gros refusé (400 `body`).
- **Quand** (toujours le téléphone, `handoff::history::sync_now`, une synchro à la fois) : 5 s après le lancement, juste après avoir lié l'ordinateur, après « Reprendre ici » / « Continuer sur l'ordinateur », à l'ouverture des statistiques et de la rétrospective (ignorée si la dernière a moins de 30 s), et bouton « Synchroniser » de Réglages › Application › Ordinateur lié (`.handoff-history`, date de la dernière synchro, `LinkInfo::syncedAt`). Échecs automatiques seulement journalisés (PC éteint ou ailleurs). Commande `sync_history(force)`. Des écoutes ajoutées émettent `history-synced` (nombre) **des deux côtés** : `watchHistory` (`lib/stores/handoff.svelte.ts`) recharge l'accueil, les statistiques et la rétrospective.

## Transfert et historique par le relais (#430, 0.5.69)

Hors du réseau local, le téléphone joint son ordinateur par le relais de la Jam, **chiffré de bout en bout** (choix de l'utilisateur, 2026-11-13) : le relais ne lit ni l'historique ni la file transférée.

- **Clé** : aléatoire, 256 bits, tirée par le PC (pas dérivée du code de lien : 60 bits, attaquable hors ligne par qui voit le trafic). Le PC tire aussi l'identifiant et le secret de son tunnel (128 bits chacun). Les trois sont gardés avec les réglages de la télécommande (`remote.tunnel`, `TunnelSettings`, tirés au premier allumage ou au lancement pour les réglages d'avant). « Nouveau code » change aussi la clé : un téléphone délié ne passe plus.
- **Chiffrement** (`handoff/sealed.rs`, testé) : ChaCha20-Poly1305 de `aws-lc-rs`, ajoutée en dépendance directe mais déjà compilée comme fournisseur de rustls (mêmes fonctionnalités, rien de plus à compiler). Nonce aléatoire de 96 bits par paquet ; paquet = base64(nonce ‖ chiffré ‖ étiquette). Données associées : sens et identifiant du tunnel, plus le nonce de la requête pour une réponse. Le relais ne peut donc ni modifier un paquet, ni rejouer une réponse sur une autre requête, ni renvoyer une requête comme réponse. La requête en clair contient sa date, le chemin, le code de propriétaire et le corps : le PC refuse une date décalée de plus de 5 min et un nonce déjà vu (`Replay`, 4 096 nonces au plus).
- **Relais** (`relay/src/devices.rs`, `device.rs`, tests `relay/tests/devices.rs`) : `GET /device` en WebSocket (même clé de build que `/host`), `hello {id, secret}` → `ready {url}` ou `error`. Le tunnel n'existe que pendant la connexion : rien n'est créé ni retenu. Le même PC qui revient (même secret) remplace son ancienne connexion ; un autre secret est refusé (« identifiant déjà utilisé »). `POST /d/<id>` : paquet opaque transmis en `request {rid, client, body}`, réponse `response {rid, status, body}` renvoyée telle quelle ; 404 `offline` si le PC n'est pas connecté. Limites : 200 tunnels, 3 par adresse, 120 appels par minute et par adresse, corps de 8 Mio (route à part, les Jams gardent 2 Kio), messages de 12 Mio, réponse attendue 30 s. **Relais à redéployer.**
- **PC** (`jam/remote/tunnel.rs`) : tunnel ouvert tant que « Accepter les transferts » l'est et qu'un relais est utilisable (`Running::sync_tunnel`, `RelayConfig::current()`, #452). Reconnexion de 1 s à 30 s, 10 min après un refus (clé de build, identifiant pris, relais sans `/device`). Chaque paquet est déchiffré puis servi par `Owner::api`, le même code que sur le réseau local (code, limites par adresse vue par le relais, droits) ; **seules les routes du téléphone** passent (`join`, `handoff/…`, `plays/…`), jamais la page ni les commandes de la télécommande. Paquet illisible = 403 `key` au niveau du relais, sans rien servir.
- **Chemin appris sur le réseau local** : `POST api/relay` (code de propriétaire, transferts acceptés) → `{url, key}`, 404 `relay` tant que le tunnel n'est pas ouvert ; jamais servi par le tunnel. Le téléphone le demande en liant l'ordinateur et à chaque synchro tant qu'il ne l'a pas, et le garde dans le gestionnaire de secrets (`seaglass/handoff-relay`, à côté du lien ; « Délier » efface les deux). Réglages › Ordinateur lié indique « Joignable aussi hors de chez vous » (`LinkInfo::online`).
- **Téléphone** (`Link::post`) : réseau local d'abord, puis relais si le PC n'y répond pas (connexion refusée ou 4 s). Après un succès par le relais, les appels suivants y passent d'abord (`PREFER_RELAY`, jusqu'au prochain lancement ou à un échec), sinon chaque appel attendrait 4 s. Par le relais : 10 s pour se connecter, 45 s par appel. 403 du relais (clé périmée) = « code refusé : liez de nouveau l'ordinateur ».
- **Tests** : `cargo test tunnel` et `cargo test sealed` dans l'app : chiffrement (aller-retour, clé, tunnel, octet modifié, réponse d'une autre requête), rejeu, et bout en bout avec un faux relais (`the_phone_reaches_the_computer_through_the_relay` : chemin appris sur le réseau local, `join`, transfert et 1 500 écoutes par le relais, clé périmée refusée). Dans `relay/` : `cargo test` (paquet de 3 Mo aller-retour, PC absent, secret).
- **Pas encore essayé** avec le vrai relais (à redéployer) ni entre le vrai PC et le S21 en données mobiles.
