# System integrations (desktop)

Seaglass implementation notes, read on demand (index in [`CLAUDE.md`](../CLAUDE.md)). Android's media session is in [`android.md`](android.md).

## SMTC, MPRIS, Discord, ListenBrainz, notification area, startup

- **SMTC** (`integrations/smtc.rs`): `ISystemMediaTransportControlsInterop::GetForWindow(hwnd of the main window)` on a dedicated thread (MTA). The actor notifies `Observers` on every `player-state` emitted; the thread only touches SMTC if the metadata, status or buttons change, and the timeline every 5 s or after a seek. Buttons → `Cmd::SetPaused(bool)`, `Next`, `Previous` (`try_send`, WinRT thread). Verified with the `GlobalSystemMediaTransportControlsSessionManager` API: `seaglass.exe` session, title / artist / album / thumbnail / timeline, and Play / Pause / Next / Previous drive the player.
- **Thumbnail buttons** (0.5.31, #333, `integrations/thumbbar/`, Windows): Previous / Play-Pause / Next under the taskbar thumbnail, through `ITaskbarList3::ThumbBarAddButtons`, with the `Win32_UI_Shell`, `Win32_UI_WindowsAndMessaging`, `Win32_Graphics_Gdi` and `Win32_System_Registry` features of the `windows` crate already present. Clicks arrive as `WM_COMMAND` (`THBN_CLICKED`, identifier = button index): the `main` window is subclassed through `SetWindowSubclass` (coexists with tao), set in `setup`, which runs on the window's thread; a subclass must be set from that thread. All Win32 state (`ITaskbarList3`, icons, buttons set) lives in a `thread_local` of the main thread; the `Observers::thumbbar` observer computes a view (playing, track loaded, next / previous, language; tested) and only goes through `run_on_main_thread` if it changes. `ThumbBarAddButtons` fails as long as the taskbar button does not exist (window created hidden) and only works once per button: buttons are set on the `TaskbarButtonCreated` message (`RegisterWindowMessageW`), received when shown and after an Explorer restart, then updated through `ThumbBarUpdateButtons`. Icons drawn in code (`glyphs.rs`, 4×4 antialiasing, tested), made into Win32 icons by `icons.rs`, at `SM_CXSMICON` size, white on a dark taskbar and dark gray on a light one (`HKCU\…\Themes\Personalize\SystemUsesLightTheme`), redrawn on `WM_SETTINGCHANGE` if the theme changed; the previous set is kept one round before `DestroyIcon`. `ChangeWindowMessageFilterEx` lets Explorer's messages through if the app runs as administrator. Window hidden in the notification area: no thumbnail, nothing to do. Progress in the icon (`SetProgressValue`) ruled out: it is the Windows convention for a download or copy in progress.
- **MPRIS** (0.5.6, #312, `integrations/mpris/`, Linux): the SMTC equivalent. Name `org.mpris.MediaPlayer2.seaglass` on the session bus, object `/org/mpris/MediaPlayer2`, `zbus` 5 as a direct Linux-only dependency, with its default features (`async-io`), i.e. the configuration already compiled for `tauri-plugin-opener` and `tauri-plugin-single-instance`. The `zbus` 4 in the lockfile comes from `secret-service` (`keyring`). Observer `Observers::mpris` (`watch` of `NowPlaying`, which also carries the volume); a tokio task holds the `Player` interface and only emits `PropertiesChanged` for what changes (`logic.rs`, pure logic tested on Windows too). `Position` is never signaled (specification): it is estimated on read from the last position received, and a gap of more than 1.5 s on the same track emits `Seeked`. `Changing` (loading) keeps the previous status, MPRIS only having `Playing` / `Paused` / `Stopped`. `mpris:trackid` = `/dev/seaglass/app/track/<id>`, `xesam:artist` = one entry with the artists already joined, 320 cover through its URL. Commands to the actor: `Play`/`Pause` → `SetPaused`, `PlayPause` → `TogglePause`, `Stop` → pause (no stop in the player), relative `Seek` (past the end → `Next`, before the start → 0), `SetPosition` ignored if the track changed or out of bounds, `LoopStatus` ↔ `Repeat` (`None`/`Playlist`/`Track`), `Shuffle`, `Volume` (0–1 → 0–100, 0 if muted). `Raise` shows the window again (`tray::show_main`); `CanQuit` false, `OpenUri` not supported, no `TrackList`. The logic returns `Jump` and not `Cmd`: dropping a `Cmd` in a test breaks the Windows test binary (see `android.md`). Verified in WSL on 2026-11-11 with `playerctl` and `dbus-monitor`: metadata and cover, play / pause / play-pause, absolute and relative position, next, previous, volume, repeat, shuffle, `PropertiesChanged` and `Seeked` signals. Not verified: media applet of a real desktop (GNOME, KDE) and keyboard media keys.
- **Discord presence** (0.4.92, #215, `integrations/discord/`, desktop only): no crate, Discord's local IPC written by hand (`ipc.rs`): named pipe `\\.\pipe\discord-ipc-0..9` (Unix socket `$XDG_RUNTIME_DIR/discord-ipc-<n>` elsewhere), frames `opcode u32 LE + length u32 LE + JSON`, handshake `{v: 1, client_id}` → `READY`, then `SET_ACTIVITY` (`args.pid`, `activity` or `null`), `PING` → `PONG`, `CLOSE` = connection lost; reading in a separate task, stopped with the connection (the pipe only closes with both halves, and Discord then clears the presence). Activity (`activity.rs`, pure tested logic): type 2 "Listening", `status_display_type` 1 (the artist in the member list), title in `details`, artists in `state`, 320 cover through its `https://` URL (no uploaded asset) and album as tooltip, start / end `timestamps` (progress bar), "Open in TIDAL" button (`tidal.com/browse/track/<id>`); texts cut at 128 characters, padded up to 2. Nothing when paused or stopped, previous activity kept during a load; resent only if the track or text changes, if it appears or disappears, or after a seek (start shifted by more than 2 s); at least 4 s between two sends (Discord: 5 per 20 s), the last state waits its turn. Observer `Observers::discord` (`watch` of `NowPlaying`). **Setting** `UiSettings::discord` (**off by default**), copied into a global `watch` by `apply_to_backend`; on: connection, new attempt every 15 s if Discord is closed; off: connection closed. **Identifier**: `DISCORD_CLIENT_ID` from `.env` (`build.rs` → `SEAGLASS_DISCORD_CLIENT_ID`, a variable at launch takes priority), Discord application named "Seaglass" (that name shows in "Listening to …"); without it, `discord_available` is false and Settings › Application › Discord is hidden. Tests: `cargo test discord` (fake Discord over `tokio::io::duplex`); **`cargo test live_discord -- --ignored --nocapture`** against the real Discord (running on the machine): activity accepted on 2026-11-06 (application `1568264624166535200`, answer with `type` 2, `status_display_type` 1, button and timestamps; shown for 20 s). Cover and following playback in the app not yet checked by eye. Preview: `?route=settings&tab=app&discord=1`.
- **ListenBrainz** (0.5.84, #431, `integrations/listenbrainz/`, desktop **and Android**): optional scrobbling, without an application key (user token, `Authorization: Token …`). **Token** pasted in Settings › Application › ListenBrainz (`ListenBrainzSettings.svelte`), checked through `GET /1/validate-token` before being kept in the keyring (`seaglass` / `listenbrainz`, JSON `{token, user}`); never reread by the UI or logged (`Token` without `Debug`). **The token's presence is the switch**: no setting in `UiSettings`, so nothing in the settings backup. Verified on 2026-11-18: `validate-token` answers **200 even for an invalid token** (`{"valid": false}`), valid = `valid: true` + `user_name`; `submit-listens` with a wrong token: 401; limits of 1,000 listens per request and 10,240 bytes per listen (free fields cut at 500 characters); `X-RateLimit-*` headers (`Reset-In` in seconds). **Format** (`payload.rs`, tested): `track_name` with the version in parentheses, artists joined by ", ", `release_name`, `additional_info`: `isrc`, `duration_ms`, `media_player` / `submission_client` = `Seaglass` and their versions, `music_service: "tidal.com"` (domain recognized by ListenBrainz), `origin_url: https://tidal.com/track/<id>`. **Start of a track**: `playing_now` sent from `note_listen` when the track actually plays (not paused, `ListenTracker::announce`, once per listen, again in repeat One), never during a blind test; without a queue, without waiting for the answer. **Counted listen** (rule from `player::listen`): queued in SQLite (`store/scrobbles.rs`, 10,000 at most, the oldest dropped) with `listened_at` = now − time actually listened, frozen on entry (a resent batch keeps its dates). Listens received from another device (#430) go into `plays` without going through here: never resent. Nothing is queued without an account. **Sending task**: one listen → `single`, several → `import` by 100; network, 5xx, 429 → new attempt after `X-RateLimit-Reset-In` or a growing wait (30 s to 30 min); 401/403 → token marked refused (toast, message in the settings), sending suspended until the next token, queue kept; 400/413 on a batch → retried one listen at a time, only the refused listen is removed. "Remove" forgets the token and **empties the queue**. Preview: `?route=settings&tab=app&listenbrainz=1|refused` (token containing "bad" refused). **Not yet verified** with a real account (listens visible on listenbrainz.org, MusicBrainz matching), nor on the S21.
- **Notification area** (#83, `integrations/tray.rs`, `tray-icon` feature of `tauri`): icon always created (left click = show the window, or hide it if it is visible and in front, #226: `click_hides`, tested; clicking the icon takes focus away from the window just before, so a focus loss of less than 500 ms counts as in front, `note_focus` on `WindowEvent::Focused`; menu: current track grayed out, Play/Pause, Next, Previous, Show Seaglass, Mini player, Quit), commands through `Cmd` like SMTC, menu and tooltip kept up to date as an actor observer (`Observers::tray`, texts recomputed only if the view or the language changes; labels tested). Setting `UiSettings::close_action` (`quit` by default, `tray`) in Settings › Application › Window, copied on the backend into an atomic (`apply_to_backend`, at startup and through `set_ui_settings`) and read on `CloseRequested` of `main`: `prevent_close` + `hide`, **only if the icon exists** (otherwise the app would become unreachable). Quit = `app.exit(0)` (mpv stopped, postponed update installed). Minimized start: autostart passes `--minimized`, an active `Run` entry is rewritten at launch to add it (`refresh_autostart`); the `main` window is `visible: false` in the config and shown in `setup` except with `--minimized` and an icon created. Single instance (`tauri-plugin-single-instance`, validated in #118, registered first): a second launch shows the existing window again then closes, unless it carries `--minimized` (`tray::show_on_second_launch`, tested). On Windows the plugin only pulls in `windows-sys`; `zbus` and the `async-*` crates in `Cargo.lock` are only used on Linux. Preview: `?route=settings&tab=app&tray=1`.
- **Mini player** (0.5.36, #384, `commands/mini_player.rs`, desktop): second window `mini` (`WebviewWindowBuilder`, 360 × 112 logical, no decorations or resizing, configurable `always_on_top`) that loads the same page; `main.ts` mounts `views/MiniWindow.svelte` instead of `App` when the WebView's label is `mini` (`isMiniWindow`, read from the metadata, without IPC; `?mini` in the preview). It only reads `player-state` and favorites, and only sends player commands. Only one of the two windows is visible: opening the mini player hides `main`, closing `mini` (`CloseRequested`: button, Esc, Ctrl+M, Alt+F4) shows `main` again through `tray::reveal_main`, and `tray::show_main` (icon, menu, app relaunch) closes `mini` first. Created off the main thread (`async` command, task for the icon menu): a WebView created from an event handler hangs on Windows. `mini_player` settings in SQLite: `onTop` (true by default) and physical position, kept on close and on `ExitRequested`; restored only if the top of the window falls on a screen (`reachable`, tested: unplugged screen, minimized window at -32000), otherwise bottom right corner of `main`'s screen (`corner`, tested). Capability `mini.json`: `core:default` plus `core:window:allow-start-dragging` for `data-tauri-drag-region`. The app's commands stay callable from `mini`: filtering them per window would need an app manifest listing every command, for a trusted local page. Interface zoom (#337) only applies to `main`. Double-click on the cover = back to the large window (double-clicking a drag region tries to maximize, refused for lack of permission).
- **Global shortcuts** (0.5.61, #413, `integrations/hotkeys.rs`, desktop): `tauri-plugin-global-shortcut` (2.4, `global-hotkey` 0.8 crate: `RegisterHotKey` on Windows, X11 on Linux) driven from Rust only, without a JS package or capability. Plugin added in `setup` through `app.plugin(…)` after `AppState`, not in the builder: without an X server its creation fails, and the app must not die from it (`global_shortcuts_status.available` is then false, the Settings group is hidden). Setting `UiSettings::global_shortcuts` (`commands/settings/global_shortcuts.rs`, pure tested logic): `enabled` (**off by default**) and `bindings` (action → combination `Ctrl+Alt+Space`, modifiers then `KeyboardEvent.code`, `global-hotkey`'s format); Ctrl, Alt or Super required, Shift alone refused; lenient reading (unknown action, malformed or duplicate combination left out, without losing the other settings). Combinations offered with Ctrl+Alt (unused by the app's shortcuts): Space, ←, →, ↑, ↓, L (like), S (show the window). `apply` (at startup and through `store_and_apply`) removes everything then registers each combination; a failure (taken by another app, unknown key) is kept and returned by `global_shortcuts_status.failed`, shown under the action. Actions: play/pause, next, previous → `Cmd` like SMTC; volume → `Cmd::StepVolume(±5)` (step from the level heard, `Volume::step` tested); show the window → `tray::show_main`; like → `global-shortcut` event to the UI, which runs it through its registry (`runAction("play.like")`, #412), because the favorites state lives there. `globalShortcuts` is desktop-specific in the settings backup. UI: Settings › Application › Global shortcuts (`GlobalShortcutsList.svelte`, capture in `lib/hotkeys.ts`, tested); a click on the combination waits for the next one, Esc cancels, Backspace removes, duplicate refused. A combination already registered by the app no longer reaches the page during capture (the system takes it): the action triggers instead of being captured. Verified through `cargo test hotkeys` (combinations readable by `global-hotkey`) and in the preview (`?route=settings&tab=app&hotkeys=1|taken`); **not yet verified** in the real app (keys pressed outside the window, conflict with another app), nor on Linux (Wayland: only through XWayland, to be checked).
- **Launch at startup** (#13): `tauri-plugin-autostart` driven from Rust (`autostart_enabled` / `set_autostart`), without a JS package or capability. The state is read from the registry (`HKCU\…\Run`, value `Seaglass`, and `StartupApproved\Run`), never copied into SQLite. Path = `current_exe()`: to be tested on an installed build. Known limitations: `auto-launch` tries `HKLM` first (app launched as admin), value not quoted, entry not removed on uninstall, window opened normally.

## New release notifications (0.5.85, #435)

- **Choice**: native code, without `tauri-plugin-notification`. On desktop, that plugin (notify-rust) does not report the click, and the notification must open the album or the feed. Only two more features for the `windows` crate (`UI_Notifications`, `Data_Xml_Dom`); `zbus` on Linux; Kotlin in `seaglass-mobile` on Android.
- **Detection** (`commands/feed_alerts.rs`, pure tested logic): after each read of the feed by the background task (`feed::spawn_watch`: 20 s after launch, then every 6 h), if the `releaseNotifications` setting is on (off by default, `UiSettings`, carried over by `apply_to_backend`). Kept: albums **not seen** (local feed state), dated less than 3 days ago and absent from the `feed_notified` set (SQLite setting, per account, 1,000 keys at most, same shape as `feed_seen`). Without a set for this account (first pass after turning it on, another account), it is created with the current releases **without notifying**: no burst when turned on. If it cannot be saved, nothing is notified (otherwise the same release would come back 6 h later). Feed mixes are not releases.
- **Content**: one release gives "New release" with "artist · title", and the click opens the album. Several give "N new releases" with the first three artists, and the click opens the feed. The click goes through the shared links mechanism (`link::open`: `LinkTarget` kept, `open-link` event, `take_shared_link`), now also listened to on desktop; new target `LinkTarget::Feed`.
- **Windows** (`integrations/notify/toast.rs`): WinRT `ToastGeneric` toast, escaped text, `CreateToastNotifierWithId` with the app's identifier (`dev.seaglass.app`). Windows only accepts the AUMID of a Start menu shortcut: Tauri's NSIS installer sets it on `Seaglass.lnk` (verified on 2026-11-18). Without an install, the toast is refused without error, and `pnpm tauri dev` benefits from it if the app is installed. The click arrives through `Activated` as long as the process lives (notification area included): the window is shown again (`tray::show_main`), then the page opens. Tapped later from the notification center, app closed, the toast only relaunches the app: no COM activator registered. Test: `cargo test live_toast -- --ignored`.
- **Linux** (`integrations/notify/dbus.rs`): `Notify` on `org.freedesktop.Notifications` (like `notify-send`), `default` action. The `ActionInvoked` signal is awaited until `NotificationClosed`, at most 24 h; the subscription is taken before sending.
- **Android** (`ReleaseNotifications.kt`, `notifyRelease` command of `Bridge`, without an activity): `releases` channel ("New releases", name in the app's language), a single notification at a time (id 435), small icon `notification_release` (disc silhouette). The click opens `ShareActivity` with `https://tidal.com/album/<id>` or `seaglass://feed` (internal link recognized by `link::resolve`). `POST_NOTIFICATIONS` permission declared and requested when the setting is turned on (`requestNotifications` command, Android 13+). If refused, sending fails and goes to the log. Limitation: the check only runs while the process lives (playback in progress, app open). There is no WorkManager.

## Logs and crash reports

0.5.10, #192, `logs/` (desktop and Android). Everything stays on the device: no reporting service (Sentry & co), the user copies the text into an issue.

- **Log** (`logs/file.rs`): a second `tracing_subscriber::fmt` layer (without ANSI, same `RUST_LOG` / `seaglass_lib=info` filter) writes to `seaglass.log` in Tauri's `app_log_dir` folder (`%LOCALAPPDATA%\<identifier>\logs` on Windows, `<dataDir>/logs` on Android). Opened in `setup`, right after the Keystore: earlier lines only go to standard output. At launch, the old one becomes `seaglass.old.log`; also beyond 4 MB (Android keeps the process for days). Unbuffered writing, one line per call (`panic = "abort"` in release leaves nothing in memory); a per-thread guard prevents a panic during writing from taking the lock again. **URL parameters masked** (`redact`: `https://h/p?…`): stream URLs are signed. Tokens are never logged anyway. A second launch blocked by the single instance quits before `setup` and does not rotate the first one's log.
- **Rust panics** (`logs/report.rs`): hook installed on the first call to `run`, which writes `crash.txt` (version, OS, UTC date, thread, message, location, backtrace; no symbols in release, `strip = true`) then calls the previous hook. The message also goes into the log.
- **Android** (`CrashLog.kt`, `crashSetup` command of the JNI bridge, called by `android::crash_setup` with the logs folder): handler for uncaught exceptions that writes its stack to the same `crash.txt` before Android's own; and `ActivityManager.getHistoricalProcessExitReasons` (Android 11+), which gives the last `REASON_CRASH`, `REASON_CRASH_NATIVE` (Rust panic included, `SIGABRT`) or `REASON_ANR` exit not yet seen (date of the most recent kept in `exit-seen`). Trace attached only for an ANR (64 KB at most): a native crash's trace is a binary tombstone. On the first launch of this version, an older abnormal exit still in the history is reported once.
- **Report**: at launch, `crash.txt` and/or the Android exit become `last-crash.txt`, with the last 300 lines of `seaglass.old.log` (the log of the launch that crashed). `take_crash_notice` reports it once to the UI, which shows a clickable toast (15 s) copying the report. Settings › Application › Logs: "Copy log" (last 500 lines of this launch, useful for a bug without a crash, especially on Android where the folder is inaccessible), "Copy last crash report", "Open folder" (desktop, `tauri-plugin-opener` from Rust). Copied through `navigator.clipboard` (refused in the built-in browser's preview pane, not in the app's WebView).
- **Desktop, limitations**: a native crash of the app (other than a Rust panic) or of WebView2 leaves no report, only the end of the log (Tauri does not expose `ProcessFailed`). An mpv that stops on its own leaves its exit code in the log on relaunch (`ProcessGuard::set`); its standard output stays ignored (`--no-terminal`, and an mpv log would contain the signed URLs).
- Preview: `?route=settings&tab=app&crash=1` (toast and fake report).
