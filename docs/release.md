# Installeur, mises à jour et CI

Notes d'implémentation de Seaglass, lues à la demande (index dans [`CLAUDE.md`](../CLAUDE.md)). La distribution de l'APK est dans [`android.md`](android.md).

## Installeur et mises à jour

- **Installeur** : NSIS uniquement (`bundle.targets`), installation par utilisateur (`installMode: currentUser`, pas d'admin), dans `%LOCALAPPDATA%\Seaglass`, en anglais et en français (`nsis.languages`, depuis 0.4.17 ; français seulement en 0.4.7) : NSIS prend la langue de Windows si elle est dans la liste, sinon la première (anglais). Le modèle NSIS de Tauri crée toujours le raccourci du menu Démarrer ; sa page de fin propose « Lancer » et le raccourci sur le bureau. Pas de signature Authenticode : SmartScreen avertit au premier lancement (seul remède : un certificat payant, par exemple Azure Trusted Signing). Icône (0.4.52, #126) : un vinyle dont l'étiquette est un soleil au-dessus de la mer, `src-tauri/icons/app-icon.svg`. Déclinée avec `pnpm tauri icon src-tauri/icons/icon.json` (supprimer ensuite `icons/ios`) : le manifeste ajoute l'icône adaptative d'Android, écrite directement dans `gen/android/app/src/main/res` (premier plan `app-icon-android-fg.svg`, disque réduit à 68 % pour la zone sûre ; fond blanc `app-icon-bg.svg` ; icône thématique `app-icon-monochrome.svg`). Modifier le dessin = modifier les trois SVG. Les icônes héritées (`ic_launcher.png`, Android 7) sont tirées du premier plan par Tauri et débordent un peu. **Barre des tâches et Gestionnaire des tâches** (#139) : Tauri ne pose que la petite icône de la fenêtre (`ICON_SMALL`), la grande vient de l'exe, que Windows garde dans son cache d'icônes par chemin : après un changement de logo, l'ancienne restait affichée. Hook `src-tauri/nsis/hooks.nsh` (`nsis.installerHooks`, `NSIS_HOOK_POSTINSTALL`) : `SHChangeNotify` `SHCNE_UPDATEITEM` sur l'exe puis `SHCNE_ASSOCCHANGED`. Sur un poste déjà touché : `ie4uinit.exe -show`, et désépingler / réépingler l'app. Licences livrées dans `licenses/` (GPL-3.0 de Seaglass, notice mpv). **Images** (0.4.71, #194) : `nsis.sidebarImage` (164 × 314, pages d'accueil et de fin) et `nsis.headerImage` (150 × 57), BMP 24 bits dans `src-tauri/nsis/`, générés depuis `icons/icon.png` par `python -I scripts/installer-images.py` (Pillow) : à relancer après un changement de logo.
- **mpv embarqué** : seulement au build de release, via `src-tauri/tauri.release.conf.json` (`externalBin: binaries/mpv`). Le script copie le mpv du `PATH` (ou `SEAGLASS_MPV_PATH`) en `src-tauri/binaries/mpv-x86_64-pc-windows-msvc.exe` (gitignoré, 119 Mo), **seulement s'il correspond à `scripts/mpv.lock`** (#87) : SHA-256 vérifié avant toute exécution du binaire, puis version (deux premiers mots de `mpv --version`), puis empreinte de la copie. **Copie figée** : `powershell -File scripts/update-mpv-lock.ps1` copie le mpv du `PATH` (ou `-Source`) dans `%LOCALAPPDATA%\Seaglass-build\mpv.exe`, hors de portée de l'`updater.bat` de zhongfly (build quotidienne), après confirmation (chemin, taille, date, empreinte et ancien verrou affichés) ; empreinte de la copie vérifiée, version lue sur la copie seulement, `mpv.lock` réécrit et variable utilisateur `SEAGLASS_MPV_PATH` posée sur la copie. Les releases ne cassent donc plus à chaque mise à jour de mpv : changer de mpv = le vérifier, lancer le script, commiter `mpv.lock`. Le verrou ne suit jamais tout seul le mpv installé (il ne protégerait plus de rien). Dans la config de base, `externalBin` ferait échouer tout `cargo build` sans ce fichier. Le build actuel de mpv (zhongfly, x86-64-v3) exige un processeur AVX2.
- **Mises à jour** (`src-tauri/src/updater.rs`) : vérification 20 s après le démarrage puis toutes les 6 h ; téléchargement en arrière-plan, signature vérifiée par le plugin ; événement `update-ready` → `UpdatePrompt.svelte` (« Installer et redémarrer » = `install_update`, « Plus tard » = installation sur `RunEvent::Exit`, sans relance). `on_before_exit` arrête mpv avant que l'installeur ferme l'app. Rien n'est vérifié automatiquement en debug sauf si `SEAGLASS_UPDATE_URL` est défini (aussi utile pour tester un autre manifeste). Bouton « Vérifier » dans Réglages › Application (0.4.6, #43) : `check_for_updates` lance la même vérification, sérialisée avec la tâche de fond (`UpdateState::checking`), et réémet `update-ready` si une version est prête, même déjà reportée. Il fonctionne aussi en debug (manifeste de production par défaut). **Réponse avant le téléchargement** (0.4.71, #187) : `check` rend la main dès le manifeste lu ; l'installeur (~42 Mo) se télécharge dans une tâche à part (`download`, `UpdateState::downloading`, un seul à la fois), puis `update-ready`, ou `update-failed` (message) en cas d'échec. `UpdateInfo::downloading` vrai tant que ce n'est pas fini : Réglages affiche « Version x disponible, téléchargement en cours… » puis « prête ». Aperçu : `?route=settings&tab=app&update=download`. **Linux** (0.5.8, #314) : seulement depuis une AppImage (`updater::supported` = `app.env().appimage`, validé par Tauri ; `--appimage-extract-and-run` compte, `APPIMAGE` désignant le vrai fichier). Hors AppImage, le plugin prendrait l'exécutable courant pour cible et remplacerait le binaire nu par une AppImage : pas de vérification, `updates_available` faux, et Réglages affiche « mises à jour réservées à l'AppImage » sans bouton (aperçu `?updates=manual`). Le plugin réécrit l'AppImage sans relancer : `install_update` appelle `request_restart` (file sauvegardée et mpv arrêté par `RunEvent::Exit`). Dossier non modifiable : message clair (`install_error`), mise à jour gardée pour un nouvel essai. Un manifeste sans entrée pour la plateforme (`TargetNotFound`) vaut « à jour ».
- **Signature** : clé minisign dans `%USERPROFILE%\.tauri\seaglass.key` (hors du dépôt), clé publique dans `tauri.conf.json` (`plugins.updater.pubkey`). **Perdre la clé privée** = plus aucune mise à jour acceptée par les versions installées (réinstallation manuelle) : elle doit être sauvegardée.
- **Mot de passe de la clé** (#87) : un fichier Tauri est le base64 d'une clé secrète minisign, **toujours chiffrée** (scrypt + XOR, `Sc`) ; « sans mot de passe » = mot de passe vide. Changer de clé casserait les mises à jour : on rechiffre la même avec `python -I scripts/protect-signing-key.py <clé> <nouvelle clé>` (bibliothèque standard, mots de passe au clavier sans écho, 12 caractères au moins, nouveau fichier, relu avant d'être gardé). Vérifié sur des clés jetables : signature de la clé rechiffrée acceptée par `minisign-verify` avec la clé publique d'origine. `release.ps1` teste d'abord le mot de passe vide (`--check`, mot de passe sur l'entrée standard) : clé encore sans mot de passe → avertissement et release normale ; sinon mot de passe pris dans `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, puis l'entrée générique `seaglass-signing-key` du Gestionnaire d'identifiants (facultative : `cmdkey /generic:seaglass-signing-key /user:seaglass /pass`, plus pratique mais lisible par tout programme du compte), puis saisi sans écho ; vérifié avant le build, passé à Tauri par l'environnement seulement, retiré ensuite. Session non interactive sans mot de passe → échec explicite. Sans python, pas de vérification préalable (Tauri échoue à la signature sur un mauvais mot de passe). Procédure de rechiffrement dans l'issue #87.
- **Hébergement** (en service) : le Gitea exige une connexion partout, donc l'updater ne peut pas y lire de releases. Les mises à jour sont servies par le Caddy du serveur (Docker) : `updates.bebanana.ch` (CNAME vers `bebanana.internet-box.ch`) sert `/srv/updates` en lecture seule, `latest.json` en `Cache-Control: no-cache`. Le dossier est public, les installeurs étant signés.
- **Publication** : utilisateur `seaglass-deploy` (sans mot de passe ni sudo, clé SSH avec `restrict`), alias `seaglass-updates` dans `~/.ssh/config` du PC (IP locale du serveur), `SEAGLASS_RELEASE_DEST=seaglass-updates:/srv/updates/seaglass` (variable utilisateur Windows). Après `scp`, le script remet les droits à 755 / 644 : sinon le dossier de version arrive en écriture pour tous.
- **Profil release** (0.4.53) : `lto = "thin"` sur les 16 unités de compilation par défaut, et la lib en `["cdylib", "rlib"]` (pas de `staticlib`, iOS seulement). Avant, une LTO complète sur une seule unité était refaite pour chaque type de lib (staticlib, cdylib) puis pour l'exe, sur un seul cœur : recompiler la crate Seaglass seule prenait 3 min 11 s, 1 min 01 s depuis (mesuré le 2026-11-03, `touch src/lib.rs` puis `cargo build --release`). Ne pas remettre `codegen-units = 1` ni `lto = true` sans mesurer.
- **Release** : `pnpm release` (`scripts/release.ps1`) vérifie l'arbre git, `.env`, la clé et `VERSION`, embarque mpv, lance `pnpm tauri build --config src-tauri/tauri.release.conf.json`, puis écrit `release/latest.json`, `release/<version>/Seaglass_<version>_x64-setup.exe` et la page de téléchargement `release/index.html` (modèle `scripts/download-page.html`, champs `{{…}}` échappés en HTML, nouveautés tirées des notes). Avec `-Publish`, il copie vers `SEAGLASS_RELEASE_DEST` (dossier ou cible scp) l'installeur, puis la page, le manifeste en dernier, puis pose et pousse le tag `v<version>`. Une release = un tag : pas de mise à jour à chaque push. Le `.sig` est aussi gardé dans `release/<version>/` (depuis #108). **Build de test** (arbre modifié, `-AllowDirty`) : installeur non compressé (`scripts/tauri.test.conf.json`, `compression: none`), makensis ~1 s pour 140 Mo au lieu de ~50 s pour 42 Mo en LZMA (mesuré le 2026-11-03 : zlib 14 s / 57 Mo, bzip2 10 s / 54 Mo ; LZMA gardé pour les releases, l'updater télécharge l'installeur entier depuis la connexion de la maison). Décidé sur l'arbre réellement modifié, pas sur le drapeau : un tel build n'est jamais publiable (`-PublishOnly` refuse un repère `dirty`).
- **Release complète** (`scripts/release-all.ps1`, recommandée) : `powershell -File scripts/release-all.ps1 [-Publish] [-Notes …]` construit l'installeur, l'APK puis l'AppImage Linux (`release-linux.ps1`, #313, dans WSL : voir `linux.md`, « Release ») **sans rien publier**, puis, avec `-Publish`, publie Android, Linux puis **Windows en dernier** (#314 : sa publication envoie `latest.json`, qui annonce aussi l'AppImage), pose le tag et crée une seule release Gitea avec les trois. `-SkipLinux` laisse Linux de côté (WSL ou la distribution de build absents). Un build en échec = rien en ligne. Chaque étape tourne dans son propre processus `powershell`. Alias `pnpm release:all` (0.4.52, ajouté avec un vrai changement de l'app : `package.json` compte pour le contrôle de version) ; les options suivent (`pnpm release:all -Publish`). Les trois scripts acceptent `-PublishOnly` (publie le dernier build sans le refaire) et `-SkipGiteaRelease`. Chaque build écrit un repère `release/.build/<windows|android|linux>.json` (`version`, `commit`, `dirty`, `scripts/build-stamp.ps1`) : `-PublishOnly` refuse un build d'une autre version, d'un autre commit ou d'un arbre modifié. La publication Windows ne copie plus que l'installeur et son `.sig`, pas tout `release/<version>/` (l'APK et l'AppImage y sont aussi). Ne publier jamais automatiquement (CI ou changement de `VERSION`) : les clés de signature restent sur le PC, voir « Pas de release en CI ».
- **Manifeste de l'updater** (#314, `scripts/updater-manifest.ps1`) : `release/latest.json` est écrit par une seule fonction, `Write-UpdaterManifest`, appelée par `release.ps1` et `release-linux.ps1` après leur build. Il ne décrit que la version construite, avec une entrée par plateforme dont le repère (`release/.build/<plateforme>.json`) est de cette version, de ce commit et du même état de l'arbre : `windows-x86_64` (installeur) et `linux-x86_64` (AppImage, signée avec la même clé : `scripts/signing-key.ps1`, commun aux deux scripts, transmise à WSL par `WSLENV`). Jamais d'entrée d'une version plus ancienne, que l'updater installerait. Avant d'envoyer `latest.json`, la publication Windows vérifie que chaque autre fichier annoncé est déjà en ligne (`Assert-ManifestOnline` : requête HEAD, ou fichier présent pour une destination locale), sinon elle échoue. `release-linux.ps1 -Publish` seul n'envoie pas `latest.json` : l'AppImage est téléchargeable, pas encore proposée. Testé hors ligne (Windows seul, les deux, Linux d'une autre version ignoré, refus puis acceptation du contrôle).
- **Release Gitea** (#108, `scripts/gitea-release.ps1`, appelé par `-Publish` après le tag) : release `Seaglass <version>` sur le tag avec en pièces jointes ce qui existe dans `release/` pour cette version : l'installeur, son `.sig` et `latest.json`, l'APK et `android.json`, l'AppImage, son `.sig` et `linux.json` (les fichiers publiés, rien n'est reconstruit en CI : la clé reste sur le PC). Jeton **de l'utilisateur** (pas celui de `claude` : la release est à son nom), droit `write:repository`, dans `SEAGLASS_GITEA_TOKEN` ou l'entrée générique `seaglass-gitea-token` du Gestionnaire d'identifiants (`cmdkey /generic:seaglass-gitea-token /user:seaglass /pass`) ; lecture partagée avec le mot de passe de la clé dans `scripts/credentials.ps1`. Un échec n'est qu'un avertissement (la mise à jour est déjà en ligne) : relancer `powershell -File scripts/gitea-release.ps1 [-Version x.y.z]`. Relancé, il remplace les pièces jointes du même nom. Pour une version publiée avant #108 : installeur seul (pas de `.sig` gardé), `latest.json` non joint s'il décrit une autre version, notes tirées de `git log` depuis le tag précédent ; le tag doit exister sur `origin`. Pas d'alias `pnpm` : `package.json` ferait monter la version de l'app (contrôle de la CI). Testé contre un faux serveur Gitea (création, relance, jeton absent ou refusé, serveur injoignable, ancienne version) ; pas encore contre le vrai. `[attachment] ALLOWED_TYPES` du serveur exclut `.exe`, mais les releases ont leur propre réglage (`[repository.release] ALLOWED_TYPES`, vide = tout) : si Gitea refuse l'installeur, c'est là.

## CI

- **Workflow** : `.gitea/workflows/ci.yml`, sur push vers `main` et sur chaque PR, sauf si seuls des `*.md` / `LICENSE` changent : contrôle de version, `pnpm check`, `pnpm build`, `cargo fmt --check`, `clippy -D warnings`, `cargo test`. `pnpm build` passe avant Rust car `tauri::generate_context!` exige `dist/`. Ni `.env` ni `fixtures.json` ne sont nécessaires.
- **Contrôle de version** (`scripts/check-version.sh`, checkout avec `fetch-depth: 0`) : échoue si `VERSION` est inférieure au dernier tag `v*`, ou si elle lui est égale alors que des fichiers de l'app ont changé depuis ce tag (hors `*.md`, `LICENSE`, `.gitea/`, `ci/`, `scripts/`, `spike/`, `.claude/`, `.mcp.json`, `.gitignore`, `.gitattributes`, `src/lib/mock/`, tests du frontend `src/**/*.test.ts` et `src/lib/testing/`, hors du bundle). Un changement de tests Rust seuls demande donc aussi une nouvelle version. Lançable en local : `bash scripts/check-version.sh`. Pas de publication automatique : la clé de signature reste sur le PC et l'installeur se construit sous Windows.
- **Runner dédié** (`ci/`, installation dans `ci/README.md`) : `act_runner` 0.6.1 en Docker sur le serveur, enregistré **au niveau du dépôt**, label `seaglass`. Il monte le socket Docker, donc il équivaut à root sur le serveur : ne jamais l'ouvrir à d'autres dépôts. Le runner partagé (firmware, KiCad) n'est plus utilisé.
- **Image des jobs** `seaglass-ci:<tag daté>` (`ci/Dockerfile`, base `node:24-bookworm`) : bibliothèques de Tauri, Rust stable + rustfmt + clippy, pnpm. Construite sur le serveur (`docker compose --profile build build`), sans registre (`force_pull: false`). Changer de tag = `.env` + label de `config.yaml`.
- **Cache** : les jobs rejoignent le réseau du runner (`container.network: seaglass-ci`) et le cache écoute sur un port fixe (8088). Sans ça, chaque action de cache attend 5 min un `ETIMEDOUT` (vu sur le runner partagé).
- **Limite** : sous Linux, le code `#[cfg(windows)]` (SMTC, Job Object, `CREATE_NO_WINDOW`) n'est ni compilé ni testé ; `pnpm release` le vérifie sous Windows. Du code partagé utilisé seulement par une intégration Windows doit tolérer le code mort hors Windows (`#[cfg_attr(not(windows), allow(dead_code))]`, voir `integrations/mod.rs` et `Cmd::SetPaused`), sinon clippy échoue en CI. L'IPC mpv passe par un socket Unix hors Windows (`mpv::ipc::open`).
- **Durée** : environ 7 min sur le runner partagé, sans cache (préparation ~4 min, clippy ~1 min, tests ~1 min 30). Runner dédié (2026-10-30) : 5 min sans cache (Rust ~2 min 40, sauvegarde du cache ~1 min 40), 4 min 30 au premier run de `main` (cache restauré en 35 s mais clé partielle, Rust ~1 min 15, nouvelle sauvegarde ~2 min 20). Un run dont la clé correspond exactement ne sauvegarde pas : durée en régime établi à confirmer. 2026-11-03 : runs d'environ 2 min avec le cache complet (restauration de 1,9 Go ~1 min 15, clippy 7 s, compilation des tests 18 s), mais un run est resté figé plus de 10 min sur la compilation des tests (mémoire du serveur soupçonnée). Depuis : `timeout-minutes: 20` sur le job et `CARGO_PROFILE_{DEV,TEST}_DEBUG=0` (pas d'infos de débogage : édition de liens plus légère, cache plus petit ; les variables `CARGO_*` entrent dans la clé du cache, le premier run après ce changement repart sans cache). L'API Gitea n'expose pas l'annulation d'un run (404) : annuler depuis l'interface web.
- **Mise en service** : si un job démarre sur `runner-images:ubuntu-latest` avec un réseau `…-check-network`, le runner ne lit pas `config.yaml` (conteneur lancé depuis d'anciens fichiers). Le `data/.runner` appartient à root : `sudo rm` pour réenregistrer.
- **Pas de release en CI** : la clé minisign reste sur le PC, `pnpm release` reste manuel.
- **Dépendances** (#263) : étape « Dépendances » après les tests. `pnpm audit --prod --ignore-registry-errors` (seulement ce qui part dans l'app), puis `cargo audit --no-fetch` sur `src-tauri/Cargo.lock` et `relay/Cargo.lock`, avec la base RustSec clonée à part (`git clone --depth 1`) : si elle est injoignable, l'étape avertit et passe. Elle n'échoue que sur une vulnérabilité ; les crates non maintenues, retirées ou « unsound » restent des avertissements. `cargo-audit` vient de l'image (`ci/Dockerfile`) ; sans lui, l'audit Rust est sauté avec un avertissement. Le workflow ne l'installe plus lui-même : `CARGO_HOME` est dans le conteneur (`/usr/local/cargo`), hors du cache Rust, et `cargo install` le recompilait à chaque run (1 min 44 s, le job passait de ~1 min 10 à ~3 min). Une alerte à ignorer va en `--ignore RUSTSEC-…` dans le workflow avec sa raison, jamais dans un fichier sous `src-tauri/` (il compterait pour le contrôle de version). Première passe le 2026-11-10 (cargo-audit 0.23.0) : aucune vulnérabilité sur 566 crates (app) et 92 (relais) ; 5 avertissements, tous hors de l'app Windows et Android : `proc-macro-error` (macro de compilation), `zbus_names` / `zvariant` / `zvariant_derive` (D-Bus, Linux) non maintenues, `glib` 0.18 « unsound » (GTK, Linux, tiré par Tauri). `pnpm audit --prod` : rien.
