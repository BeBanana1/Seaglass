# Installer, updates and CI

Seaglass implementation notes, read on demand (index in [`CLAUDE.md`](../CLAUDE.md)). APK distribution is in [`android.md`](android.md).

## Installer and updates

- **Installer**: NSIS only (`bundle.targets`), per-user install (`installMode: currentUser`, no admin), in `%LOCALAPPDATA%\Seaglass`, in English and French (`nsis.languages`, since 0.4.17; French only in 0.4.7): NSIS takes the Windows language if it is in the list, otherwise the first one (English). Tauri's NSIS template always creates the Start menu shortcut; its finish page offers "Launch" and the desktop shortcut. No Authenticode signature: SmartScreen warns on first launch (only remedy: a paid certificate, for example Azure Trusted Signing). Icon (0.4.52, #126): a vinyl record whose label is a sun above the sea, `src-tauri/icons/app-icon.svg`. Derived with `pnpm tauri icon src-tauri/icons/icon.json` (then delete `icons/ios`): the manifest adds Android's adaptive icon, written directly into `gen/android/app/src/main/res` (foreground `app-icon-android-fg.svg`, disc reduced to 68 % for the safe zone; white background `app-icon-bg.svg`; themed icon `app-icon-monochrome.svg`). Changing the drawing = changing all three SVGs. Legacy icons (`ic_launcher.png`, Android 7) are derived from the foreground by Tauri and overflow a little. **Taskbar and Task Manager** (#139): Tauri only sets the window's small icon (`ICON_SMALL`), the large one comes from the exe, which Windows keeps in its icon cache by path: after a logo change, the old one stayed displayed. Hook `src-tauri/nsis/hooks.nsh` (`nsis.installerHooks`, `NSIS_HOOK_POSTINSTALL`): `SHChangeNotify` `SHCNE_UPDATEITEM` on the exe then `SHCNE_ASSOCCHANGED`. On a machine already affected: `ie4uinit.exe -show`, and unpin / repin the app. Licenses shipped in `licenses/` (Seaglass's GPL-3.0, mpv notice). **Images** (0.4.71, #194): `nsis.sidebarImage` (164 × 314, welcome and finish pages) and `nsis.headerImage` (150 × 57), 24-bit BMPs in `src-tauri/nsis/`, generated from `icons/icon.png` by `python -I scripts/installer-images.py` (Pillow): rerun after a logo change.
- **Bundled mpv**: only in release builds, through `src-tauri/tauri.release.conf.json` (`externalBin: binaries/mpv`). The script copies the mpv from `PATH` (or `SEAGLASS_MPV_PATH`) to `src-tauri/binaries/mpv-x86_64-pc-windows-msvc.exe` (gitignored, 119 MB), **only if it matches `scripts/mpv.lock`** (#87): SHA-256 checked before the binary is ever run, then version (first two words of `mpv --version`), then checksum of the copy. **Frozen copy**: `powershell -File scripts/update-mpv-lock.ps1` copies the mpv from `PATH` (or `-Source`) to `%LOCALAPPDATA%\Seaglass-build\mpv.exe`, out of reach of zhongfly's `updater.bat` (daily build), after confirmation (path, size, date, checksum and old lock shown); checksum of the copy checked, version read from the copy only, `mpv.lock` rewritten and user variable `SEAGLASS_MPV_PATH` pointed at the copy. Releases therefore no longer break on every mpv update: changing mpv = checking it, running the script, committing `mpv.lock`. The lock never follows the installed mpv on its own (it would no longer protect against anything). In the base config, `externalBin` would make any `cargo build` fail without that file. The current mpv build (zhongfly, x86-64-v3) requires an AVX2 CPU.
- **Updates** (`src-tauri/src/updater.rs`): check 20 s after startup then every 6 h; background download, signature verified by the plugin; `update-ready` event → `UpdatePrompt.svelte` ("Install and restart" = `install_update`, "Later" = install on `RunEvent::Exit`, without relaunch). `on_before_exit` stops mpv before the installer closes the app. Nothing is checked automatically in debug unless `SEAGLASS_UPDATE_URL` is set (also useful to test another manifest). "Check" button in Settings › Application (0.4.6, #43): `check_for_updates` runs the same check, serialized with the background task (`UpdateState::checking`), and re-emits `update-ready` if a version is ready, even one already postponed. It also works in debug (production manifest by default). **Answer before the download** (0.4.71, #187): `check` returns as soon as the manifest is read; the installer (~42 MB) downloads in a separate task (`download`, `UpdateState::downloading`, one at a time), then `update-ready`, or `update-failed` (message) on failure. `UpdateInfo::downloading` is true until it is done: Settings shows "Version x available, downloading…" then "ready". Preview: `?route=settings&tab=app&update=download`. **Linux** (0.5.8, #314): only from an AppImage (`updater::supported` = `app.env().appimage`, validated by Tauri; `--appimage-extract-and-run` counts, `APPIMAGE` pointing to the real file). Outside an AppImage, the plugin would target the current executable and replace the bare binary with an AppImage: no check, `updates_available` false, and Settings shows "updates only available in the AppImage" without a button (preview `?updates=manual`). The plugin rewrites the AppImage without relaunching: `install_update` calls `request_restart` (queue saved and mpv stopped by `RunEvent::Exit`). Folder not writable: clear message (`install_error`), update kept for a new attempt. A manifest without an entry for the platform (`TargetNotFound`) counts as "up to date".
- **Built-in addresses** (0.5.79, #452): no service address is written in the code or in `tauri.conf.json` (no more `plugins.updater.endpoints`, optional in the plugin). `build.rs` reads `SEAGLASS_UPDATE_BASE_URL` (updates folder) and `SEAGLASS_RELAY_BASE_URL` (Jam relay) from the build environment, otherwise from `.env`, and passes them as `SEAGLASS_BUILD_*` (`cargo:rerun-if-env-changed`), read by `src-tauri/src/servers.rs`. Desktop reads `<base>/latest.json` (`updater::endpoint`, `SEAGLASS_UPDATE_URL` at launch always wins), Android `<base>/android.json` and only accepts APKs under `<base>/`. **Without a built-in address**: no check, and Settings shows neither the switch nor the button (so a `pnpm tauri dev` has none, unless the variable is set). The three release scripts set `$env:SEAGLASS_UPDATE_BASE_URL` to their `$baseUrl` before the build (#489: no default anymore, read from the environment then from `.env` by `scripts/release-env.ps1`, otherwise the script stops): the built-in address is always that of the manifests written; `release-linux.ps1` passes it to WSL through `WSLENV`. The relay comes from `.env` (with its key). **No update address configurable in the app**: the updater only accepts builds signed by the built-in key (`pubkey`, APK certificate), another server could only serve a mirror of the same builds. Whoever rebuilds with their own key also sets their own address. **Switch** "Automatic updates" (`UiSettings::auto_updates`, on by default, `servers::auto_updates` reread on every round of the background task): when off, only the periodic check stops, the "Check" button stays.
- **Signing**: minisign key in `%USERPROFILE%\.tauri\seaglass.key` (outside the repository). **Built-in public key** (0.5.91, #489): `plugins.updater.pubkey` stays empty in `tauri.conf.json` (field required by the plugin); `build.rs` reads `SEAGLASS_UPDATER_PUBKEY` (environment, then `.env`), `servers::updater_pubkey` passes it to the plugin (`Builder::pubkey`, `lib.rs`). Without it, desktop checks no update and Settings hides the section, even with an address (Android does not need it: APK certificate). `release.ps1` and `release-linux.ps1` read it from `<private key>.pub` (content as is, already base64) if the variable is missing, and Linux passes it to WSL through `WSLENV`. **Losing the private key** = no update accepted anymore by installed versions (manual reinstall): it must be backed up.
- **Key password** (#87): a Tauri file is the base64 of a minisign secret key, **always encrypted** (scrypt + XOR, `Sc`); "no password" = empty password. Changing the key would break updates: the same key is re-encrypted with `python -I scripts/protect-signing-key.py <key> <new key>` (standard library, passwords typed without echo, at least 12 characters, new file, reread before being kept). Verified on throwaway keys: signature from the re-encrypted key accepted by `minisign-verify` with the original public key. `release.ps1` first tests the empty password (`--check`, password on standard input): key still without a password → warning and normal release; otherwise the password is taken from `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, then from the generic Credential Manager entry `seaglass-signing-key` (optional: `cmdkey /generic:seaglass-signing-key /user:seaglass /pass`, more convenient but readable by any program of the account), then typed without echo; checked before the build, passed to Tauri through the environment only, removed afterwards. Non-interactive session without a password → explicit failure. Without python, no prior check (Tauri fails at signing on a wrong password). Re-encryption procedure in issue #87.
- **Taking over the project** (#489): no value specific to the author in the code or in the scripts. To publish your own versions: `tauri signer generate -w ~/.tauri/seaglass.key`, `SEAGLASS_UPDATE_BASE_URL` (public folder served over HTTPS) and `SEAGLASS_RELEASE_DEST`; for Android, your own keystore (`android.md`); for the GitHub release, `SEAGLASS_GITHUB_REPO` (environment or `.env`) and a token, or `-SkipGitHubRelease`. Step by step: [`self-hosting.md`](self-hosting.md). The rest describes the author's instance.
- **Hosting** (author's instance, #517): the updater reads its manifests from the maintainer's server, not from the forge's releases (the former Gitea required sign-in everywhere; GitHub releases only mirror the published files). Everything is served by the server's Caddy (Docker) on `seaglass.bebanana.ch` (CNAME to `bebanana.internet-box.ch`), from the read-only `/srv/updates` mount: `/updates/` = `/srv/updates/seaglass` (manifests and packages, `SEAGLASS_UPDATE_BASE_URL=https://seaglass.bebanana.ch/updates`), everything else = `/srv/updates/site` (the website). The folder is public, the installers being signed. **Single address**: the former `updates.bebanana.ch/seaglass/` was dropped without a redirect (maintainer's choice, a single user then): builds up to 0.5.100 have it built in and never see a newer version, a manual install of the next one (forge release) moves them to the new address; the APK installs over the old app (same key).
- **No authentication on that folder** (2026-11-12): the updater, the Android app and the page read the manifests without a session; a password would have to be embedded in the app, hence readable by everyone. What protects updates: the minisign signature (an installer replaced on the server is refused by the updater), the private key kept on the PC and the restricted `seaglass-deploy` account. Verified online (old domain, same setup): HTTP redirected to HTTPS (308), no directory listing (`/<version>/` gives 404).
- **Caddy block** (server Caddyfile, outside the repository), then reload Caddy (Docker: `docker exec -w /etc/caddy <container> caddy validate`, then the same with `caddy reload`; `-w` because both look for `Caddyfile` in the current folder; container name from `docker ps`, or `docker compose exec` with the service name):

  ```caddyfile
  seaglass.bebanana.ch {
      header {
          Strict-Transport-Security "max-age=31536000"
          X-Content-Type-Options "nosniff"
          Referrer-Policy "no-referrer"
          -Server
      }
      # One CSP per path, never two: the app demo (/try/, #28) is built by Vite and its Svelte
      # components write `style` attributes.
      @site_csp not path /try/*
      header @site_csp Content-Security-Policy "default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'"
      header /try/* Content-Security-Policy "default-src 'none'; script-src 'self'; style-src 'self' 'unsafe-inline'; connect-src 'self'; img-src 'self' data:; font-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'"
      handle_path /updates/* {
          root * /srv/updates/seaglass
          header /*.json Cache-Control "no-cache"
          file_server
      }
      handle {
          root * /srv/updates/site
          header Cache-Control "no-cache"
          file_server
      }
  }
  ```

  The CSP forbids inline code, styles included (`style="…"` attributes): the site build moves what Astro and Starlight inline into files (see "Website" below). `connect-src 'self'` covers the `fetch` of the manifests under `/updates/`; download links are navigations, which the CSP does not restrict. It also applies to the `.json` files and installers, with no effect on the updater or the Android app (HTTP clients, not browsers). Pages and a few files (`/download.js`, `/images/`, `/favicon.png`) keep the same names from one publication to the next, hence `no-cache` (revalidated by ETag, no stale page). `file_server` redirects `/download` to `/download/` and lists no directory. HSTS without `includeSubDomains`: the other `bebanana.ch` subdomains keep their own setting. `/try/` (the app demo) gets its own CSP, which allows inline styles (Svelte writes `style` attributes) and `data:` images (some theme effects). The two CSPs have mutually exclusive matchers: a second CSP header next to the global one would relax nothing (the browser enforces both), and overriding it inside a `handle` does not work either, because the `-Server` deletion defers the whole global `header` block, which would then overwrite the relaxed CSP when the response is written. Check: `curl -sI https://seaglass.bebanana.ch/try/` shows exactly one CSP, the relaxed one; `curl -sI https://seaglass.bebanana.ch/download/` and `curl -sI https://seaglass.bebanana.ch/updates/latest.json` show the headers, and the browser console reports no CSP blocking.
- **Website** (#517, `site/`; Astro + Starlight since GitHub #18): static site in English, its own package (`site/package.json` and lockfile, outside the app's dependencies), pages in `site/src/content/docs/` (Markdown / MDX), theme in `site/src/styles/custom.css`. `/` home page (splash template: hero, screenshots, features), `/download/` download page. **GitHub Pages ruled out**: the site shares `seaglass.bebanana.ch` with `/updates/`, whose address is built into every installed version; on Pages the download page would read the manifests cross-origin, and server-rendered pages (link previews of GitHub #14) could not run. **CSP** (no inline code): `build.inlineStylesheets: "never"` and `assetsInlineLimit: 0` in `astro.config.mjs`; after `astro build`, `site/scripts/no-inline.mjs` moves the remaining inline `<script>`s (Starlight's theme and sidebar restore, classic scripts kept synchronous) to `/_astro/inline.<hash>.js`, turns every `style="…"` into `data-sgs="<hash>"` with one generated stylesheet, moves the `data:` images of the stylesheets (Starlight and code block icons, blocked by `img-src 'self'`) to `/_astro/data.<hash>.svg`, and fails the build if anything inline is left. Pagefind search is off (`wasm-unsafe-eval`). The screenshots and the icon are copied from the repository by `site/scripts/assets.mjs` (gitignored copies: `docs/images/*.webp` → `/images/`, `src-tauri/icons/64x64.png` → `/favicon.png`, `app-icon.svg` → logo). CI builds the site (job `site`). The download page builds each platform's card in `site/public/download.js` from `/updates/windows.json` (written by `release.ps1`), `android.json` and `linux.json` (same format: `version`, `url`, `sha256`, `size`, `notes`, `pub_date`); a card stays hidden while its manifest is missing, what's new comes from `windows.json`'s notes. The site therefore never depends on a release. **Publishing**: `powershell -File scripts/publish-site.ps1` builds the site (`pnpm build` in `site/`) and copies `site/dist/` to `SEAGLASS_SITE_DEST` (environment or `.env`; author: `seaglass-updates:/srv/updates/site`, folder owned by `seaglass-deploy`), assets before pages (one `tar` stream over `ssh` per group, through `cmd`: Windows PowerShell 5.1 corrupts binary pipes between native programs), then resets permissions to 755 / 644. Files of older builds stay on the server (unreferenced hashed assets). `site/` is outside the app: no version change (version check). **App demo** (#28, `/try/`, "Try it in your browser" in the sidebar and on the home page): after the site, `publish-site.ps1` builds the app itself with its mock backend (`vite build --mode demo --base /try/`) into `site/dist/try/`, from the highest `v*` tag checked out in a temporary `git worktree` (`pnpm install` there, worktree removed afterwards), so the demo shows the downloadable version, not the work in progress; a tag without `src/lib/mock/demo.ts` falls back to the working tree with a warning, `-DemoRef <ref>` picks another reference (`HEAD` = the working tree). The build command lives in the script, so an older tag only has to know `--mode demo`. It runs after `no-inline.mjs`, which never sees the demo (its own CSP). The script fails if the demo holds `resources.tidal.com` (covers of the maintainer's fixtures). `-NoPublish` builds site and demo into `site/dist/` and stops, for the local preview; `preview.mjs` sends the `/try/` CSP like Caddy. CI builds the site without the demo. **Local preview**: `pnpm --dir site dev` while writing (no CSP, no demo); `pnpm --dir site build` (or `publish-site.ps1 -NoPublish -DemoRef HEAD`, with the demo) then `pnpm --dir site preview` (`site/scripts/preview.mjs`, port 4321) serves `dist/` with the server's exact CSP and proxies `/updates/*` to the live server, so CSP blocking shows in the browser console before publishing.
- **Publishing**: user `seaglass-deploy` (no password or sudo, SSH key with `restrict`), alias `seaglass-updates` in the PC's `~/.ssh/config` (server's local IP), `SEAGLASS_RELEASE_DEST=seaglass-updates:/srv/updates/seaglass` (Windows user variable). After `scp`, the script resets permissions to 755 / 644: otherwise the version folder arrives world-writable.
- **Release profile** (0.4.53): `lto = "thin"` on the default 16 codegen units, and the lib as `["cdylib", "rlib"]` (no `staticlib`, iOS only). Before, a full LTO on a single unit was redone for each lib type (staticlib, cdylib) then for the exe, on a single core: rebuilding the Seaglass crate alone took 3 min 11 s, 1 min 01 s since (measured on 2026-11-03, `touch src/lib.rs` then `cargo build --release`). Do not bring back `codegen-units = 1` or `lto = true` without measuring.
- **Release**: `pnpm release` (`scripts/release.ps1`) checks the git tree, `.env`, the key and `VERSION`, bundles mpv, runs `pnpm tauri build --config src-tauri/tauri.release.conf.json`, then writes `release/latest.json`, `release/<version>/Seaglass_<version>_x64-setup.exe` and `release/windows.json` (the website's download page, #517). With `-Publish`, it copies to `SEAGLASS_RELEASE_DEST` (folder or scp target) the installer, then `windows.json`, the manifest last, then sets and pushes the `v<version>` tag. One release = one tag: no update on every push. The `.sig` is also kept in `release/<version>/` (since #108). **Test build** (modified tree, `-AllowDirty`): uncompressed installer (`scripts/tauri.test.conf.json`, `compression: none`), makensis ~1 s for 140 MB instead of ~50 s for 42 MB with LZMA (measured on 2026-11-03: zlib 14 s / 57 MB, bzip2 10 s / 54 MB; LZMA kept for releases, the updater downloads the whole installer over the home connection). Decided on the actually modified tree, not on the flag: such a build is never publishable (`-PublishOnly` refuses a `dirty` marker).
- **Full release** (`scripts/release-all.ps1`, recommended): `powershell -File scripts/release-all.ps1 [-Publish] [-Notes …]` builds the installer, the APK then the Linux AppImage (`release-linux.ps1`, #313, in WSL: see `linux.md`, "Release") **without publishing anything**, then, with `-Publish`, publishes Android, Linux then **Windows last** (#314: its publication uploads `latest.json`, which also announces the AppImage), sets the tag and creates a single GitHub release with all three. `-SkipLinux` leaves Linux out (WSL or the build distribution missing). A failed build = nothing online. Each step runs in its own `powershell` process. Alias `pnpm release:all` (0.4.52, added with a real app change: `package.json` counts for the version check); options follow (`pnpm release:all -Publish`). All three scripts accept `-PublishOnly` (publishes the last build without redoing it) and `-SkipGitHubRelease`. Each build writes a marker `release/.build/<windows|android|linux>.json` (`version`, `commit`, `dirty`, `scripts/build-stamp.ps1`): `-PublishOnly` refuses a build of another version, another commit or a modified tree. The Windows publication now only copies the installer and its `.sig`, not all of `release/<version>/` (the APK and AppImage are there too). Never publish automatically (CI or `VERSION` change): the signing keys stay on the PC, see "No release in CI".
- **Updater manifest** (#314, `scripts/updater-manifest.ps1`): `release/latest.json` is written by a single function, `Write-UpdaterManifest`, called by `release.ps1` and `release-linux.ps1` after their build. It only describes the version built, with one entry per platform whose marker (`release/.build/<platform>.json`) is of that version, that commit and the same tree state: `windows-x86_64` (installer) and `linux-x86_64` (AppImage, signed with the same key: `scripts/signing-key.ps1`, shared by both scripts, passed to WSL through `WSLENV`). Never an entry for an older version, which the updater would install. Before uploading `latest.json`, the Windows publication checks that every other announced file is already online (`Assert-ManifestOnline`: HEAD request, or file present for a local destination), otherwise it fails. `release-linux.ps1 -Publish` alone does not upload `latest.json`: the AppImage is downloadable, not yet offered. Tested offline (Windows alone, both, Linux of another version ignored, check refused then accepted).
- **GitHub release** (#108, `scripts/github-release.ps1`, called by `-Publish` after the tag; Gitea until 2026-11-22): release `Seaglass <version>` on the tag with as attachments whatever exists in `release/` for that version: the installer, its `.sig` and `latest.json`, the APK and `android.json`, the AppImage, its `.sig` and `linux.json` (the published files, nothing is rebuilt in CI: the key stays on the PC). Through `gh` with an **explicit token**, never its default login (another personal account may be signed in on the PC): fine-grained token of the repository owner, "Contents: Read and write", in `SEAGLASS_GITHUB_TOKEN` (environment or `.env`: `build.rs` only embeds its own list of keys, so the token never reaches the app) or the generic Credential Manager entry `seaglass-github-token` (`cmdkey /generic:seaglass-github-token /user:seaglass /pass`); `SEAGLASS_GITHUB_REPO` = `owner/name`, `SEAGLASS_GITHUB_USER` (optional) refuses a token of another account. Reading shared with the key password in `scripts/credentials.ps1`. The tag must already be on `origin` (`--verify-tag`). A failure is only a warning (the update is already online): rerun `powershell -File scripts/github-release.ps1 [-Version x.y.z]`; a rerun keeps the notes and replaces attachments with the same name (`--clobber`). For a version published before #108: installer only (no `.sig` kept), `latest.json` not attached if it describes another version, notes taken from `git log` since the previous tag. No `pnpm` alias: `package.json` would bump the app version (CI check). First real run on 2026-11-22 (v0.5.106, eight attachments). Under Windows PowerShell 5.1, `$ErrorActionPreference = 'Stop'` turns the stderr of a native command into a terminating error: the `gh` calls run with `Continue` and check `$LASTEXITCODE`.

## CI

- **Workflow**: `.github/workflows/ci.yml` (GitHub Actions, GitHub-hosted runners, free for a public repository), on push to `main`, on every PR, weekly (Monday 05:17 UTC, full run: catches a new advisory when no app PR runs the audit) and by hand (`workflow_dispatch`). `linux` and `windows` are required checks of the `main` ruleset (no direct push, no force push, PR required with 0 approvals, no bypass), so no `paths-ignore`: a PR whose required checks never start could not be merged. Since 2026-11-22 (move to GitHub); before that, `.gitea/workflows/ci.yml` on a dedicated `act_runner` on the maintainer's server (`ci/`, removed: a self-hosted runner must never serve a public repository, any fork PR could run code on it). `permissions: contents: read`; a new push cancels the previous run of the same branch.
- **Jobs by change** (GitHub #24): the `changes` job runs `scripts/ci-changes.sh` (plain `git diff` against the PR base, no third-party action; runnable locally: `bash scripts/ci-changes.sh <base> [<head>]`) and outputs `app`, `site`, `relay`. `app` is true unless every changed file is documentation (`*.md`, `docs/`), `site/`, `relay/`, `spike/`, `scripts/` (release scripts, never run in CI), `.github/`, `.claude/` or a repository file (`LICENSE`, `.env.example`, `.gitignore`…); the mock backend and the frontend tests count as app (checked by `linux`). A change to `ci.yml`, `ci-changes.sh` or `check-version.sh`, a push to `main`, a scheduled or manual run: everything. `linux` / `windows` run when `app`, `site` and `relay` when their folder changed; a job skipped by its `if:` reports success, so a docs-only PR passes its required checks in ~30 s instead of ~4 min. Each job also runs if `changes` failed (`needs.changes.result != 'success'`): an error never skips a required check. `site` and `relay` are not required checks: a red one shows on the PR without blocking it (add them to the ruleset to block).
- **`linux` job** (`ubuntu-24.04`): version check, Tauri system libraries (`apt-get`), pnpm + Node 24, `pnpm format:check`, `pnpm check`, `pnpm test`, `pnpm build`, then `cargo fmt --check`, `clippy -D warnings`, `cargo test` in `src-tauri/`, then the dependency audit (`pnpm audit`, `cargo audit` of `src-tauri/`).
- **`site` job**: `pnpm install` and `pnpm build` in `site/` (pnpm cache keyed on `site/pnpm-lock.yaml`).
- **`relay` job**: `cargo fmt --check`, `clippy -D warnings`, `cargo test` and `cargo audit` in `relay/`, with its own Rust cache. `pnpm build` runs before Rust because `tauri::generate_context!` requires `dist/`. Neither `.env` nor `fixtures.json` is needed.
- **`windows` job** (`windows-2025`): `pnpm build` (for `dist/` only), then `clippy -D warnings` and `cargo test` in `src-tauri/`. It covers the `#[cfg(windows)]` code (SMTC, Job Object, WASAPI) that the Linux job does not compile; before, only `pnpm release` checked it. Steps run under `bash`: a multi-line `pwsh` step only fails on its last command.
- **Version check** (`scripts/check-version.sh`, checkout with `fetch-depth: 0`): fails if `VERSION` is lower than the last `v*` tag, or equal to it while app files changed since that tag (excluding `*.md`, `docs/` (README screenshots), `LICENSE`, `.env.example`, `.github/`, `scripts/`, `spike/`, `relay/`, `site/`, `.claude/`, `.gitignore`, `.gitattributes`, `.git-blame-ignore-revs`, `src/lib/mock/`, frontend tests `src/**/*.test.ts` and `src/lib/testing/`, outside the bundle). A change to Rust tests alone therefore also needs a new version. Runnable locally: `bash scripts/check-version.sh`.
- **Shared code used only on Windows** must tolerate dead code outside Windows (`#[cfg_attr(not(windows), allow(dead_code))]`, see `integrations/mod.rs` and `Cmd::SetPaused`), otherwise clippy fails in the Linux job. mpv IPC goes through a Unix socket outside Windows (`mpv::ipc::open`).
- **Cache**: `Swatinem/rust-cache` (kept on failure), pnpm store through `actions/setup-node`. `CARGO_PROFILE_{DEV,TEST}_DEBUG=0`: no debug info, lighter linking and cache.
- **Dependabot** (`.github/dependabot.yml`): monthly version updates for the GitHub Actions only, grouped in one PR (labels `type/chore`, `area/ci`). Not for Cargo or npm: a lockfile change counts as an app change for the version check, so every automatic PR would fail until `VERSION` is bumped by hand; those are covered by the Dependabot security alerts and by `cargo audit` / `pnpm audit` in CI, and a real advisory is fixed in a PR with its version bump. Advisories that cannot be fixed (`glib` 0.18 from Tauri): `audits.md`.
- **CodeQL** (`.github/workflows/codeql.yml`): weekly (Monday 05:41 UTC) and by hand, not on PRs: GitHub's default setup ran it on every push, 9 to 12 min for Rust (about 1 min for the other languages), never a required check but a pending check on every PR. Languages: `actions`, `javascript-typescript`, `rust` (`build-mode: none`); no Python (only `spike/`). Results in the Security tab. The repository's CodeQL **default setup must stay off** (Settings › Code security): GitHub refuses advanced uploads while it is on.
- **No release in CI**: the minisign key and the Android keystore stay on the PC, `pnpm release` stays manual.
- **Dependencies** (#263): `pnpm audit --prod --ignore-registry-errors` (only what ships in the app), then `cargo audit` on `src-tauri/Cargo.lock` and `relay/Cargo.lock` (`cargo-audit` installed prebuilt by `taiki-e/install-action`). It only fails on a vulnerability; unmaintained, yanked or "unsound" crates stay warnings. An advisory to ignore goes as `--ignore RUSTSEC-…` in the workflow with its reason, never in a file under `src-tauri/` (it would count for the version check). First pass on 2026-11-10 (cargo-audit 0.23.0): no vulnerability across 566 crates (app) and 92 (relay); 5 warnings, all outside the Windows and Android app: `proc-macro-error` (build-time macro), `zbus_names` / `zvariant` / `zvariant_derive` (D-Bus, Linux) unmaintained, `glib` 0.18 "unsound" (GTK, Linux, pulled in by Tauri).
