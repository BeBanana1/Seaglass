# Installer, updates and CI

Seaglass implementation notes, read on demand (index in [`CLAUDE.md`](../CLAUDE.md)). APK distribution is in [`android.md`](android.md).

## Installer and updates

- **Installer**: NSIS only (`bundle.targets`), per-user install (`installMode: currentUser`, no admin), in `%LOCALAPPDATA%\Seaglass`, in English and French (`nsis.languages`, since 0.4.17; French only in 0.4.7): NSIS takes the Windows language if it is in the list, otherwise the first one (English). Tauri's NSIS template always creates the Start menu shortcut; its finish page offers "Launch" and the desktop shortcut. No Authenticode signature: SmartScreen warns on first launch (only remedy: a paid certificate, for example Azure Trusted Signing). Icon (0.4.52, #126): a vinyl record whose label is a sun above the sea, `src-tauri/icons/app-icon.svg`. Derived with `pnpm tauri icon src-tauri/icons/icon.json` (then delete `icons/ios`): the manifest adds Android's adaptive icon, written directly into `gen/android/app/src/main/res` (foreground `app-icon-android-fg.svg`, disc reduced to 68 % for the safe zone; white background `app-icon-bg.svg`; themed icon `app-icon-monochrome.svg`). Changing the drawing = changing all three SVGs. Legacy icons (`ic_launcher.png`, Android 7) are derived from the foreground by Tauri and overflow a little. **Taskbar and Task Manager** (#139): Tauri only sets the window's small icon (`ICON_SMALL`), the large one comes from the exe, which Windows keeps in its icon cache by path: after a logo change, the old one stayed displayed. Hook `src-tauri/nsis/hooks.nsh` (`nsis.installerHooks`, `NSIS_HOOK_POSTINSTALL`): `SHChangeNotify` `SHCNE_UPDATEITEM` on the exe then `SHCNE_ASSOCCHANGED`. On a machine already affected: `ie4uinit.exe -show`, and unpin / repin the app. Licenses shipped in `licenses/` (Seaglass's GPL-3.0, mpv notice). **Images** (0.4.71, #194): `nsis.sidebarImage` (164 × 314, welcome and finish pages) and `nsis.headerImage` (150 × 57), 24-bit BMPs in `src-tauri/nsis/`, generated from `icons/icon.png` by `python -I scripts/installer-images.py` (Pillow): rerun after a logo change.
- **Bundled mpv**: only in release builds, through `src-tauri/tauri.release.conf.json` (`externalBin: binaries/mpv`). The script copies the mpv from `PATH` (or `SEAGLASS_MPV_PATH`) to `src-tauri/binaries/mpv-x86_64-pc-windows-msvc.exe` (gitignored, 119 MB), **only if it matches `scripts/mpv.lock`** (#87): SHA-256 checked before the binary is ever run, then version (first two words of `mpv --version`), then checksum of the copy. **Frozen copy**: `powershell -File scripts/update-mpv-lock.ps1` copies the mpv from `PATH` (or `-Source`) to `%LOCALAPPDATA%\Seaglass-build\mpv.exe`, out of reach of zhongfly's `updater.bat` (daily build), after confirmation (path, size, date, checksum and old lock shown); checksum of the copy checked, version read from the copy only, `mpv.lock` rewritten and user variable `SEAGLASS_MPV_PATH` pointed at the copy. Releases therefore no longer break on every mpv update: changing mpv = checking it, running the script, committing `mpv.lock`. The lock never follows the installed mpv on its own (it would no longer protect against anything). In the base config, `externalBin` would make any `cargo build` fail without that file. The current mpv build (zhongfly, x86-64-v3) requires an AVX2 CPU.
- **Updates** (`src-tauri/src/updater.rs`): check 20 s after startup then every 6 h; background download, signature verified by the plugin; `update-ready` event → `UpdatePrompt.svelte` ("Install and restart" = `install_update`, "Later" = install on `RunEvent::Exit`, without relaunch). `on_before_exit` stops mpv before the installer closes the app. Nothing is checked automatically in debug unless `SEAGLASS_UPDATE_URL` is set (also useful to test another manifest). "Check" button in Settings › Application (0.4.6, #43): `check_for_updates` runs the same check, serialized with the background task (`UpdateState::checking`), and re-emits `update-ready` if a version is ready, even one already postponed. It also works in debug (production manifest by default). **Answer before the download** (0.4.71, #187): `check` returns as soon as the manifest is read; the installer (~42 MB) downloads in a separate task (`download`, `UpdateState::downloading`, one at a time), then `update-ready`, or `update-failed` (message) on failure. `UpdateInfo::downloading` is true until it is done: Settings shows "Version x available, downloading…" then "ready". Preview: `?route=settings&tab=app&update=download`. **Linux** (0.5.8, #314): only from an AppImage (`updater::supported` = `app.env().appimage`, validated by Tauri; `--appimage-extract-and-run` counts, `APPIMAGE` pointing to the real file). Outside an AppImage, the plugin would target the current executable and replace the bare binary with an AppImage: no check, `updates_available` false, and Settings shows "updates only available in the AppImage" without a button (preview `?updates=manual`). The plugin rewrites the AppImage without relaunching: `install_update` calls `request_restart` (queue saved and mpv stopped by `RunEvent::Exit`). Folder not writable: clear message (`install_error`), update kept for a new attempt. A manifest without an entry for the platform (`TargetNotFound`) counts as "up to date".
- **Built-in addresses** (0.5.79, #452): no service address is written in the code or in `tauri.conf.json` (no more `plugins.updater.endpoints`, optional in the plugin). `build.rs` reads `SEAGLASS_UPDATE_BASE_URL` (updates folder) and `SEAGLASS_RELAY_BASE_URL` (Jam relay) from the build environment, otherwise from `.env`, and passes them as `SEAGLASS_BUILD_*` (`cargo:rerun-if-env-changed`), read by `src-tauri/src/servers.rs`. Desktop reads `<base>/latest.json` (`updater::endpoint`, `SEAGLASS_UPDATE_URL` at launch always wins), Android `<base>/android.json` and only accepts APKs under `<base>/`. **Without a built-in address**: no check, and Settings shows neither the switch nor the button (so a `pnpm tauri dev` has none, unless the variable is set). The three release scripts set `$env:SEAGLASS_UPDATE_BASE_URL` to their `$baseUrl` before the build (#489: no default anymore, read from the environment then from `.env` by `scripts/release-env.ps1`, otherwise the script stops): the built-in address is always that of the manifests written; `release-linux.ps1` passes it to WSL through `WSLENV`. The relay comes from `.env` (with its key). **No update address configurable in the app**: the updater only accepts builds signed by the built-in key (`pubkey`, APK certificate), another server could only serve a mirror of the same builds. Whoever rebuilds with their own key also sets their own address. **Switch** "Automatic updates" (`UiSettings::auto_updates`, on by default, `servers::auto_updates` reread on every round of the background task): when off, only the periodic check stops, the "Check" button stays.
- **Signing**: minisign key in `%USERPROFILE%\.tauri\seaglass.key` (outside the repository). **Built-in public key** (0.5.91, #489): `plugins.updater.pubkey` stays empty in `tauri.conf.json` (field required by the plugin); `build.rs` reads `SEAGLASS_UPDATER_PUBKEY` (environment, then `.env`), `servers::updater_pubkey` passes it to the plugin (`Builder::pubkey`, `lib.rs`). Without it, desktop checks no update and Settings hides the section, even with an address (Android does not need it: APK certificate). `release.ps1` and `release-linux.ps1` read it from `<private key>.pub` (content as is, already base64) if the variable is missing, and Linux passes it to WSL through `WSLENV`. **Losing the private key** = no update accepted anymore by installed versions (manual reinstall): it must be backed up.
- **Key password** (#87): a Tauri file is the base64 of a minisign secret key, **always encrypted** (scrypt + XOR, `Sc`); "no password" = empty password. Changing the key would break updates: the same key is re-encrypted with `python -I scripts/protect-signing-key.py <key> <new key>` (standard library, passwords typed without echo, at least 12 characters, new file, reread before being kept). Verified on throwaway keys: signature from the re-encrypted key accepted by `minisign-verify` with the original public key. `release.ps1` first tests the empty password (`--check`, password on standard input): key still without a password → warning and normal release; otherwise the password is taken from `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, then from the generic Credential Manager entry `seaglass-signing-key` (optional: `cmdkey /generic:seaglass-signing-key /user:seaglass /pass`, more convenient but readable by any program of the account), then typed without echo; checked before the build, passed to Tauri through the environment only, removed afterwards. Non-interactive session without a password → explicit failure. Without python, no prior check (Tauri fails at signing on a wrong password). Re-encryption procedure in issue #87.
- **Taking over the project** (#489): no value specific to the author in the code or in the scripts. To publish your own versions: `tauri signer generate -w ~/.tauri/seaglass.key`, `SEAGLASS_UPDATE_BASE_URL` (public folder served over HTTPS) and `SEAGLASS_RELEASE_DEST`; for Android, your own keystore (`android.md`); for the Gitea release, `SEAGLASS_GITEA_URL` and `SEAGLASS_GITEA_REPO` (environment or `.env`), or `-SkipGiteaRelease`. The rest describes the author's instance.
- **Hosting** (author's instance, in service): the Gitea requires sign-in everywhere, so the updater cannot read releases there. Updates are served by the server's Caddy (Docker): `updates.bebanana.ch` (CNAME to `bebanana.internet-box.ch`) serves `/srv/updates` read-only, `latest.json` with `Cache-Control: no-cache`. The folder is public, the installers being signed.
- **No authentication on that folder** (2026-11-12): the updater, the Android app and the page read the manifests without a session; a password would have to be embedded in the app, hence readable by everyone. What protects updates: the minisign signature (an installer replaced on the server is refused by the updater), the private key kept on the PC and the restricted `seaglass-deploy` account. Verified online: HTTP redirected to HTTPS (308), no directory listing (`/seaglass/<version>/` gives 404).
- **Security headers** (server Caddyfile, outside the repository): in the `updates.bebanana.ch` block, then reload Caddy:

  ```caddyfile
  header {
      Strict-Transport-Security "max-age=31536000"
      X-Content-Type-Options "nosniff"
      Referrer-Policy "no-referrer"
      Content-Security-Policy "default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'"
      -Server
  }
  ```

  The CSP forbids inline code: the page's styles and script are in `scripts/download-page.css` and `.js`, uploaded by `release.ps1` before `index.html` and loaded with `?v=<version>` (same name for every version, without a stale cache). `connect-src 'self'` is enough for the `fetch` of `android.json` and `linux.json`; download links are navigations, which the CSP does not restrict. It also applies to the `.json` files and installers, with no effect on the updater or the Android app (HTTP clients, not browsers). HSTS without `includeSubDomains`: the other `bebanana.ch` subdomains keep their own setting. A page published before this change (inline styles and script) would show unstyled, without the Android and Linux cards: only set the CSP after a publication that uploads the new page. Check: `curl -sI https://updates.bebanana.ch/seaglass/` shows the headers, and the browser console reports no CSP blocking.
- **Publishing**: user `seaglass-deploy` (no password or sudo, SSH key with `restrict`), alias `seaglass-updates` in the PC's `~/.ssh/config` (server's local IP), `SEAGLASS_RELEASE_DEST=seaglass-updates:/srv/updates/seaglass` (Windows user variable). After `scp`, the script resets permissions to 755 / 644: otherwise the version folder arrives world-writable.
- **Release profile** (0.4.53): `lto = "thin"` on the default 16 codegen units, and the lib as `["cdylib", "rlib"]` (no `staticlib`, iOS only). Before, a full LTO on a single unit was redone for each lib type (staticlib, cdylib) then for the exe, on a single core: rebuilding the Seaglass crate alone took 3 min 11 s, 1 min 01 s since (measured on 2026-11-03, `touch src/lib.rs` then `cargo build --release`). Do not bring back `codegen-units = 1` or `lto = true` without measuring.
- **Release**: `pnpm release` (`scripts/release.ps1`) checks the git tree, `.env`, the key and `VERSION`, bundles mpv, runs `pnpm tauri build --config src-tauri/tauri.release.conf.json`, then writes `release/latest.json`, `release/<version>/Seaglass_<version>_x64-setup.exe` and the download page `release/index.html` (template `scripts/download-page.html`, `{{…}}` fields HTML-escaped, what's new taken from the notes). With `-Publish`, it copies to `SEAGLASS_RELEASE_DEST` (folder or scp target) the installer, then the page, the manifest last, then sets and pushes the `v<version>` tag. One release = one tag: no update on every push. The `.sig` is also kept in `release/<version>/` (since #108). **Test build** (modified tree, `-AllowDirty`): uncompressed installer (`scripts/tauri.test.conf.json`, `compression: none`), makensis ~1 s for 140 MB instead of ~50 s for 42 MB with LZMA (measured on 2026-11-03: zlib 14 s / 57 MB, bzip2 10 s / 54 MB; LZMA kept for releases, the updater downloads the whole installer over the home connection). Decided on the actually modified tree, not on the flag: such a build is never publishable (`-PublishOnly` refuses a `dirty` marker).
- **Full release** (`scripts/release-all.ps1`, recommended): `powershell -File scripts/release-all.ps1 [-Publish] [-Notes …]` builds the installer, the APK then the Linux AppImage (`release-linux.ps1`, #313, in WSL: see `linux.md`, "Release") **without publishing anything**, then, with `-Publish`, publishes Android, Linux then **Windows last** (#314: its publication uploads `latest.json`, which also announces the AppImage), sets the tag and creates a single Gitea release with all three. `-SkipLinux` leaves Linux out (WSL or the build distribution missing). A failed build = nothing online. Each step runs in its own `powershell` process. Alias `pnpm release:all` (0.4.52, added with a real app change: `package.json` counts for the version check); options follow (`pnpm release:all -Publish`). All three scripts accept `-PublishOnly` (publishes the last build without redoing it) and `-SkipGiteaRelease`. Each build writes a marker `release/.build/<windows|android|linux>.json` (`version`, `commit`, `dirty`, `scripts/build-stamp.ps1`): `-PublishOnly` refuses a build of another version, another commit or a modified tree. The Windows publication now only copies the installer and its `.sig`, not all of `release/<version>/` (the APK and AppImage are there too). Never publish automatically (CI or `VERSION` change): the signing keys stay on the PC, see "No release in CI".
- **Updater manifest** (#314, `scripts/updater-manifest.ps1`): `release/latest.json` is written by a single function, `Write-UpdaterManifest`, called by `release.ps1` and `release-linux.ps1` after their build. It only describes the version built, with one entry per platform whose marker (`release/.build/<platform>.json`) is of that version, that commit and the same tree state: `windows-x86_64` (installer) and `linux-x86_64` (AppImage, signed with the same key: `scripts/signing-key.ps1`, shared by both scripts, passed to WSL through `WSLENV`). Never an entry for an older version, which the updater would install. Before uploading `latest.json`, the Windows publication checks that every other announced file is already online (`Assert-ManifestOnline`: HEAD request, or file present for a local destination), otherwise it fails. `release-linux.ps1 -Publish` alone does not upload `latest.json`: the AppImage is downloadable, not yet offered. Tested offline (Windows alone, both, Linux of another version ignored, check refused then accepted).
- **Gitea release** (#108, `scripts/gitea-release.ps1`, called by `-Publish` after the tag): release `Seaglass <version>` on the tag with as attachments whatever exists in `release/` for that version: the installer, its `.sig` and `latest.json`, the APK and `android.json`, the AppImage, its `.sig` and `linux.json` (the published files, nothing is rebuilt in CI: the key stays on the PC). **User's** token (not `claude`'s: the release is in their name), `write:repository` scope, in `SEAGLASS_GITEA_TOKEN` or the generic Credential Manager entry `seaglass-gitea-token` (`cmdkey /generic:seaglass-gitea-token /user:seaglass /pass`); reading shared with the key password in `scripts/credentials.ps1`. A failure is only a warning (the update is already online): rerun `powershell -File scripts/gitea-release.ps1 [-Version x.y.z]`. Rerun, it replaces attachments with the same name. For a version published before #108: installer only (no `.sig` kept), `latest.json` not attached if it describes another version, notes taken from `git log` since the previous tag; the tag must exist on `origin`. No `pnpm` alias: `package.json` would bump the app version (CI check). Tested against a fake Gitea server (creation, rerun, missing or refused token, unreachable server, old version); not yet against the real one. The server's `[attachment] ALLOWED_TYPES` excludes `.exe`, but releases have their own setting (`[repository.release] ALLOWED_TYPES`, empty = everything): if Gitea refuses the installer, look there.

## CI

- **Workflow**: `.gitea/workflows/ci.yml`, on push to `main` and on every PR, unless only `*.md` / `LICENSE` change: version check, `pnpm check`, `pnpm build`, `cargo fmt --check`, `clippy -D warnings`, `cargo test`. `pnpm build` runs before Rust because `tauri::generate_context!` requires `dist/`. Neither `.env` nor `fixtures.json` is needed.
- **Version check** (`scripts/check-version.sh`, checkout with `fetch-depth: 0`): fails if `VERSION` is lower than the last `v*` tag, or equal to it while app files changed since that tag (excluding `*.md`, `docs/` (README screenshots), `LICENSE`, `.env.example`, `.gitea/`, `ci/`, `scripts/`, `spike/`, `.claude/`, `.mcp.json`, `.gitignore`, `.gitattributes`, `src/lib/mock/`, frontend tests `src/**/*.test.ts` and `src/lib/testing/`, outside the bundle). A change to Rust tests alone therefore also needs a new version. Runnable locally: `bash scripts/check-version.sh`. No automatic publishing: the signing key stays on the PC and the installer is built on Windows.
- **Dedicated runner** (`ci/`, installation in `ci/README.md`): `act_runner` 0.6.1 in Docker on the server, registered **at repository level**, label `seaglass`. It mounts the Docker socket, so it is equivalent to root on the server: never open it to other repositories. The shared runner (firmware, KiCad) is no longer used.
- **No Docker socket in jobs**: `container.docker_host: "-"` in `ci/config.yaml`. Without this key, act_runner mounts `/var/run/docker.sock` in every job, and a `ci.yml` (or a PR that changes it) takes over the VM (audit of 2026-11-18). Only the runner container keeps the socket. A workflow that needs Docker goes another way (rootless DinD, separate runner), not by removing this key.
- **Job image** `seaglass-ci:<dated tag>` (`ci/Dockerfile`, base `node:24-bookworm`): Tauri libraries, Rust stable + rustfmt + clippy, pnpm. Built on the server (`docker compose --profile build build`), without a registry (`force_pull: false`). Changing the tag = `.env` + label in `config.yaml`.
- **Cache**: jobs join the runner's network (`container.network: seaglass-ci`) and the cache listens on a fixed port (8088). Without that, every cache action waits 5 min for an `ETIMEDOUT` (seen on the shared runner).
- **Limitation**: on Linux, `#[cfg(windows)]` code (SMTC, Job Object, `CREATE_NO_WINDOW`) is neither compiled nor tested; `pnpm release` checks it on Windows. Shared code used only by a Windows integration must tolerate dead code outside Windows (`#[cfg_attr(not(windows), allow(dead_code))]`, see `integrations/mod.rs` and `Cmd::SetPaused`), otherwise clippy fails in CI. mpv IPC goes through a Unix socket outside Windows (`mpv::ipc::open`).
- **Duration**: about 7 min on the shared runner, without cache (setup ~4 min, clippy ~1 min, tests ~1 min 30). Dedicated runner (2026-10-30): 5 min without cache (Rust ~2 min 40, cache save ~1 min 40), 4 min 30 on the first `main` run (cache restored in 35 s but partial key, Rust ~1 min 15, new save ~2 min 20). A run whose key matches exactly does not save: steady-state duration to be confirmed. 2026-11-03: runs of about 2 min with the full cache (restoring 1.9 GB ~1 min 15, clippy 7 s, test build 18 s), but one run froze for more than 10 min on the test build (server memory suspected). Since then: `timeout-minutes: 20` on the job and `CARGO_PROFILE_{DEV,TEST}_DEBUG=0` (no debug info: lighter linking, smaller cache; `CARGO_*` variables are part of the cache key, the first run after this change starts without cache). The Gitea API does not expose cancelling a run (404): cancel from the web interface.
- **Bringing it up**: if a job starts on `runner-images:ubuntu-latest` with a `…-check-network` network, the runner is not reading `config.yaml` (container started from old files). `data/.runner` belongs to root: `sudo rm` to re-register.
- **No release in CI**: the minisign key stays on the PC, `pnpm release` stays manual.
- **Dependencies** (#263): "Dependencies" step after the tests. `pnpm audit --prod --ignore-registry-errors` (only what ships in the app), then `cargo audit --no-fetch` on `src-tauri/Cargo.lock` and `relay/Cargo.lock`, with the RustSec database cloned separately (`git clone --depth 1`): if it is unreachable, the step warns and passes. It only fails on a vulnerability; unmaintained, yanked or "unsound" crates stay warnings. `cargo-audit` comes from the image (`ci/Dockerfile`); without it, the Rust audit is skipped with a warning. The workflow no longer installs it itself: `CARGO_HOME` is in the container (`/usr/local/cargo`), outside the Rust cache, and `cargo install` recompiled it on every run (1 min 44 s, the job went from ~1 min 10 to ~3 min). An advisory to ignore goes as `--ignore RUSTSEC-…` in the workflow with its reason, never in a file under `src-tauri/` (it would count for the version check). First pass on 2026-11-10 (cargo-audit 0.23.0): no vulnerability across 566 crates (app) and 92 (relay); 5 warnings, all outside the Windows and Android app: `proc-macro-error` (build-time macro), `zbus_names` / `zvariant` / `zvariant_derive` (D-Bus, Linux) unmaintained, `glib` 0.18 "unsound" (GTK, Linux, pulled in by Tauri). `pnpm audit --prod`: nothing.
