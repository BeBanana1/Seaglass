## Principes non négociables

1. **Streaming uniquement.** Aucun téléchargement, export ou mise en cache des flux audio sur disque. Aucun contournement de DRM : si un flux est protégé par Widevine, on ne le lit pas, on remonte une erreur claire.
2. **Rust est la source de vérité.** L'UI n'a aucune logique métier : elle affiche l'état reçu du backend et envoie des commandes. Elle ne parle jamais directement à TIDAL ni à mpv.
3. **Tout ce qui touche TIDAL vit dans `src-tauri/src/tidal/`.** C'est une API privée non documentée qui peut changer à tout moment : le reste du code ne dépend que des types de `tidal::models`, jamais des formats JSON bruts.
4. **Aucun secret dans le dépôt.** Client ID / secret dans `.env` (gitignoré) ou variables d'environnement. Tokens utilisateur dans le Gestionnaire d'identifiants Windows via la crate `keyring`. Ne jamais logger un token, même tronqué.
5. **Pas de nom ni de logo TIDAL** dans le nom de l'app, l'icône ou le titre de fenêtre. Mention « Client non officiel, non affilié à TIDAL » dans Réglages › Application et le README.

## Architecture du lecteur

- **Acteur unique.** Une seule tâche tokio possède `Player` (file + état). Tout passe par un `mpsc::Sender<Cmd>` : commandes UI, événements du moteur, SMTC. Pas de `Mutex` sur l'état du lecteur.
- **Moteur de lecture** (`engine.rs`, 0.4.42, #24) : l'acteur n'envoie que des opérations sémantiques (`Op::Play`, `Preload`, `RemoveNext`, `DropPrevious`, `Seek`, `LoopCurrent`, `Volume`, `CurrentGain`…) et reçoit des `Event` déjà traduits (`Position`, `Advanced`, `Ended(End::Eof | OutputFailed | Error)`, `Stopped`…). `mpv/engine.rs` (`MpvEngine`) traduit dans les deux sens (`commands`, `translate`, logique pure testée ; `cargo test live_engine_window -- --ignored --nocapture` avec un vrai mpv). Aucune commande JSON de mpv hors de `mpv/`. Le moteur Media3 d'Android implémentera le même trait `Engine`. `AudioDevice` et `CacheSize` restent dans `mpv` (réglages du bureau).
- **File d'attente** (`player/queue.rs`) :
  - `context: Vec<TrackId>` (album / playlist d'origine), `order: Vec<usize>` (ordre de lecture, mélangé ou non), `pos`
  - `manual: VecDeque<TrackId>` prioritaire sur le contexte (« Lire ensuite » = `push_front`, « Ajouter à la file » = `push_back`)
  - `history: Vec<TrackId>` pour « Précédent », indépendant du shuffle
  - `repeat: Off | All | One`
  - Shuffle = Fisher-Yates sur les pistes restantes, piste courante en tête. Désactiver le shuffle restaure l'ordre d'origine sur la piste courante.
- **Fenêtre mpv de 2 entrées maximum** : piste en cours + suivante. Les URLs de flux sont signées et expirent, donc on ne charge jamais plus loin.
  - Préchargement de la suivante (`loadfile <url> append`) quand `duration - time_pos < 30 s`.
  - Sur `playlist-pos == 1` : avancer la file, `playlist-remove 0`, `next_loaded = false`.
  - **Toute modification de la file** (lire ensuite, shuffle, retrait, repeat) → `playlist-remove 1` si une suivante est chargée, puis `next_loaded = false`.
- **Repeat One** = `loop-file=inf` côté mpv, pas de rechargement.
- **Précédent** : si `time_pos > 3 s`, seek à 0, sinon dernière piste de `history` en `loadfile … replace`.
- **Erreur de lecture** (`end-file` reason `error`) : redemander une URL une fois, puis passer à la suivante et émettre un événement `toast`.
- **Vers l'UI** : événement `player-state` émis seulement si l'état a changé, avec `time_pos` limité à environ 4 Hz. L'UI interpole la barre de progression avec `requestAnimationFrame`. La liste de la file part dans un événement séparé `queue-state`, émis seulement quand la file change (sinon elle serait renvoyée 4 fois par seconde).
- **Persistance** : file et position sauvegardées dans SQLite (debounce de 2 s), restaurées en pause au démarrage.

## mpv

- Lancé par l'app avec `--no-config --include=<seaglass.conf>` pour **ne jamais** charger la config mpv vidéo personnelle de l'utilisateur.
- Options de base : `--idle=yes --no-video --input-ipc-server=\\.\pipe\seaglass-mpv-<pid de l'app>-<aléatoire> --ao=wasapi --gapless-audio=weak --prefetch-playlist=yes`. Le pid dans le nom du pipe empêche de se connecter à un mpv orphelin d'un lancement précédent, la partie aléatoire qu'un autre processus le crée avant mpv.
- Tauri quitte sans exécuter les destructeurs : mpv est tué explicitement sur `RunEvent::Exit` (`mpv::process::ProcessGuard`). En cas de plantage, c'est le Job Object (voir plus bas) qui l'arrête.
- `media-controls=no` et `input-media-keys=no` dans `seaglass.conf` : sinon mpv publie sa propre session SMTC « mpv », qui capte les touches média (cause des issues #6 et #27). Seule la session de Seaglass doit exister.
- `audio-params` passe à `null` à chaque fin de fichier et n'est pas renvoyé si le titre suivant a le même format : un `null` est ignoré, la sortie n'est effacée que sur `idle-active` (#12, `PlayerState::set_output`).
- Mode bit-perfect (réglage utilisateur) : `--audio-exclusive=yes`, volume mpv à 100, pas de `replaygain` ni de normalisation (#82), pas de `audio-samplerate` forcé, pas de filtres audio.
- Propriétés observées : `playlist-pos`, `time-pos`, `duration`, `pause`, `paused-for-cache`, `audio-params`, `current-ao`, `idle-active`, `audio-device-list`. Événement : `end-file`. Propriétés écrites sans être observées (l'état de l'acteur fait foi) : `volume`, `mute`, `demuxer-max-bytes`, `demuxer-max-back-bytes`, `audio-device`.
- **Cache** : `cache=yes` et `cache-on-disk=no` dans `seaglass.conf` (mémoire uniquement). La taille vient du réglage `playback.settings` (`mpv/cache.rs`, `player/settings.rs` : 32 / 64 / 128 / 256 Mio, défaut 64, retour = un quart), passée en ligne de commande au lancement puis appliquée à chaud par `set_property`. Effectif dès que la lecture consomme des paquets (en pause, le démuxeur plein reste endormi) ; vérifié par `cargo test live_cache_resize -- --ignored --nocapture`. Avec la suivante préchargée, la mémoire peut atteindre deux fois la taille choisie.
- **Normalisation du volume** (#82, `player/normalize.rs`, logique pure testée) : réglage `PlaybackSettings::normalization` = `off` (défaut, validé par l'utilisateur) / `track` / `album` (gain d'album, sinon du titre). Gain de l'API (`Stream::gain`, ReplayGain de `playbackinfopostpaywall` du flux réellement lu, édition hi-res comprise), **limité par la crête** (`gain ≤ −20·log10(crête)`, jamais d'écrêtage), borné à [−24, +12] dB, arrondi au centième ; nul ou inconnu → aucun filtre. Appliqué en **option de fichier** du `loadfile` (`… replace|append -1 start=…,af=volume=volume=<g>dB`) : le titre préchargé ne touche pas le titre en cours. Changement du réglage : `set_property file-local-options/af` sur le titre en cours (remis à la fin du fichier ; `options/af` montre la valeur en vigueur, ce n'est pas une fuite), puis le préchargé est retiré pour être rechargé avec son gain. Vérifié avec mpv 0.41 (`cargo test live_per_file_af -- --ignored --nocapture`, lecture réelle courte d'un sinus à −40 dBFS, volume 30) : `af` = −6 dB sur le titre en cours, −12 dB sur le préchargé seulement après le passage gapless, `af=[]` sur un fichier chargé sans option ; la sortie reste en `s16`. `PlayerState::normalization` (gain appliqué en dB ou `null`) → verdict « Volume normalisé » (jamais bit-perfect, la coupure reste prioritaire), « RG −6,5 dB » sous mpv. Réglages › Lecture : `.normalization-modes` / `.normalization-mode` (avec `.cache-sizes` / `.cache-size` / `.hires-mode`). **Le mode exclusif / bit-perfect à venir devra griser ce réglage et ne poser aucun `af`.** Aperçu : `?normalization=track|album`.
- **Périphérique de sortie** (#79, `mpv/device.rs`, `player/output.rs`) : réglage `PlaybackSettings::audio_device` (`null` = défaut du système, ou `{id: "wasapi/{guid}", name}` validé à la désérialisation), passé en `--audio-device` au lancement et posé à chaud par `set_property audio-device` (mpv rouvre la sortie sans interrompre le titre). Vérifié avec mpv 0.41 (`cargo test live_audio_devices -- --ignored --nocapture`, silence sur la vraie sortie) : `audio-device-list` est notifiée dès l'observation (`auto`, `wasapi/{guid}` + description, `openal` : seules les entrées `wasapi/` sont gardées) ; un périphérique absent au chargement fait échouer le fichier (`end-file` `error`, `audio output initialization failed`), **mpv ne se replie pas seul**. Au branchement / débranchement, la liste est renotifiée (`ao_hotplug_event` dans `ao_wasapi_changenotify.c`, pas testable sans débrancher un périphérique). L'acteur décide (`device::resolve`, testé) : choix présent → lui, sinon `auto` + toast, le réglage restant intact ; retour automatique + toast au rebranchement. Filet : une erreur `audio output initialization failed` sur un périphérique choisi le marque inutilisable jusqu'à la liste suivante et relance le titre à la même position, sans consommer la nouvelle tentative d'URL. `PlayerState::output_device` (`name`, `systemDefault`, `missing`) : nom réel dans `SignalPath` (nœud Sortie, en `--warn` pendant un repli ; seulement en info-bulle dans la barre resserrée de Studio). En `auto`, le nom vient du périphérique par défaut de Windows (`IMMDeviceEnumerator::GetDefaultAudioEndpoint(eRender, eMultimedia)`, même rôle que mpv, guid de `GetId` retrouvé dans la liste). Réglages › Lecture › Sortie audio : `components/OutputDevicePicker.svelte` (commande `audio_devices`, puis événement `audio-devices`), classes `.cache-sizes.audio-devices` / `.cache-size.audio-device` (thèmes déjà prêts), choix débranché affiché « débranché ». Aperçu : `?route=settings&tab=playback&device=dac|missing`.
- Un micro-blanc lors d'un changement de fréquence d'échantillonnage en mode exclusif est **normal** (réouverture du périphérique). Ce n'est pas un bug à corriger.
- Résolution de mpv (`mpv::process::executable`) : `SEAGLASS_MPV_PATH`, sinon `mpv.exe` à côté de `seaglass.exe` (installé par l'installeur), sinon celui du `PATH` (dev).
- **Processeur sans AVX2** (#92, option 3 choisie par l'utilisateur : garder la build x86-64-v3) : rien n'est bloqué d'avance, mpv est lancé normalement. S'il échoue (lancement, connexion IPC, ou `Disconnected`), `MpvIssue::diagnose` (`mpv/mod.rs`) vaut `CpuUnsupported` si c'est le mpv de l'installeur (`process::is_bundled`) **et** que `IsProcessorFeaturePresent(PF_AVX2_INSTRUCTIONS_AVAILABLE)` est faux (`mpv/cpu.rs`, feature `Win32_System_Threading`), sinon `Stopped`. Pas de faux positif avec un mpv choisi par l'utilisateur ni si la build embarquée change. `PlayerState::mpv_issue` (dans l'état et pas en toast : l'échec au lancement précède l'écoute de la webview) → bandeau persistant `components/MpvIssue.svelte` au-dessus de la barre de lecture (`.mpv-issue`, `.mpv-issue-title`, `.mpv-issue-hint`), qui conseille un mpv x86-64 classique via `SEAGLASS_MPV_PATH` ; le toast d'une lecture demandée reprend `MpvIssue::message`. Aperçu : `?mpv=cpu` ou `?mpv=stopped`. Non testable sur les PC de dev et de CI (ils ont l'AVX2).
- mpv est rattaché à un Job Object Windows `KILL_ON_JOB_CLOSE` (`mpv/job.rs`) : il meurt avec l'app, même sur un plantage.

## Résultats du spike (2026-10-29, tidalapi 0.8.11, abonnement HI_RES, pays CH)

Observé avec `spike/play.py probe` puis décodage réel dans mpv 0.41.

- **Le type de connexion détermine la qualité, pas l'abonnement.**
  - Client « appareil » (device code, `link.tidal.com`) : manifeste `application/vnd.tidal.bts`, **AAC 320 kbps maximum**, même en demandant `LOSSLESS` ou `HI_RES_LOSSLESS`. Inutilisable pour l'app.
  - Client PKCE (identifiant Android embarqué dans tidalapi, redirection vers `https://tidal.com/android/login/auth?code=…`) : manifeste `application/dash+xml` pour toutes les qualités. **C'est le flux de connexion à implémenter en phase 1** (la webview Tauri peut intercepter la redirection, ce qui évite le copier-coller).
- **Formats reçus (client PKCE)** :

  | Demandé | Reçu | Codec | Format |
  |---|---|---|---|
  | `LOW` | LOW | HE-AAC `mp4a.40.5` | ~96 kbps |
  | `HIGH` | HIGH | AAC-LC `mp4a.40.2` | ~320 kbps |
  | `LOSSLESS` | LOSSLESS | FLAC dans fMP4 | 16/44,1 |
  | `HI_RES_LOSSLESS` | HI_RES_LOSSLESS | FLAC dans fMP4 | 24/44,1 et 24/48 vus |

  Un titre sans version hi-res renvoie LOSSLESS 16/44,1 quand on demande HI_RES. Un titre Dolby Atmos renvoie du FLAC stéréo. Pas encore vu de 24/96 ni de 24/192.
- **Pas de DRM** : aucun élément `ContentProtection`, aucun `cenc:default_KID`/`pssh` dans le MPD, aucune boîte `pssh`/`tenc`/`sinf`/`enca` dans le segment d'initialisation. Attention : le MPD déclare **toujours** `xmlns:cenc`, même en clair, donc ce n'est pas un marqueur de DRM.
- **Métadonnées** : `track.audioQuality` vaut `LOSSLESS` même pour un titre hi-res, la disponibilité hi-res se lit dans `mediaMetadata.tags` (`HIRES_LOSSLESS`, `DOLBY_ATMOS`). Le format réel (`bitDepth`, `sampleRate`) n'est connu qu'avec `playbackinfopostpaywall`.
- **Lecture** : le MPD utilise `SegmentTemplate` + `SegmentTimeline` avec des URLs absolues signées. mpv le lit via le démuxeur DASH de ffmpeg s'il est servi en HTTP. Le spike le sert depuis la mémoire sur `127.0.0.1` (rien sur disque). Le backend Rust devra faire de même (petit serveur local) ou valider une autre approche. mpv sort en `s32` pour du 24 bits, c'est normal.
- À surveiller : un avertissement ffmpeg `dash: Error when loading first fragment of playlist` vu une fois sur un titre 24/48, sans effet sur la lecture.

## Implémentation (phase 1)

- **Identifiant client** : `TIDAL_CLIENT_ID` / `TIDAL_CLIENT_SECRET` (client PKCE) dans `.env`, injectés à la compilation par `build.rs`. Une variable d'environnement au lancement reste prioritaire.
- **Connexion** : fenêtre webview `login` (sans aucune capability) sur `login.tidal.com/authorize` ; `on_navigation` intercepte `https://tidal.com/android/login/auth?code=…` et bloque la navigation. Refresh token dans le Credential Manager (service `seaglass`, utilisateur `tidal-refresh-token`). L'access token (4 h) n'est jamais persisté, il est rafraîchi 60 s avant expiration ou sur 401, **une seule fois** pour toutes les requêtes en attente (revérifié sous le verrou en écriture, #148). Erreurs réseau sans leur URL (`From<reqwest::Error>` → `without_url`, #144) : celle du segment d'init est signée et finirait dans les journaux et les toasts.
- **Garde DRM** : avant chaque lecture, `tidal::manifest` rejette les MPD avec `ContentProtection` / `cenc:default_KID` / `cenc:pssh` / UUID Widevine, puis le segment d'initialisation (lu en mémoire) s'il contient `pssh`/`tenc`/`sinf`/`enca`.
- **Manifestes** : `mpv::serve` écoute sur `127.0.0.1:<port aléatoire>` et garde les 4 derniers MPD en mémoire ; mpv reçoit `http://127.0.0.1:<port>/<jeton>/<track>-<n>.mpd`. Le jeton (128 bits, hex, tiré au démarrage du serveur, #86) protège les URLs de flux signées des autres processus et comptes de la machine : sans lui, 404. Lecture et écriture sous un délai de 5 s, 16 connexions simultanées au plus (au-delà, refermée aussitôt) ; tests dans `serve.rs`, dont celui du délai (~5 s).
- **Pipe mpv** : `\\.\pipe\seaglass-mpv-<pid>-<128 bits aléatoires>` (`process::pipe_id`, `OnceLock` tiré une fois par lancement, partagé par `spawn` et `ipc::connect`) : un processus local ne peut pas créer le pipe avant mpv (#86).
- **CSP** (`tauri.conf.json`) : en plus de `default-src 'self'`, `base-uri 'none'`, `form-action 'none'` (les deux `<form>` font `preventDefault`) et `object-src 'none'`. Un nouvel hôte d'images va dans `img-src`.

## Implémentation (phase 2)

- **Acteur** découpé en `actor.rs` (boucle, commandes, émission), `playback.rs` (fenêtre mpv, gapless, erreurs) et `persist.rs`. Les résolutions réseau (métadonnées + flux) tournent hors de l'acteur et reviennent en `Cmd::Resolved` ; les compteurs `load_req` / `preload_req` écartent les réponses périmées.
- **Précédent** : l'historique garde l'origine de chaque titre (`queue/entry.rs` : `Context`, `Manual`, `Detached` = contexte remplacé ou file vidée). - **Shuffle** : Fisher-Yates sur tous les autres titres du contexte, piste courante en tête.
- **Erreurs** : nouvelle URL une fois par titre, puis titre suivant avec toast ; arrêt après 3 échecs consécutifs.

Écriture au plus toutes les 2 s (position seule pendant la lecture sur Android : 10 s, #147) : position seule, ou file + métadonnées des titres référencés absents de la table si la file a changé (incrémentale depuis #90, voir « Performances du backend »). - **Cache de métadonnées** en mémoire (`tidal::cache`), alimenté par la recherche et les listes ; il permet d'afficher la file sans requête. Borné depuis #90 (titres de la file épinglés).
- Vérifié en lecture réelle : préchargement à 25 s de la fin (`playlist-count=2`), bascule sans rechargement puis `playlist-count=1`, restauration à la bonne position avec mpv inactif.
- Vérifié en lecture réelle : `audio-codec-name=flac`, `current-ao=wasapi`, sortie `s16` 44,1 kHz pour un titre 16/44,1.

Bouton « Vérifier » dans Réglages › Application (0.4.6, #43) : `check_for_updates` lance la même vérification, sérialisée avec la tâche de fond (`UpdateState::checking`), et réémet `update-ready` si une version est prête, même déjà reportée. Il fonctionne aussi en debug (manifeste de production par défaut). **Réponse avant le téléchargement** (0.4.71, #187) : `check` rend la main dès le manifeste lu ; l'installeur (~42 Mo) se télécharge dans une tâche à part (`download`, `UpdateState::downloading`, un seul à la fois), puis `update-ready`, ou `update-failed` (message) en cas d'échec. `UpdateInfo::downloading` vrai tant que ce n'est pas fini : Réglages affiche « Version x disponible, téléchargement en cours… » puis « prête ». Aperçu : `?route=settings&tab=app&update=download`.
- **Signature** : clé minisign dans `%USERPROFILE%\.tauri\seaglass.key` (hors du dépôt), clé publique dans `tauri.conf.json` (`plugins.updater.pubkey`). **Perdre la clé privée** = plus aucune mise à jour acceptée par les versions installées (réinstallation manuelle) : elle doit être sauvegardée.
- **Mot de passe de la clé** (#87) : un fichier Tauri est le base64 d'une clé secrète minisign, **toujours chiffrée** (scrypt + XOR, `Sc`) ; « sans mot de passe » = mot de passe vide. Changer de clé casserait les mises à jour : on rechiffre la même avec `python -I scripts/protect-signing-key.py <clé> <nouvelle clé>` (bibliothèque standard, mots de passe au clavier sans écho, 12 caractères au moins, nouveau fichier, relu avant d'être gardé). Vérifié sur des clés jetables : signature de la clé rechiffrée acceptée par `minisign-verify` avec la clé publique d'origine. `release.ps1` teste d'abord le mot de passe vide (`--check`, mot de passe sur l'entrée standard) : clé encore sans mot de passe → avertissement et release normale ; sinon mot de passe pris dans `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`, puis l'entrée générique `seaglass-signing-key` du Gestionnaire d'identifiants (facultative : `cmdkey /generic:seaglass-signing-key /user:seaglass /pass`, plus pratique mais lisible par tout programme du compte), puis saisi sans écho ; vérifié avant le build, passé à Tauri par l'environnement seulement, retiré ensuite. Session non interactive sans mot de passe → échec explicite. Sans python, pas de vérification préalable (Tauri échoue à la signature sur un mauvais mot de passe). Procédure de rechiffrement dans l'issue #87.

Les mises à jour sont servies par le Caddy du serveur (Docker) : `updates.bebanana.ch` (CNAME vers `bebanana.internet-box.ch`) sert `/srv/updates` en lecture seule, `latest.json` en `Cache-Control: no-cache`. Le dossier est public, les installeurs étant signés.

Après `scp`, le script remet les droits à 755 / 644 : sinon le dossier de version arrive en écriture pour tous.
- **Profil release** (0.4.53) : `lto = "thin"` sur les 16 unités de compilation par défaut, et la lib en `["cdylib", "rlib"]` (pas de `staticlib`, iOS seulement). Avant, une LTO complète sur une seule unité était refaite pour chaque type de lib (staticlib, cdylib) puis pour l'exe, sur un seul cœur : recompiler la crate Seaglass seule prenait 3 min 11 s, 1 min 01 s depuis (mesuré le 2026-11-03, `touch src/lib.rs` puis `cargo build --release`). Ne pas remettre `codegen-units = 1` ni `lto = true` sans mesurer.
- **Release** : `pnpm release` (`scripts/release.ps1`) vérifie l'arbre git, `.env`, la clé et `VERSION`, embarque mpv, lance `pnpm tauri build --config src-tauri/tauri.release.conf.json`, puis écrit `release/latest.json`, `release/<version>/Seaglass_<version>_x64-setup.exe` et la page de téléchargement `release/index.html` (modèle `scripts/download-page.html`, champs `{{…}}` échappés en HTML, nouveautés tirées des notes). Avec `-Publish`, il copie vers `SEAGLASS_RELEASE_DEST` (dossier ou cible scp) l'installeur, puis la page, le manifeste en dernier, puis pose et pousse le tag `v<version>`. Une release = un tag : pas de mise à jour à chaque push. Le `.sig` est aussi gardé dans `release/<version>/` (depuis #108). **Build de test** (arbre modifié, `-AllowDirty`) : installeur non compressé (`scripts/tauri.test.conf.json`, `compression: none`), makensis ~1 s pour 140 Mo au lieu de ~50 s pour 42 Mo en LZMA (mesuré le 2026-11-03 : zlib 14 s / 57 Mo, bzip2 10 s / 54 Mo ; LZMA gardé pour les releases, l'updater télécharge l'installeur entier depuis la connexion de la maison). Décidé sur l'arbre réellement modifié, pas sur le drapeau : un tel build n'est jamais publiable (`-PublishOnly` refuse un repère `dirty`).
- **Release complète** (`scripts/release-all.ps1`, recommandée) : `powershell -File scripts/release-all.ps1 [-Publish] [-Notes …]` construit l'installeur puis l'APK **sans rien publier**, puis, avec `-Publish`, publie Windows puis Android, pose le tag et crée une seule release Gitea avec les deux. Un build en échec = rien en ligne. Chaque étape tourne dans son propre processus `powershell`. Alias `pnpm release:all` (0.4.52, ajouté avec un vrai changement de l'app : `package.json` compte pour le contrôle de version) ; les options suivent (`pnpm release:all -Publish`). Les deux scripts acceptent `-PublishOnly` (publie le dernier build sans le refaire) et `-SkipGiteaRelease`. Chaque build écrit un repère `release/.build/<windows|android>.json` (`version`, `commit`, `dirty`, `scripts/build-stamp.ps1`) : `-PublishOnly` refuse un build d'une autre version, d'un autre commit ou d'un arbre modifié. La publication Windows ne copie plus que l'installeur et son `.sig`, pas tout `release/<version>/` (l'APK y est aussi). Ne publier jamais automatiquement (CI ou changement de `VERSION`) : les clés de signature restent sur le PC, voir « Pas de release en CI ».
- **Release Gitea** (#108, `scripts/gitea-release.ps1`, appelé par `-Publish` après le tag) : release `Seaglass <version>` sur le tag avec en pièces jointes ce qui existe dans `release/` pour cette version : l'installeur, son `.sig` et `latest.json`, l'APK et `android.json` (les fichiers publiés, rien n'est reconstruit en CI : la clé reste sur le PC). Jeton **de l'utilisateur** (pas celui de `claude` : la release est à son nom), droit `write:repository`, dans `SEAGLASS_GITEA_TOKEN` ou l'entrée générique `seaglass-gitea-token` du Gestionnaire d'identifiants (`cmdkey /generic:seaglass-gitea-token /user:seaglass /pass`) ; lecture partagée avec le mot de passe de la clé dans `scripts/credentials.ps1`. Un échec n'est qu'un avertissement (la mise à jour est déjà en ligne) : relancer `powershell -File scripts/gitea-release.ps1 [-Version x.y.z]`. Relancé, il remplace les pièces jointes du même nom. Pour une version publiée avant #108 : installeur seul (pas de `.sig` gardé), `latest.json` non joint s'il décrit une autre version, notes tirées de `git log` depuis le tag précédent ; le tag doit exister sur `origin`. Pas d'alias `pnpm` : `package.json` ferait monter la version de l'app (contrôle de la CI). Testé contre un faux serveur Gitea (création, relance, jeton absent ou refusé, serveur injoignable, ancienne version) ; pas encore contre le vrai. `[attachment] ALLOWED_TYPES` du serveur exclut `.exe`, mais les releases ont leur propre réglage (`[repository.release] ALLOWED_TYPES`, vide = tout) : si Gitea refuse l'installeur, c'est là.

## Implémentation (phase 5 : CI)

- **Workflow** : `.gitea/workflows/ci.yml`, sur push vers `main` et sur chaque PR, sauf si seuls des `*.md` / `LICENSE` changent : contrôle de version, `pnpm check`, `pnpm build`, `cargo fmt --check`, `clippy -D warnings`, `cargo test`. `pnpm build` passe avant Rust car `tauri::generate_context!` exige `dist/`. Ni `.env` ni `fixtures.json` ne sont nécessaires.
- **Contrôle de version** (`scripts/check-version.sh`, checkout avec `fetch-depth: 0`) : échoue si `VERSION` est inférieure au dernier tag `v*`, ou si elle lui est égale alors que des fichiers de l'app ont changé depuis ce tag (hors `*.md`, `LICENSE`, `.gitea/`, `ci/`, `scripts/`, `spike/`, `.claude/`, `.mcp.json`, `.gitignore`, `.gitattributes`, `src/lib/mock/`). Un changement de tests Rust seuls demande donc aussi une nouvelle version. Lançable en local : `bash scripts/check-version.sh`. Pas de publication automatique : la clé de signature reste sur le PC et l'installeur se construit sous Windows.
- **Runner dédié** (`ci/`, installation dans `ci/README.md`) : `act_runner` 0.6.1 en Docker sur le serveur, enregistré **au niveau du dépôt**, label `seaglass`. Il monte le socket Docker, donc il équivaut à root sur le serveur : ne jamais l'ouvrir à d'autres dépôts. Le runner partagé (firmware, KiCad) n'est plus utilisé.
- **Image des jobs** `seaglass-ci:<tag daté>` (`ci/Dockerfile`, base `node:24-bookworm`) : bibliothèques de Tauri, Rust stable + rustfmt + clippy, pnpm. Construite sur le serveur (`docker compose --profile build build`), sans registre (`force_pull: false`). Changer de tag = `.env` + label de `config.yaml`.
- **Cache** : les jobs rejoignent le réseau du runner (`container.network: seaglass-ci`) et le cache écoute sur un port fixe (8088). Sans ça, chaque action de cache attend 5 min un `ETIMEDOUT` (vu sur le runner partagé).
- **Limite** : sous Linux, le code `#[cfg(windows)]` (SMTC, Job Object, `CREATE_NO_WINDOW`) n'est ni compilé ni testé ; `pnpm release` le vérifie sous Windows. Du code partagé utilisé seulement par une intégration Windows doit tolérer le code mort hors Windows (`#[cfg_attr(not(windows), allow(dead_code))]`, voir `integrations/mod.rs` et `Cmd::SetPaused`), sinon clippy échoue en CI. L'IPC mpv passe par un socket Unix hors Windows (`mpv::ipc::open`).
- **Durée** : environ 7 min sur le runner partagé, sans cache (préparation ~4 min, clippy ~1 min, tests ~1 min 30). Runner dédié (2026-10-30) : 5 min sans cache (Rust ~2 min 40, sauvegarde du cache ~1 min 40), 4 min 30 au premier run de `main` (cache restauré en 35 s mais clé partielle, Rust ~1 min 15, nouvelle sauvegarde ~2 min 20). Un run dont la clé correspond exactement ne sauvegarde pas : durée en régime établi à confirmer. 2026-11-03 : runs d'environ 2 min avec le cache complet (restauration de 1,9 Go ~1 min 15, clippy 7 s, compilation des tests 18 s), mais un run est resté figé plus de 10 min sur la compilation des tests (mémoire du serveur soupçonnée). Depuis : `timeout-minutes: 20` sur le job et `CARGO_PROFILE_{DEV,TEST}_DEBUG=0` (pas d'infos de débogage : édition de liens plus légère, cache plus petit ; les variables `CARGO_*` entrent dans la clé du cache, le premier run après ce changement repart sans cache). L'API Gitea n'expose pas l'annulation d'un run (404) : annuler depuis l'interface web.
- **Mise en service** : si un job démarre sur `runner-images:ubuntu-latest` avec un réseau `…-check-network`, le runner ne lit pas `config.yaml` (conteneur lancé depuis d'anciens fichiers). Le `data/.runner` appartient à root : `sudo rm` pour réenregistrer.
- **Pas de release en CI** : la clé minisign reste sur le PC, `pnpm release` reste manuel.

## Langue (0.4.17, #7)

- **Choix proposé dans l'issue** : pas de bibliothèque i18n, un module maison typé (deux langues). Réglage Réglages › Apparence › Langue : `system` (défaut, confirmé par l'utilisateur : un Windows en anglais passe l'app en anglais à la mise à jour), `fr`, `en` (`UiSettings::language`).
- **Langue effective décidée côté Rust** (`i18n.rs`) : réglage, sinon langue d'affichage de Windows (`GetUserDefaultUILanguage`, français si la langue principale est le français, anglais sinon), `java.util.Locale.getDefault()` par JNI sur Android (#186, `android::system_language` : Android ne pose pas `LANG`), `LANG` ailleurs (`from_code`, testé). Appliquée au démarrage avant le lecteur, puis par `set_language` (renvoie la langue effective) et `set_ui_settings`. Commande `language` pour l'UI. État global atomique : lu par les messages et la `locale`, jamais par la logique.
- **Messages du backend** : `i18n::tr(fr, en)` pour un texte fixe, `trf!("… {}", "… {}", args)` pour un texte formaté, utilisables dans `#[error("{}", trf!(…, .0))]` de `thiserror`. ## Implémentation (édition hi-res, 0.4.8, #18)

- **Principe** : un titre sans tag `HIRES_LOSSLESS` existe souvent en 24 bits sur une autre édition (album d'origine, réédition, compilation) avec la même ISRC. `Track::isrc` (absent des titres enregistrés avant 0.4.8 : redemandé via `tracks/{id}`), puis `GET v1/tracks?isrc=<ISRC>&limit=50` (vérifié le 2026-10-30 : toutes les éditions avec leurs tags, ~130 ms ; `cargo test live_hires -- --ignored --nocapture`). Les versions Dolby Atmos ont une autre ISRC.
- **Album jumeau** (0.4.13, #55, `tidal/twin.rs`, logique pure testée) : certains labels publient le master hi-res comme un album à part, au même titre, **sous d'autres ISRC** (Eagles, « Hotel California (2013 Remaster) » : `20767338` en 16/44,1 et `68709104` en 24/192, ISRC `USEE11300353` / `USEE11300195`). Ni `tracks?isrc=` ni la recherche (qui déduplique les éditions) ne le voient ; la discographie de l'artiste (`artists/{id}/albums`, avec et sans `filter=EPSANDSINGLES`) liste les deux. Repli quand l'ISRC ne donne rien : albums hi-res de l'artiste principal au titre identique (casse et espaces ignorés), puis titre de même nom, même version, durée à ±2 s. Discographie chargée **en parallèle** de la requête ISRC ; cache par artiste (albums hi-res) et par album jumeau (titres hi-res). Mesuré (`cargo test live_hires_twin -- --ignored --nocapture`) : ~430 ms au premier titre, ~170 ms pour les suivants de l'album.
- **Choix** (`tidal/hires.rs`, logique pure testée) : hi-res, lisible (`streamReady` / `allowStreaming`), durée à ±2 s ; préférence pour un album de même titre puis le même marquage explicite, sinon l'ordre de l'API. Résultat mis en cache en mémoire par id d'origine, « aucune » compris ; les erreurs ne sont pas mises en cache.
- **Résolution** (`player/upgrade.rs`) : titre suivant = recherche puis flux pendant le préchargement (invisible) ; titre courant = recherche en parallèle du flux d'origine, limitée à 1,5 s, sans demande du flux d'origine si la réponse est en cache. L'autre flux n'est retenu que s'il est `HI_RES_LOSSLESS` et meilleur (profondeur ou fréquence, sans perdre sur l'autre axe) ; sinon, ou en cas d'erreur, flux d'origine. Mesuré : ~480 ms au premier lancement, ~250 ms ensuite (autant qu'un titre normal).
- **Ce qui change** : seulement le flux. File, historique, favoris, SMTC et affichage gardent le titre d'origine. `StreamFormat::hires_edition` (titre de l'album de l'édition lue) → « Hi-Res · autre édition » sous la source de la chaîne audio, et (0.4.10) une ligne « Édition hi-res : <album> » sous la chaîne complète (`.hires-edition`, « En lecture » ; pas dans la version resserrée de la barre Studio, qui garde l'info-bulle). L'UI ne déduit rien : tout vient de `player-state`. Choix confirmés par l'utilisateur dans l'issue : indication visible, réglage activé par défaut. Aperçu : `?hiresedition=Thriller` (le backend factice remplace aussi un titre non hi-res joué si le réglage est actif).
- **Réglage** `PlaybackSettings::hires_upgrade` (Réglages › Lecture › Qualité) : `auto` (défaut), `ask` ou `off` depuis 0.4.15 (#59) ; l'ancien booléen est relu (`true` = `auto`). Appliqué à la résolution suivante (`Cmd::SetPlaybackSettings`, qui remplace `SetCacheSize`). Le master de l'autre édition peut différer (autre remastérisation) : c'est la raison de l'indication et du réglage.
- **Mode « Demander »** (0.4.15, #59, `player/upgrade.rs`) : le titre d'origine démarre sans attendre la recherche ; `maybe_offer_hires` la lance ensuite en arrière-plan (`find_offer` : édition + `playback_format`, sans lire le flux) et, si l'édition est meilleure (`is_better`), `PlayerState::hires_offer` porte son format (album dans `hires_edition`). Compteur `offer_req` contre les réponses périmées ; offre retirée à chaque changement de titre ou de réglage. Bandeau `components/HiresOffer.svelte` au-dessus de la barre de lecture ; `answer_hires_offer(accept)` : la réponse vaut pour l'album pendant la session (`Player::hires_answers`, non persisté). Oui = rechargement à la même position (la lecture reprend, le suivant préchargé est retiré), puis bascule automatique des autres titres de l'album ; non = plus d'offre pour cet album. Infos du titre : `played` seulement en mode automatique. Pas une fenêtre modale : elle couperait l'écoute à chaque titre d'un album.
- **Lien vers l'album hi-res** (0.4.15, #59) : `hires_twin_album(albumId)` (`tidal/twin.rs`) = album hi-res de l'artiste principal au même titre (logique de l'album jumeau, discographie en cache), `None` si l'album est déjà hi-res. Appelé par `Album.svelte` après l'affichage ; bandeau « Cet album existe en Hi-Res → Ouvrir » (`.hires-twin`). ## Conventions

- Rust : `cargo fmt` et `clippy -D warnings` doivent passer. Pas de `unwrap()` / `expect()` hors tests et initialisation. Erreurs typées avec `thiserror` dans les modules, `anyhow` seulement aux frontières.
- Les commandes Tauri renvoient `Result<T, String>` ou une erreur sérialisable, jamais de panic.
- Les types partagés UI ↔ Rust sont définis côté Rust et dupliqués dans `src/lib/ipc.ts` (envisager `tauri-specta` si ça devient pénible).
- Tests unitaires obligatoires pour `player/queue.rs` (shuffle, repeat, file manuelle, précédent) : c'est de la logique pure, sans mpv ni réseau.
- Identifiants et code en anglais, commentaires et docs en français.
- Commits au format Conventional Commits (`feat(player): …`). Dépôt sur le Gitea perso (`origin`). Claude peut commiter et pousser seul, en le signalant dans son message.
- **Version** : `VERSION` à la racine est la source de vérité, affichée dans l'en-tête de l'app. `0.<phase>.<patch>` avant la 1.0 : patch à chaque lot de changements **qui modifie l'app livrée** (code, config, dépendances), mineure à la fin d'une phase. Pas de changement de version pour la seule documentation (`*.md`), sinon chaque correction de doc deviendrait une « mise à jour » une fois l'updater en place. La CI le vérifie (voir « Contrôle de version »). `src-tauri/Cargo.toml` doit être mis à jour en même temps (`build.rs` fait échouer la compilation sinon) ; `tauri.conf.json` n'a pas de version et reprend celle de Cargo.
- Licence GPL-3.0 (`LICENSE`).

## Issues Gitea (pour Claude)

- Dépôt : `bebanana/Seaglass` sur `https://git.bebanana.ch` (Gitea 1.27). L'API exige une authentification.
- Accès via le serveur MCP officiel `gitea-mcp` (v1.11.0, installé dans `%LOCALAPPDATA%\Programs\gitea-mcp\`), déclaré dans `.mcp.json`. Il agit sous le compte dédié `claude` (collaborateur en écriture du dépôt), pour que ses issues, commentaires et PR se distinguent de ceux de l'utilisateur et lui soient notifiés. Le jeton de ce compte vient de la variable d'environnement utilisateur `GITEA_CLAUDE_TOKEN` (droits `write:issue`, `write:repository`, `read:user`) : ne jamais l'écrire dans un fichier ni l'afficher. Le jeton personnel de l'utilisateur n'est pas utilisé par Claude : si les outils Gitea échouent (variable absente, jeton révoqué), le signaler à l'utilisateur plutôt que de revenir à `GITEA_ACCESS_TOKEN` ou de passer par l'API avec un autre jeton. Vérification : `get_me` doit renvoyer `claude`. Les commits restent à l'identité git de l'utilisateur, avec la ligne `Co-Authored-By` ; la fusion des PR revient à l'utilisateur. Outils utiles : `list_issues`, `issue_read` (`method: get` / commentaires), `issue_write` (commenter, labels), `pull_request_write`.
- **Labels** (2026-11-04, labels à portée de Gitea) : `platform/android` | `platform/windows` (exclusif ; aucun = les deux), `type/bug` | `feature` | `improvement` | `perf` | `security` | `chore` | `docs` (exclusif), `area/player` | `tidal` | `ui` | `theme` | `library` | `release` | `ci` (plusieurs possibles), `status/needs-info` | `blocked` | `wontdo` | `duplicate` (exclusif). Toute issue créée ou traitée reçoit au moins un `type/` et une `area/` ; `status/needs-info` quand elle attend une réponse de l'utilisateur, retiré quand il a répondu ; `status/wontdo` sur une proposition écartée.
- Pour traiter une issue : la lire avec ses commentaires, poster un commentaire avec le plan avant de coder, travailler sur une branche `issue-<n>-<sujet>`, référencer l'issue dans le commit (`fix(ui): … (#8)`) et ouvrir une PR vers `main` avec `Closes #<n>`. Répondre dans l'issue si une question s'y pose plutôt que de deviner.
